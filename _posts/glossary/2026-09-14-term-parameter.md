## 한 줄 정의

> 모델이 학습하면서 스스로 맞춰 놓은 숫자. 모델 크기를 말할 때 세는 단위다

---

## 1. 비유로 이해하기

코코아를 탄다고 해 보자. 맛을 정하는 손잡이가 두 개 있다. **가루를 몇 숟갈** 넣을지, **우유를 몇 ml** 부을지.

처음엔 대충 넣고 맛본다. 너무 달면 가루를 조금 줄이고, 싱거우면 조금 늘린다. 몇 번 고치다 보면 딱 맞는 숫자가 나온다. 그 숫자를 레시피 카드에 적어 두면, 다음부터는 **맛보고 고칠 필요 없이** 카드대로 타기만 하면 된다.

{% include figure.html src="/assets/images/term-parameter/knob-scale.svg" alt="학습으로 맞춰지는 숫자인 파라미터의 개수를 비교한다. 코코아 레시피와 카페 매출 선형모델은 2개, qwen3:0.6b는 6억 개, Llama 3.1 8B는 80억 개, 대형 언어모델은 수천억 개다" caption="그림 1. 손잡이 2개에서 수천억 개까지" %}

그래서 실제로는 모델 안의 **가중치** 하나하나가 이 손잡이다. 학습은 예측해 보고, 틀린 만큼 손잡이를 조금씩 돌리는 일의 반복이다. 학습이 끝나면 숫자가 고정되고, 우리는 그 레시피 카드(모델 파일)를 받아서 쓰기만 한다. 코코아는 손잡이가 2개지만 언어모델은 수십억에서 수천억 개다.

## 2. 왜 필요한가

### 모델 이름의 B가 이것이다

모델 이름 끝의 숫자는 거의 항상 파라미터 개수다. B는 billion, 곧 **10억**이다.

| 이름 | 파라미터 개수 |
| --- | --- |
| qwen3:0.6b | 6억 개 |
| 7B 모델 | 70억 개 |
| Llama 3.1 8B | 80억 개 |
| gpt-oss-20b | 총 210억 개 (21B) |

이름만 보고도 "대략 얼마나 무거운가"를 가늠할 수 있다.

### 개수 × 바이트 = 파일 크기

숫자 하나를 몇 바이트로 적느냐에 따라 파일 크기가 정해진다.

```
7B × 2바이트(FP16)     = 약 14GB
7B × 0.5바이트(4비트)  = 약 3.5GB   ← 양자화
```

내 노트북에 받은 qwen3:0.6b는 **6억 개짜리인데 파일이 522MB**였다. 다운로드는 90초 걸렸다. 6억 개 숫자가 반 기가바이트 남짓에 들어간 것이다.

### 만들 때와 쓸 때는 짐이 다르다

같은 파라미터라도 **학습할 때**는 숫자 하나에 딸린 짐이 훨씬 많다. 손잡이를 어느 쪽으로 돌릴지 적은 메모(그래디언트), 지금까지 어떻게 돌려 왔는지 적은 기록(옵티마이저 상태)까지 함께 들고 있어야 한다.

| | 파라미터 하나당 | 7B 모델이면 |
| --- | --- | --- |
| 학습 | 18바이트 + 중간값(활성값) | 126GB 이상 |
| 추론(쓰기만) | 2바이트 (FP16) | 14GB 남짓 |

아홉 배 가까이 차이 난다. 그래서 **모델을 만드는 건 데이터센터의 일이고, 쓰는 건 노트북의 일이 될 수 있다.** 남이 맞춰 놓은 레시피 카드를 읽기만 하면 되기 때문이다.

### 총 파라미터와 활성 파라미터

요즘 모델 중에는 숫자를 전부 올려 두되 **일부만 쓰는** 구조(MoE)가 있다. 여러 전문가를 두고, 단어마다 그중 몇 명에게만 일을 시킨다.

```
gpt-oss-20b
  총 파라미터   21B   → 메모리에 다 올려야 한다
  활성 파라미터 3.6B  → 단어 하나 만들 때 실제로 계산하는 몫
  층마다 전문가 32명 중 4명만 골라 쓴다
```

그래서 두 숫자를 따로 봐야 한다. **메모리에 들어가느냐는 총 파라미터, 얼마나 빠르냐는 활성 파라미터**가 정한다.

### 개수가 적으면 무엇이 무너지나

작은 모델은 문장은 만들어 내지만 지시를 자주 흘리고 형식을 못 지킨다. 수업 자료는 1GB 안팎 모델을 "어디서부터 무너지는지 보는 대조군"으로 썼다.

내 노트북에서 qwen3:0.6b와 대화하고 번역도 시켜 봤다. 실력은 어딘가 엉성하고 석연찮았다. 그런데 반응은 무척 빨라서 **초당 41.7토큰**이 나왔다. 손잡이 6억 개로는 실력이 모자라지만, 적은 만큼 가볍다는 걸 몸으로 봤다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| 파라미터 | 가중치 | 가중치는 파라미터의 대부분을 차지하는 숫자. 모델 크기를 말할 때는 거의 같은 뜻으로 쓴다 |
| 파라미터 | 토큰 | 파라미터는 **모델 안에 고정된 숫자**, 토큰은 **모델에 넣고 받는 글 조각**. 7B는 모델 크기, 128K는 한 번에 넣는 글 길이 |
| 파라미터 | 실행 설정값 | Ollama의 `/set parameter num_ctx`, 온도 같은 건 **내가 돌릴 때 정하는 값**이다. 학습으로 맞춰진 숫자가 아니다 |
| 총 파라미터 | 활성 파라미터 | 총은 **메모리**를 정하고, 활성은 **속도**를 정한다. MoE 모델에서만 둘이 갈린다 |

## 5. 많이들 오해하는 지점

**ㄱ. "파라미터가 크면 무조건 똑똑하다"**

질문에 따라 다르다. 짧고 정답이 분명한 사실 확인 질문은 작은 모델도 곧잘 맞힌다. 크기의 값어치는 조건 여러 개를 동시에 맞춰야 하는 추론, 출력 형식을 엄격히 지켜야 하는 요청에서 드러난다.

그러니 "몇 B냐"보다 **"내 일에 필요한 것을 지키는 가장 작은 모델이 무엇이냐"**를 묻는 편이 낫다.

**ㄴ. "큰 모델은 무조건 느리다"**

MoE 구조라면 아니다. gpt-oss-20b는 총 21B지만 단어 하나를 만들 때는 3.6B만 계산한다. 메모리 요구량은 21B급인데 속도는 3.6B급에 가깝다.

**ㄷ. "파라미터 개수만 알면 필요한 메모리를 안다"**

두 가지가 더 필요하다. 하나는 **숫자 하나를 몇 바이트로 적었나**다. 같은 7B라도 FP16이면 14GB, 4비트면 3.5GB 남짓이다.

다른 하나는 **대화가 길어지며 쌓이는 KV 캐시**다. 이건 파라미터와 상관없이 대화 길이에 따라 늘어난다. 파라미터 개수는 계산의 출발점이지 끝이 아니다.
