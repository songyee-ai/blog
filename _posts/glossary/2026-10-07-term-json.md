## 한 줄 정의

> 이름표와 값을 짝지어 적는, 사람도 읽고 프로그램도 그대로 읽어 들일 수 있는 글자 데이터 형식

---

## 1. 비유로 이해하기

소풍 가는 날, 칸이 나뉜 도시락통에 칸마다 **이름표**를 붙였다고 해 보자.

```
[밥]     김밥 10줄
[과일]   사과, 귤, 포도
[음료]   보리차
[간식]   (없음)
```

누가 열어 봐도 "과일 칸에는 무엇이 있지?"를 바로 찾을 수 있다. 이름표가 없으면 "두 번째 칸이 과일이었나?" 하고 헷갈린다. 같은 도시락을 JSON으로 적으면 이렇다.

```json
{
  "밥": "김밥",
  "줄수": 10,
  "과일": ["사과", "귤", "포도"],
  "음료": "보리차",
  "간식": null
}
```

- `"과일"` 같은 **이름표(키)** 와 `["사과", "귤", "포도"]` 같은 **내용(값)** 이 짝을 이룬다.
- 중괄호 `{ }` 는 이름표 붙은 칸들을 묶은 **도시락통 하나**(객체)다.
- 대괄호 `[ ]` 는 한 칸 안에 **줄 세워 담은 것**(배열)이다. 순서가 있다.
- `null` 은 "이 칸은 비어 있다"를 일부러 적은 것이다. 칸 자체를 빼먹은 것과는 다르다.

실제로는, JSON은 이런 모양으로 적은 **글자(텍스트)** 다. 사람 눈에는 읽기 쉬운 메모이고, 프로그램은 이 글자를 읽어 "과일 칸의 두 번째 값" 같은 것을 바로 꺼내 쓸 수 있는 데이터로 바꾼다. 이름은 자바스크립트에서 왔지만 지금은 파이썬을 비롯해 거의 모든 언어가 읽고 쓴다. 웹에서 {% include term.html name="API" %}가 요청과 응답을 주고받을 때 가장 흔히 쓰는 형식이기도 하다.

## 2. 왜 필요한가

### 프로그램이 받아서 바로 쓰려면

사람에게는 "과일은 사과랑 귤, 포도예요"라는 문장이 충분하다. 프로그램에게는 아니다. 문장 속 어디까지가 과일 이름인지 매번 추측해야 한다. JSON으로 받으면 추측할 필요가 없다.

```python
import json

text = '{"과일": ["사과", "귤", "포도"], "간식": null}'
box = json.loads(text)      # 글자 → 파이썬 값

print(box["과일"][1])        # 귤
print(box["간식"] is None)   # True  (JSON의 null은 파이썬의 None)
```

`json.loads()` 처럼 글자를 읽어 프로그램이 쓸 수 있는 값으로 바꾸는 일을 **파싱**이라고 한다. 파싱을 해 주는 부품을 파서라고 부른다.

### 파서는 아주 깐깐하다

JSON 문법은 짧지만 엄격하다. 글자 묶음은 반드시 큰따옴표로 감싸야 하고, 마지막 값 뒤에 쉼표를 남기면 안 되며, 주석도 넣을 수 없다. 하나만 어겨도 파서는 일부만 읽어 주는 게 아니라 **통째로 멈춘다**.

20회차 실습에서 이것을 직접 봤다. 모델에게 고객 답변을 `reply`, `question` 두 키를 가진 JSON 객체로만 내라고 했더니, 세 번 모두 내용은 멀쩡했는데 응답 맨 앞에 마크다운 코드 펜스가 붙어 있었다.

````text
```json
{"reply": "...", "question": "주문번호를 알려주실 수 있을까요?"}
```
````

사람 눈에는 JSON이 분명하지만, `json.loads()` 는 첫 글자부터 백틱(`` ` ``)을 만나 세 번 모두 `JSONDecodeError` 를 냈다. 형식 기준은 0/3이었다. 지시 끝에 "코드 펜스나 설명 없이 중괄호로 시작하고 끝나는 JSON 객체만 출력하라"는 문장 하나를 더하자, 다시 돌린 세 번 모두 파싱에 성공했다(3/3).

### 파싱 성공은 "모양이 맞다"까지만 말해 준다

블록 끼우기 장난감을 떠올려 보자. 세모 구멍에는 세모 블록만 들어간다. 그런데 구멍은 **모양만** 본다. 빨간 세모가 와야 할 자리에 파란 세모를 넣어도 쏙 들어간다.

실제로는, 파서와 검사기는 구멍이고 모델의 답은 블록이다. 모양이 맞으면 통과시키지만, 안에 든 내용이 사실인지는 보지 않는다.

같은 날 다른 실습에서 작은 모델(`qwen3.5:2b`)에게 "한국의 3대 강을 알려줘. JSON 배열로만 답하라"를 세 번 보냈다.

| 회차 | 응답 | 파싱 | 내용 |
| --- | --- | --- | --- |
| 1 | `["강남강", "낙동강", "성수강"]` | 성공 | 틀림 (강 두 개가 없는 강) |
| 2 | `[강 (강), 한강, 유고강, 해남강]` | **실패** (따옴표 없음) | 틀림 |
| 3 | `["안녕하세요"]` | 성공 | 틀림 (강 이름이 아님) |

파서만으로 채점했다면 2/3 통과였다. 실제로 맞는 답은 0/3이었다. 3번 `["안녕하세요"]` 는 문법상 완벽한 JSON 배열이다. **형식 통과와 내용 정확은 따로 재야 한다.**

### 모양을 미리 정해 두는 JSON Schema와 validator

"키는 `reply` 와 `question` 두 개, 둘 다 비어 있지 않은 글자"처럼 JSON이 어떤 모양이어야 하는지를 적어 둔 규칙서를 **JSON Schema**라고 한다. 규칙서 자체도 JSON으로 쓴다. 자세한 읽는 법은 {% include term.html name="스키마" %} 글에 정리해 두었다.

이 규칙서를 들고 실제 JSON을 하나하나 대조하는 프로그램이 **validator(검증기)** 다. 역할을 나누면 이렇다.

| 검사 | 잡아내는 것 | 못 잡는 것 |
| --- | --- | --- |
| 파서 | 따옴표 누락, 코드 펜스, 쉼표 오류 같은 **문법** | 키가 빠졌는지, 값이 맞는지 |
| 스키마 validator | 필수 키 누락, 글자 자리에 숫자, 허용하지 않은 값·추가 키 | 값이 **사실**인지 |
| 내용 검사 (사람·원문 대조) | "강남강"이 실제로 없는 강이라는 것 | — |

### JSON을 받는 세 가지 방법

모델에게 JSON을 받는 길은 크게 세 갈래다. 아래로 갈수록 약속이 단단해진다.

1. **프롬프트로 부탁하기** — 지시문에 "JSON으로만 답하라"라고 쓰고 예시를 보여 준다. 어디서나 쓸 수 있지만 말로 한 부탁일 뿐이다. 위의 코드 펜스 사례처럼 문법부터 깨질 수 있다.
2. **JSON 모드** — 호출 설정에서 켜는 기능이다. 일반적으로 "파싱되는 JSON"을 내도록 맞춰 주지만, 내가 원하는 키가 다 들어 있는지까지 약속하지는 않는다.
3. **구조화 출력 (strict schema)** — JSON Schema를 호출에 함께 넘겨, 모델이 그 모양에서 벗어난 답을 내지 못하게 막는 기능이다. 지원하는 스키마 문법 범위 안에서 필수 키와 자료형을 맞춰 준다.

{% include figure.html src="/assets/images/term-json/three-promises.svg" alt="세 칸짜리 사다리. 맨 아래 프롬프트로 부탁하기는 문법도 보장하지 않고, 가운데 JSON 모드는 파싱은 되지만 키 구성은 보장하지 않으며, 맨 위 구조화 출력은 스키마 모양까지 맞춘다. 세 칸 모두 옆에 내용이 사실인지는 따로 검사해야 한다는 띠가 붙어 있다" caption="그림 1. JSON을 받는 세 가지 약속과, 셋 다 대신해 주지 않는 것" %}

이름과 지원 범위는 회사마다 다르다. OpenAI는 JSON 모드와 스키마를 엄격히 따르는 구조화 출력을 별개 기능으로 나눠 두고 있고, 다른 회사들도 비슷한 기능을 "도구 입력 스키마를 엄격히 지키게 하는 설정" 같은 다른 이름으로 제공한다. 언제 무엇이 바뀔지 모르니, 쓰기 전에 그 회사의 공식 문서에서 지금 지원하는 범위를 확인한다.

그리고 세 번째 방법을 써도 내용은 따로 봐야 한다. 스키마가 막아 주는 것은 모양이지, "강남강" 같은 지어낸 값이 아니다.

## 3. 어디서 만났나

JSON이라는 말은 전부터 여러 글에 링크로만 걸려 있었다. 도구의 입력 모양을 적는 {% include term.html name="스키마" %}(6·7회차)와, 프로그램끼리 데이터를 주고받는 {% include term.html name="API" %}(4회차)에서다. 정식으로 따로 정리한 것은 이번이 처음이다.

**20회차**에서는 "답의 모양을 약속한다"는 흐름 안에서 깊게 다뤘다. 파싱 성공이 곧 정답은 아니라는 것, 스키마와 validator가 잡는 것과 못 잡는 것, 그리고 프롬프트 부탁·JSON 모드·구조화 출력이 서로 다른 수준의 약속이라는 것이었다. 실습에서는 위의 "3대 강" JSON 배열 실험과, 코드 펜스 하나 때문에 형식 기준이 0/3이었다가 문장 하나를 더해 3/3이 된 지시 비교 실험을 했다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| JSON | JSON Schema | JSON은 **실제 값이 담긴 도시락**, JSON Schema는 "칸이 무엇무엇이어야 한다"는 **규칙서**. 규칙서도 JSON으로 쓰기 때문에 더 헷갈린다 |
| JSON | 파이썬 딕셔너리 | 생김새가 닮았지만 JSON은 **글자**이고 딕셔너리는 프로그램 안의 **값**이다. `json.loads()` 로 글자→값, `json.dumps()` 로 값→글자. JSON은 `true`·`null`, 파이썬은 `True`·`None` |
| 파싱 성공 | 정답 | 파싱은 **문법이 맞다**는 뜻일 뿐이다. `["안녕하세요"]` 도 파싱된다 |
| JSON 모드 | 구조화 출력 (strict schema) | JSON 모드는 대개 **읽히는 JSON**까지, 구조화 출력은 넘겨준 **스키마 모양**까지 맞춘다. 정확한 범위는 회사마다 다르다 |

## 5. 많이들 오해하는 지점

**ㄱ. "사람 눈에 JSON처럼 보이면 JSON이다"**

코드 펜스 사례가 그 반례다. 화면에서는 중괄호와 키가 다 보이는데, 파서는 맨 앞 백틱 세 개에서 바로 멈췄다. 프로그램이 받아 쓸 JSON인지는 눈이 아니라 `json.loads()` 같은 파서로 확인한다.

**ㄴ. "JSON으로 받으면 답이 정확해진다"**

형식이 정돈되는 것과 사실이 맞는 것은 다른 일이다. "3대 강" 실험에서 파싱은 2/3이 통과했지만 맞는 강 이름은 하나도 없었다. 형식 검사와 내용 검사를 한 점수로 합치면 어느 쪽이 깨졌는지도 안 보인다.

**ㄷ. "구조화 출력을 켜면 validator는 필요 없다"**

구조화 출력이 맞춰 주는 것은 넘겨준 스키마의 모양이다. 값이 원문에 있는지, 업무 규칙에 맞는지는 여전히 모른다. 지원하지 않는 스키마 문법이 있을 수도 있고, 응답이 중간에 잘리거나 모델이 답을 거절하는 경우도 따로 처리해야 한다. 받는 쪽에서 한 번 더 검사하는 습관은 남겨 둔다.
