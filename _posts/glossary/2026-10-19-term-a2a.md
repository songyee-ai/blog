## 한 줄 정의

> 만든 회사나 프레임워크가 다른 에이전트끼리 일을 맡기고 결과를 돌려받도록 정한 공개 통신 약속

---

## 1. 비유로 이해하기

우리 반이 식물 관찰 일지를 썼는데, 옆 학교 과학 동아리에 "틀린 데가 없는지 봐 달라"고 부탁하고 싶다고 하자. 우리는 그 동아리가 안에서 어떻게 회의하고 누가 무엇을 하는지 모른다. 알 필요도 없다.

대신 몇 가지 약속이 있으면 된다. 옆 학교 게시판에는 **동아리 소개 카드**가 붙어 있다. 이름, 연락할 곳, "식물 일지 검토 가능"처럼 할 수 있는 일이 적혀 있다. 우리는 카드를 보고 **부탁 쪽지**를 보낸다. 동아리는 "접수했어요", "보는 중이에요", "사진이 더 필요해요", "다 됐어요" 하고 **진행 상황**을 알려 준다. 끝나면 말로 "괜찮던데요" 하고 마는 게 아니라 **고칠 곳을 적은 검토표**를 돌려준다. 우리는 그 검토표가 맞는지 한 번 더 보고 일지를 고친다.

{% include figure.html src="/assets/images/term-a2a/request-flow.svg" alt="왼쪽에 우리 팀의 의뢰 에이전트, 오른쪽에 다른 회사의 수행 에이전트가 있고 가운데 화살표 네 개가 오간다. ① 수행 쪽의 Agent Card(이름·주소·인증 방식·할 수 있는 일)를 읽고, ② task(할 일과 입력)를 보내고, ③ submitted에서 working을 거쳐 completed로 상태를 알려 받으며(중간에 input-required, 끝에 failed도 있다), ④ 파일이나 구조화 데이터인 artifact를 돌려받는다. ⑤ 의뢰 쪽은 결과물을 검증하고 다음 일을 정한다. 아래에는 속을 몰라도 약속한 형식만 맞추면 되며, 카드는 선언일 뿐이라 권한과 품질은 따로 확인한다는 설명이 있다" caption="그림 1. 카드를 읽고, task를 보내고, 상태를 받고, artifact를 돌려받는다" %}

그래서 실제로는, 소개 카드가 **Agent Card**, 부탁 쪽지가 **task**, 진행 알림이 **task 상태**, 검토표가 **artifact**다. 서로 다른 회사가 다른 도구로 만든 에이전트라도 이 네 가지 형식만 맞추면 일을 주고받을 수 있게 하자는 것이 A2A다.

## 2. 왜 필요한가

### 같은 집 안에서는 따로 약속이 없어도 된다

26회차 실습 C의 리드와 locator는 한 파이썬 프로그램이 띄운 한 세션 안에 같이 있었다. `agents={"locator": ...}` 한 줄로 이름을 올려 두면 리드는 그 이름만으로 locator를 부를 수 있었고, 주소나 주고받을 형식을 따로 약속할 일이 없었다. 같은 집 식구끼리는 "이거 좀 봐 줘" 한마디로 통하는 것과 같다.

문제는 상대가 **다른 집**일 때다. 소유자도, 만든 프레임워크도 다른 바깥 에이전트에게 "검토 좀 맡길게"라는 문장만 보내서는 아무 일도 일어나지 않는다.

### 바깥과 연결하려면 미리 정해야 할 네 가지

다른 시스템의 에이전트에게 일을 맡기려면 적어도 이런 질문에 답이 있어야 한다. A2A는 질문마다 정해진 형식을 하나씩 둔다.

- **누구에게, 어디로 보내나? 그 상대는 무슨 일을 받을 수 있나?** → Agent Card
- **무슨 일을 맡기나?** → task (할 일과 입력)
- **지금 어디까지 했나? 끝났나?** → task 상태 (`submitted`, `working`, `input-required`, `completed`, `failed` 등)
- **결과물은 무엇이고 어디 있나?** → artifact (파일이나 구조화된 데이터)

상태를 따로 두는 이유는 오래 걸리는 일이 많아서다. 한 번 묻고 한 번 답하면 끝나는 게 아니라, 중간에 "자료가 더 필요하다(`input-required`)"고 되묻기도 한다. artifact를 따로 두는 이유는 "끝났다"는 표시와 "무엇이 만들어졌나"를 나눠 보기 위해서다.

### Agent Card는 이렇게 생겼다

카드는 JSON 문서다. 아래는 이해를 돕기 위해 만든 가상의 짧은 예다. 주소는 실제로 연결되지 않는 자리표시자다.

```json
{
  "name": "recipe-check-agent",
  "description": "요리법 초안의 재료 분량과 알레르기 표시를 점검한다",
  "url": "https://agent.example.org/a2a",
  "skills": [
    {
      "id": "allergen-check",
      "name": "알레르기 표시 점검",
      "description": "재료 목록에서 알레르기 유발 재료 표시가 빠졌는지 본다"
    }
  ]
}
```

카드는 "이런 일을 할 수 있어요"라는 **자기소개**다. 옆 학교 동아리 카드에 "식물 일지 검토 가능"이라고 적혀 있어도, 정말 꼼꼼히 보는지, 우리 일지 말고 다른 서랍까지 열어 보지는 않는지는 카드로 알 수 없다. 그래서 맡기기 전에 무엇을 건네고 무엇을 돌려받는지, 어디서 사람이 한 번 확인할지를 우리 쪽에서 따로 정해 둬야 한다.

### 먼저 물을 질문: 바깥 에이전트가 정말 있나?

A2A를 쓸지 고민하는 일은 기술 목록이 아니라 상대를 보는 데서 시작한다. 지금 하는 일에 **주인이 다른 바깥 에이전트가 정말 끼어 있는지**부터 본다. 26회차 실습처럼 한 세션 안에서 locator 하나를 불러 쓰는 일이라면 카드도 상태 알림도 필요 없었다. 옆 학교 동아리처럼 서로 속사정을 모르는 상대와 일을 여러 번 주고받아야 할 때 비로소 이 약속이 쓸모를 낸다.

## 3. 어디서 만났나

**26회차** 노드 2의 "깊이 보기"에서 만났다. 멀티 에이전트의 소통 구조를 정리하던 흐름에서, 지금까지 본 구조와 실습의 에이전트는 모두 **하나의 실행 환경 안**에 있다는 점을 짚고, 소유자와 프레임워크가 다른 에이전트를 잇는 방법으로 A2A가 소개됐다. Google이 2025년 4월에 발표했고, 공식 문서에 따르면 Linux Foundation에 기증되어 그쪽 위원회가 유지한다는 설명도 함께 나왔다.

실습에서는 A2A나 Agent Card를 만들지 않았다. 실습의 오케스트레이션 실행(C)에서 리드가 부를 수 있었던 탐색 워커 `locator`는 같은 실행 환경 안의 서브에이전트였고, 모든 소통은 리드를 거쳤다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| A2A | {% include term.html name="MCP" %} | MCP는 AI 앱이 **도구나 데이터**에 붙는 연결 약속이다. A2A는 **에이전트와 에이전트**가 일을 맡기고 결과를 돌려받는 약속이다. 상대가 시키는 대로 움직이는 도구인지, 스스로 판단하며 일하는 다른 에이전트인지가 다르다 |
| A2A | {% include term.html name="서브에이전트" %} | 서브에이전트는 **같은 하네스 안에서** 리드가 불러 쓰고 결과를 리드에게 돌려준 뒤 끝나는 워커다. A2A는 소유자와 프레임워크가 **다른 바깥** 에이전트를 잇는 형식이다 |
| Agent Card | 실제 능력·권한 | 카드는 할 수 있다고 밝힌 **선언**이다. 정말 그 일을 잘하는지, 무엇까지 건드릴 수 있는지는 의뢰하는 쪽이 따로 확인해야 한다 |
| task 상태 `completed` | artifact | `completed`는 "끝났다"는 **표시**일 뿐이다. 무엇이 만들어졌는지는 artifact를 열어 봐야 안다 |

## 5. 많이들 오해하는 지점

**ㄱ. "A2A를 붙이면 에이전트 여러 개가 알아서 잘 협업한다"**

A2A가 정하는 것은 **주고받는 형식**이다. 누구에게 어떤 일을 나눠 줄지, 받은 결과를 믿어도 되는지는 여전히 의뢰하는 쪽이 정하고 확인해야 한다. 그림 1의 ⑤번 칸이 그 일이다. 형식이 맞는다고 일이 잘 나뉘는 것은 아니다.

**ㄴ. "A2A는 MCP의 다음 버전이다"**

둘은 잇는 대상이 다르다. MCP는 AI 앱과 도구·데이터 사이를, A2A는 에이전트와 에이전트 사이를 잇는다. 그래서 한쪽이 다른 쪽을 대신한다고 보기보다는, 맡는 자리가 다르다고 보는 편이 맞다.

**ㄷ. "멀티 에이전트를 만들려면 A2A부터 넣어야 한다"**

26회차 실습의 리드와 워커는 A2A 없이 같은 실행 환경 안에서 움직였다. 에이전트가 같은 집 안에 있으면 내부 호출로 충분하고, 오히려 그쪽이 단순하다. A2A는 **독립된 외부 에이전트가 실제로 있을 때** 꺼내는 약속이다.
