## 한 줄 정의

> 여러 단계의 일을 사람이 미리 순서대로 이어 두고, 정해 둔 순서와 조건대로만 실행되게 만든 흐름

---

## 1. 비유로 이해하기

종이접기 책을 펴면 그림마다 번호가 붙어 있다. ① 반으로 접는다, ② 모서리를 안쪽으로 접는다, ③ 뒤집는다. 접는 사람은 순서를 바꾸지 않는다. ③을 먼저 하면 학이 아니라 다른 모양이 나온다. 어제 접어도, 오늘 접어도, 친구가 접어도 같은 번호를 따라가니 같은 학이 나온다. 다 접은 학이 이상하게 생겼으면 몇 번 그림에서 틀렸는지 책을 펴 놓고 되짚을 수도 있다.

설명서에 없는 일은 일어나지 않는다. 종이가 찢어지면 어떻게 하라는 그림이 없으면, 접는 사람은 거기서 멈춘다.

{% include figure.html src="/assets/images/term-workflow/fixed-route.svg" alt="메일 요약 워크플로를 네 칸으로 그렸다. 트리거, Gmail(오늘 메일 가져오기), AI Agent(메일 요약하기), Google Sheets(표에 한 줄 추가)가 화살표로 이어진다. 칸과 화살표 순서는 사람이 정했고, 주황색 AI Agent 칸 안에서만 모델이 요약 문장을 만든다. 그다음 어디로 갈지는 여전히 화살표가 정한다" caption="그림 1. 순서는 화살표가, 요약 문장만 모델이 — 모델이 들어 있어도 워크플로다" %}

그래서 실제로는, 워크플로는 **컴퓨터가 따라가는 종이접기 설명서**다. "메일을 가져온다 → 요약한다 → 표에 적는다"처럼 할 일을 칸으로 나누고 화살표로 이어 두면, 컴퓨터는 그 화살표대로만 움직인다. n8n 같은 도구에서는 이 칸 하나를 **노드(그래프의 칸)**라고 부른다. 수업 자료의 단원을 부르는 "노드"와는 다른 말이다.

## 2. 왜 필요한가

### 매번 같은 길로 가니까 다시 볼 수 있다

워크플로는 실행할 때마다 같은 순서를 밟는다. 그래서 결과가 이상하면 "어느 칸에서 무엇이 들어오고 무엇이 나갔는가"를 칸별로 확인할 수 있다. n8n은 한 번 돌 때마다 칸마다 입력과 출력을 기록으로 남긴다.

갈림길도 미리 그려 둔다. 고객 문의를 받는 흐름이라면 이렇게 나눌 수 있다.

```
문의 받기 → 분류하기 ─┬─ "환불"이면  → 환불 담당에게 넘기기
                      └─ 그 밖이면   → 일반 답변 보내기
```

환불 문의가 엉뚱한 곳으로 갔다면, 기록에서 분류 칸이 무엇을 내놓았는지만 보면 된다. 길이 고정돼 있으니 의심할 곳이 좁다.

### 설계도가 글자로 남는다

화면에서 칸을 끌어다 이은 워크플로도 속은 글자 파일이다. n8n은 워크플로를 내보내거나 주고받을 때 {% include term.html name="JSON" %} 한 덩어리로 다룬다. 칸 목록(`nodes`)과 칸 사이 연결(`connections`)이 들어 있다. 두 칸짜리 흐름을 줄여 적으면 대략 이런 모양이다.

```json
{
  "name": "Wikipedia N8n 요약 가져오기",
  "nodes": [
    { "name": "Manual Trigger", "type": "n8n-nodes-base.manualTrigger" },
    { "name": "HTTP Request",   "type": "n8n-nodes-base.httpRequest" }
  ],
  "connections": {
    "Manual Trigger": { "main": [[ { "node": "HTTP Request" } ]] }
  }
}
```

글자로 남으니 사람이 읽고 검토할 수 있고, {% include term.html name="CLI" %}로 다른 프로그램이 대신 만들 수도 있다. 위 예는 설명용으로 줄인 것이고, 실제 파일에는 칸의 위치·버전 같은 값이 더 들어간다.

### 모델을 넣어도 길은 사람이 쥐고 있다

워크플로 한가운데에 AI 모델을 넣을 수 있다. 그림 1의 AI Agent 칸처럼 "이 메일을 세 줄로 줄여라"는 일만 모델에게 맡기는 식이다. 그래도 그 칸 **다음에 어디로 갈지**는 화살표가 정한다. 모델이 "표에 적지 말고 메일을 보내자"라고 마음대로 길을 바꿀 수 없다. 판단이 필요한 한 칸만 모델에게 주고, 나머지 순서는 사람이 쥐고 있는 것이다.

## 3. 어디서 만났나

**24회차**에서 "다음 행동을 누가 정하는가"라는 질문으로 일하는 방식을 셋으로 나누면서 정식으로 다뤘다. 사람이 하나씩 지시하는 방식, 미리 이어 둔 흐름이 순서를 정하는 워크플로, 모델이 다음 행동을 고르는 {% include term.html name="AI 에이전트" %}다. 실습 도구는 {% include term.html name="n8n" %}이었다.

[24회차 — 다음 행동은 누가 정하나]({{ site.baseurl }}/2026/10/15/who-picks-next-step/)

실습에서 만든 흐름은 둘이고, 만든 방법은 세 가지였다. 노드 3에서는 n8n 화면에서 Manual Trigger와 HTTP Request 두 칸을 직접 잇고 실행한 뒤 실행 기록을 열어 봤다. 노드 4에서는 같은 흐름을 Claude Code에게 맡겼다. Claude Code가 `wf.json`을 써서 칸과 연결을 먼저 보여 주고, 내가 확인했다고 답한 뒤에 n8n CLI로 워크플로를 만들었다. 그 워크플로는 화면에서 실행했다. 노드 5에서는 Gmail → AI Agent(Gemini) → Google Sheets로 이어지는, 메일을 요약해 표에 적는 워크플로를 만들었다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| 워크플로 | {% include term.html name="AI 에이전트" %} | 워크플로는 **사람이 그려 둔 화살표**가 다음 칸을 정한다. 에이전트는 앞 결과를 읽은 **모델이** 어떤 도구를 쓰고 어디로 갈지 고른다 |
| 워크플로 | 자동화 | 자동화는 반복하는 일을 도구에 맡기는 것 **전체**를 부르는 말이다. 워크플로는 그 방법 가운데 하나다 |
| 워크플로 | 실행(execution) | 워크플로는 **설계도**이고, 실행은 그 설계도대로 **한 번 돈 것** 한 건이다. 워크플로 하나에 실행 기록이 여러 건 쌓인다 |
| 워크플로 | 노드(그래프의 칸) | 노드는 **행동 하나**(메일 가져오기)다. 워크플로는 노드 여러 개를 화살표로 이은 **전체 흐름**이다 |

## 5. 많이들 오해하는 지점

**ㄱ. "AI 모델이 들어가면 에이전트다"**

모델이 들어 있어도 다음 칸을 화살표가 정하면 워크플로다. 노드 5의 메일 요약 흐름에서 모델은 요약 문장만 만들었고, 메일을 가져오고 표에 적는 순서는 그대로였다. 에이전트인지 아닌지는 "모델이 있느냐"가 아니라 "**다음 행동을 누가 고르느냐**"로 가른다. 한 도구 안에서도 칸마다 답이 다를 수 있다.

**ㄴ. "워크플로는 에이전트보다 덜 똑똑한 옛날 방식이다"**

더 낫고 못한 관계가 아니라 쓰임이 다르다. 길이 고정된 워크플로는 같은 입력에 같은 길로 가니 검토하고 다시 해 보기 쉽다. 에이전트는 예외가 많은 일에 유연하지만, 모델을 여러 번 부르니 비용이 늘고 앞 단계의 실수가 뒤로 이어질 수 있다. 규칙으로 적을 수 있는 일은 워크플로에 두는 편이 오히려 다루기 쉽다.

**ㄷ. "n8n에 그 서비스 칸이 있으면 그 일을 맡겨도 된다"**

Gmail 칸이 있다는 건 연결할 **수 있다**는 뜻일 뿐이다. 그 칸에 어떤 계정 권한을 주는지(읽기만인지, 보내기·지우기까지인지), 실패하면 무엇이 기록되는지, 사람이 어디서 결과를 다시 볼지를 정하지 않았다면 아직 맡길 준비가 안 된 것이다. 종이접기 책에 "종이가 찢어지면" 그림이 없으면 접는 사람이 멈추듯, 워크플로도 설계할 때 생각하지 못한 상황에서 알아서 좋은 쪽을 골라 주지 않는다.
