## 1. 비유로 이해하기

학교 정문에는 경비 아저씨가 있다. 우리 반 친구가 옆 학교 친구에게 쪽지를 보냈고, 답장이 정문으로 돌아왔다. 경비 아저씨는 답장을 바로 건네주지 않는다. 봉투에 **"○○학교 학생에게 줘도 됨"**이라는 옆 학교 도장이 찍혀 있는지 먼저 본다. 도장이 있으면 친구에게 건네고, 없으면 돌려보낸다.

여기서 중요한 건 두 가지다. 첫째, 도장을 찍는 사람은 **답장을 보낸 옆 학교**다. 우리 반 친구가 경비 아저씨에게 아무리 졸라도 도장이 생기지 않는다. 둘째, 경비 아저씨는 **학교 정문에만** 있다. 학교 밖 어른이 옆 학교에 직접 전화를 걸면, 이 검사는 아예 없다.

{% include figure.html src="/assets/images/term-cors/origin-check.svg" alt="왼쪽 파란 상자는 브라우저다. 그 안의 페이지는 https://YOUR_ID.github.io 라는 출처에서 열렸다. 오른쪽 노란 상자는 내 컴퓨터의 Ollama로, 주소는 http://localhost:11434 이고 출입 명단 OLLAMA_ORIGINS를 갖고 있다. 기본 명단에는 localhost 같은 내 주소만 있고, github.io 주소는 직접 더해야 들어간다. 페이지가 요청을 보내면 Ollama는 명단에 있는 출처에만 허락 표시를 붙여 답을 돌려주고, 없으면 403으로 거절한다. 아래 초록 상자는 표시가 있으면 브라우저가 답을 페이지에 넘긴다는 것, 빨간 상자는 표시가 없으면 브라우저가 막고 콘솔에 CORS 오류가 뜬다는 것이다. 맨 아래에는 터미널의 node와 curl은 브라우저가 아니라 이 검사를 거치지 않으며, 23회차 작업물은 이쪽으로 Ollama를 불렀다고 적었다" caption="그림 1. 막는 건 브라우저, 허락 명단을 정하는 건 받는 쪽" %}

그래서 실제로는, 경비 아저씨가 **브라우저**, 쪽지를 보낸 친구가 **웹 페이지의 코드**, 옆 학교가 **요청을 받는 서버**(23회차에서는 내 컴퓨터의 {% include term.html name="Ollama" %})다. 브라우저는 페이지가 자기와 다른 출처에 보낸 요청의 답을 받으면, 받는 쪽이 "이 출처는 허락" 표시를 붙였는지 확인한 뒤에야 페이지에 넘긴다. 그 허락을 정하는 방법을 통틀어 CORS라고 부른다. Ollama에서는 그 허락 명단이 `OLLAMA_ORIGINS`라는 설정이고, 명단에 없는 출처에서 온 요청에는 Ollama가 답 대신 403(거절)을 돌려준다. 어느 쪽이든 허락 표시가 없으니 브라우저는 페이지에 넘기지 않는다. 학교 밖 어른은 터미널의 `node`나 `curl`이다. 브라우저가 아니니 이 검사를 받지 않는다.

## 2. 왜 필요한가

### 출처란 무엇인가 — 세 가지가 모두 같아야 같은 출처

**출처(origin)**는 주소의 앞부분 세 가지, 즉 **방식(http/https) + 이름(호스트) + 번호(포트)**를 묶은 것이다. 셋 중 하나만 달라도 다른 출처다.

| 페이지가 열린 주소 | 요청하는 주소 | 같은 출처인가 |
| --- | --- | --- |
| `http://localhost:11434` | `http://localhost:11434/api/chat` | 같다 |
| `http://localhost:4000` | `http://localhost:11434/api/chat` | **다르다** — 포트 번호가 다름 |
| `https://YOUR_ID.github.io` | `http://localhost:11434/api/chat` | **다르다** — 셋 다 다름 |

같은 내 컴퓨터 안이어도 포트가 다르면 다른 출처다. 그래서 내 컴퓨터에서 띄운 화면이 같은 컴퓨터의 Ollama를 불러도 CORS 검사를 받는다. 다만 Ollama는 기본 명단에 `localhost` 같은 내 컴퓨터 주소를 넣어 두어서, 이런 경우는 따로 설정하지 않아도 대개 통과한다.

### 왜 막는가 — 내 브라우저를 남이 빌려 쓰지 못하게

브라우저는 웹사이트 수십 곳을 한 창에서 연다. 그중에는 처음 들어가 본 낯선 사이트도 있다. 만약 어떤 페이지든 다른 출처에 마음대로 요청하고 답을 읽을 수 있다면, 낯선 사이트가 내 브라우저를 빌려 내가 로그인해 둔 사이트나 **내 컴퓨터 안의 `localhost:11434`**에 요청하고 그 답을 가져갈 수 있다.

그래서 브라우저는 기본으로 "다른 출처의 답은 페이지에 안 넘긴다"는 원칙(동일 출처 정책)을 지킨다. CORS는 이 원칙에 **받는 쪽이 정한 예외**를 만드는 규칙이다. 받는 쪽이 답에 `Access-Control-Allow-Origin` 같은 허락 표시를 붙이면, 브라우저가 그 출처의 페이지에는 답을 넘긴다. 요청 종류에 따라서는 브라우저가 본 요청을 보내기 전에 "이런 요청 보내도 돼?" 하고 먼저 물어보는 사전 확인을 하기도 한다.

### 23회차 챗봇에서 왜 문제가 되나

23회차 노드의 챗봇은 GitHub Pages에 올리는 정적 페이지다. 페이지는 인터넷에서 받아 오지만, **답을 만드는 Ollama는 페이지를 연 사람의 컴퓨터**에서 돈다. 브라우저가 `https://YOUR_ID.github.io`에서 연 페이지로 `http://localhost:11434`를 부르는 것이다. 출처가 다르니 CORS 검사를 받고, Ollama의 기본 명단에는 `localhost` 같은 내 컴퓨터 주소만 있어서 github.io 주소는 허락되지 않는다.

그래서 받는 쪽, 즉 **Ollama에게** 이 출처를 허락하라고 알려 줘야 한다. 노드가 운영체제별로 적어 둔 명령은 이렇다.

```text
# macOS
launchctl setenv OLLAMA_ORIGINS "https://YOUR_ID.github.io"

# Windows
setx OLLAMA_ORIGINS "https://YOUR_ID.github.io"

# systemd 환경 (리눅스)
systemctl set-environment OLLAMA_ORIGINS="https://YOUR_ID.github.io"
```

`OLLAMA_ORIGINS`는 {% include term.html name="PATH" %}처럼 **환경 변수**다. Ollama는 켜질 때 이 값을 읽으므로, 설정한 뒤에는 Ollama를 껐다 다시 켜야 한다. 그다음 실제 배포 주소에서 연결 상태 확인과 답변 스트리밍이 둘 다 되는지 본다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| CORS | 동일 출처 정책 | 동일 출처 정책은 "다른 출처의 답은 넘기지 않는다"는 브라우저의 **기본 원칙**이다. CORS는 받는 쪽이 허락 표시로 **예외를 여는 규칙**이다 |
| `OLLAMA_ORIGINS` | `OLLAMA_HOST` | `OLLAMA_ORIGINS`는 **어느 출처의 웹 페이지**에서 온 요청을 허락할지 정한다. `OLLAMA_HOST`는 Ollama가 **어느 주소·포트에서 요청을 기다릴지** 정한다. 다른 컴퓨터에서 접속하게 하려는 것이면 이쪽이다 |
| CORS 오류 | Ollama가 꺼져 있음 | 페이지 코드에는 둘 다 "요청 실패"로 비슷하게 보인다. 꺼져 있으면 요청이 닿을 곳이 없고, CORS 오류는 요청이 Ollama에 닿았지만 허락 표시가 붙은 답이 오지 않아(명단 밖 출처라 403) 브라우저가 페이지에 넘기지 않은 것이다. 브라우저 개발자 도구의 콘솔 문구로 구분한다 |
| CORS | {% include term.html name="API" %} 키 같은 인증 | 인증은 서버가 "**누가** 보냈나"를 확인한다. CORS는 브라우저가 "**어느 페이지**에서 보냈나"를 기준으로 답을 넘길지 정한다. CORS를 허락했다고 비밀번호가 생기는 건 아니다 |

## 5. 많이들 오해하는 지점

**ㄱ. "CORS 오류는 페이지 코드를 고치면 해결된다"**

허락 명단을 가진 건 **받는 쪽**이다. 터미널에서 `curl`로 보내면(출처를 밝히는 `Origin` 정보를 따로 넣지 않는 한) Ollama는 평소처럼 답한다. 그래서 "curl로는 되는데 브라우저에서만 안 된다"면 CORS를 먼저 의심한다. 이때 페이지 코드를 아무리 고쳐도 소용없고, Ollama의 `OLLAMA_ORIGINS`에 그 페이지의 출처를 더해야 한다. `fetch`에 `mode: "no-cors"`를 주는 방법도 해결이 아니다. 오류는 사라지지만 페이지가 답의 내용을 읽을 수 없게 된다.

**ㄴ. "GitHub Pages에 올리면 Ollama도 인터넷에서 같이 돌아간다"**

Pages에 올라가는 건 화면 파일(HTML·자바스크립트)뿐이다. Ollama는 여전히 **페이지를 연 사람 각자의 컴퓨터**에서 돈다. 그래서 친구가 내 배포 주소를 열면, 친구의 브라우저는 친구 컴퓨터의 `localhost:11434`를 부른다. 친구도 Ollama와 모델을 설치하고, 자기 Ollama에 `OLLAMA_ORIGINS`를 설정해야 쓸 수 있다.

**ㄷ. "귀찮으니 `OLLAMA_ORIGINS`를 `*`(전부 허락)로 두면 된다"**

그러면 내가 들어간 **아무 웹사이트나** 내 브라우저를 통해 내 컴퓨터의 Ollama를 부를 수 있게 된다. 2절에서 본, 브라우저가 막으려던 바로 그 일이다. 쓸 페이지의 출처 하나(`https://YOUR_ID.github.io`)만 정확히 적는다. 출처는 방식·이름·포트까지 맞아야 하므로, 끝에 경로(`/moducon-…`)를 붙이지 않는다.
