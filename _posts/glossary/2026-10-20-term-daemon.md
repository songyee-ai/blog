## 한 줄 정의

> 터미널 창을 열어 두지 않아도 뒤에서 계속 돌며 일을 기다리는 프로그램. 켜고 끄는 일은 운영체제의 서비스 관리자에게 맡긴다

---

## 1. 비유로 이해하기

**냉장고**를 생각해 보자. 문을 열 때만 켜지는 게 아니다. 아무도 부엌에 없는 밤에도 조용히 돌면서 안을 차갑게 유지한다. 누가 계속 지켜보거나 버튼을 누르고 있을 필요가 없다. 그게 냉장고가 일하는 방식이다.

그런데 이 냉장고가 본채가 아니라 **마당 건너 별채의 콘센트**에 꽂혀 있다고 해 보자. 본채 전기를 아무리 켜도, 별채 차단기가 올라가기 전까지 냉장고는 돌지 않는다. "전기 켜면 냉장고도 돌지" 하고 생각했다면 별채를 빼먹은 것이다.

{% include figure.html src="/assets/images/term-daemon/daemon-boot-chain.svg" alt="왼쪽부터 네 칸이 화살표로 이어진다. ① 윈도우를 켜고 로그인한다, ② WSL이 시작돼 Ubuntu가 깨어난다, ③ systemd가 등록된 사용자 서비스를 켠다, ④ Gateway가 18789번 문에서 기다린다. ① 아래에는 여기서 멈추면 Gateway는 아직 없다고, ②~④ 아래에는 WSL이 시작돼야 이어지는 칸이며 서비스 파일이 ~/.config/systemd/user/openclaw-gateway.service라고 적었다. 그 아래 상자 두 개에는 에이전트 답변 '컴퓨터를 켜면 저절로 실행됩니다'가 정확하지 않다는 것과, ④가 nvm으로 설치한 Node에 기대고 있어 그 Node를 지우거나 올리면 서비스가 깨질 수 있다는 gateway status의 지적을 적었다" caption="그림 1. 데몬은 혼자 돌지만, 누가 켜 주는지까지 따라가 봐야 한다" %}

그래서 실제로는, 냉장고가 **데몬**이다. 사람이 보지 않아도 뒤에서 계속 돌며 일을 기다린다. 차단기 역할을 하는 것이 **서비스 관리자**(Linux의 systemd 같은 것)이고, 27회차 실습에서는 그 서비스 관리자가 윈도우가 아니라 **WSL 안**에 있었다. 별채가 바로 {% include term.html name="WSL" %}이다.

## 2. 왜 필요한가

### 창을 닫아도 살아 있어야 하는 프로그램이 있다

터미널에서 프로그램을 그냥 실행하면 그 창에 묶인다. 창을 닫거나 `Ctrl-C`를 누르면 같이 끝난다. 계산 한 번 하고 끝나는 프로그램은 그래도 된다.

하지만 OpenClaw의 {% include term.html name="게이트웨이" %}는 휴대폰에서 언제 올지 모르는 메시지를 **계속 기다려야** 한다. 내가 터미널을 열어 둔 동안에만 받는다면 쓸모가 반으로 준다. 그래서 수업 자료는 온보딩 때 데몬 등록까지 함께 하는 옵션을 안내한다.

```bash
openclaw onboard --install-daemon
```

`--install-daemon`을 붙이면 첫 설정(온보딩)과 함께 Gateway를 서비스로 등록한다. 실습 환경(WSL2 Ubuntu)에서는 온보딩이 끝났을 때 이렇게 돼 있었다.

```text
openclaw-gateway.service   systemd 사용자 서비스, active running
서비스 파일   ~/.config/systemd/user/openclaw-gateway.service
```

수업 자료에 따르면 macOS에서는 같은 일을 LaunchAgent가 맡는다. 운영체제마다 "뒤에서 켜 두는 프로그램을 관리하는 담당자"가 다를 뿐, 하는 일은 같다.

### 켜는 것도, 끄는 것도 따로 한다

데몬은 창과 상관없이 돌기 때문에, 끌 때도 명령으로 끈다.

| 하고 싶은 일 | 명령 |
| --- | --- |
| 지금 도는지 보기 | `openclaw gateway status` |
| 멈추기 | `openclaw gateway stop` |
| 서비스 등록 지우기 | `openclaw gateway uninstall` |

옛 자료에는 `openclaw daemon stop`처럼 `daemon`이라는 이름으로 나온다. `gateway` 서비스 명령의 예전 이름(별칭)이라 같은 일을 한다.

11월 4일에 확인했을 때도 Gateway 서비스는 active였다. 데몬은 내가 끄라고 하기 전까지 계속 돈다. 그래서 다 쓴 데몬은 **멈추고, 등록까지 지워야** 정리가 끝난다.

### 이름 끝의 d, 그리고 윈도우의 "서비스"

Linux에서는 데몬 프로그램 이름 끝에 `d`를 붙이는 관습이 있다. 원격 접속을 받는 `sshd`, 서비스 관리자 자신인 `systemd`가 그 예다. 윈도우에서는 같은 종류를 보통 **서비스**라고 부르고, 작업 관리자의 "서비스" 탭에서 볼 수 있다. 부르는 이름은 달라도 "창 없이 뒤에서 도는 프로그램"이라는 뜻은 같다.

### 데몬이 기대고 있는 것까지 봐야 한다

데몬은 혼자 도는 것처럼 보이지만, 실행에 필요한 것들에 기대고 있다. 실습에서 `openclaw gateway status`는 서비스 설정에 대해 지적 하나를 덧붙였다. Gateway 서비스가 nvm으로 설치한 Node를 쓰고 있어서, 그 Node를 지우거나 올리면 서비스가 깨질 수 있다는 것이다. 따로 깔린 시스템 Node(24.16 이상)도 없다고 했다. 오늘 실습에는 영향이 없어 그대로 뒀다.

nvm은 Node를 여러 버전 설치해 두고 골라 쓰게 해 주는 도구다. 내 터미널에서는 nvm이 "지금은 24번을 써" 하고 길을 잡아 주지만, 뒤에서 혼자 도는 서비스는 그 안내를 매번 받지 못한다. 서비스가 쓰던 버전을 지우면 실행할 Node를 못 찾게 된다({% include term.html name="PATH" %}와 비슷한 문제다). 실습 기록의 정리 표도 Gateway 데몬이 맨 위, Node 24가 맨 아래 순서로 적혀 있다.

## 3. 어디서 만났나

**27회차** OpenClaw 설치에서 만났다. 수업 자료는 데몬을 "터미널 창을 열어 두지 않아도 백그라운드에서 실행되는 관리 서비스"로 소개하며, 온보딩과 데몬 설치를 함께 하는 `openclaw onboard --install-daemon`을 안내했다. 실습에서는 온보딩이 끝났을 때 `openclaw-gateway.service`가 active running이었고, `openclaw gateway status`로 127.0.0.1:18789에서 기다리는 것을 확인했다.

세션 기록을 읽는 실습(노드 3)에서는 에이전트의 답변 하나를 실제 구성과 대조해 봤다. 아래 '많이들 오해하는 지점'의 ㄱ이 그 이야기다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| 데몬 | 그냥 실행한 프로그램 | 터미널에서 바로 실행한 프로그램은 그 **창에 묶여** 창을 닫으면 같이 끝난다. 데몬은 서비스 관리자에게 맡겨져 **창과 상관없이** 돈다 |
| 데몬 | 서비스 (윈도우) | 거의 같은 뜻이다. 유닉스·Linux 쪽에서 데몬이라 부르는 것을 윈도우에서는 서비스라고 부른다. systemd도 등록 단위를 "서비스"라고 부른다 |
| 데몬 | cron (예약 작업) | 데몬은 **계속 깨어 있으며** 일이 오기를 기다린다. 예약 작업은 정해진 시각에 **잠깐 깨어 일하고 끝난다**. 다만 그 시간표를 지켜보는 쪽은 계속 켜져 있어야 해서, 예약 기능 자체는 데몬이 맡는 경우가 많다 |
| 데몬 | Gateway | Gateway는 데몬으로 띄운 **프로그램 하나**다. 데몬은 "어떻게 띄웠나"를 말하는 방식이고, Gateway는 "무엇을 하는 프로그램인가"를 말하는 이름이다. Gateway를 터미널에서 직접 띄우면 데몬이 아니게 된다 |

## 5. 많이들 오해하는 지점

**ㄱ. "서비스로 등록했으니 컴퓨터를 켜면 저절로 돈다"**

노드 3 실습에서 에이전트가 "컴퓨터를 켜면 저절로 실행됩니다"라고 답했다. 기록에 적어 둔 결론은 **정확하지 않다**는 것이다. 이 서비스는 윈도우가 아니라 **WSL 안의 systemd**에 등록돼 있다. 윈도우를 켜도 WSL이 시작되기 전에는 Gateway가 돌지 않는다. 그림 1의 ①에서 멈춘 상태다.

"자동으로 켜진다"는 말을 들으면 **누가 켜 주는지**를 거슬러 올라가 본다. 서비스 관리자가 어디에 있는지, 그 서비스 관리자는 언제 깨어나는지까지 따라가야 답이 나온다. 그리고 에이전트의 답변 문장은 근거가 아니다. 근거는 서비스가 어디에 등록돼 있는지 같은 실제 구성이다.

**ㄴ. "화면에 안 보이면 꺼진 것이다"**

데몬은 원래 창이 없다. 아무 창도 안 떠 있어도 뒤에서 돌고 있을 수 있다. 11월 4일에 확인했을 때도 Gateway 서비스는 active였고, 예약 목록에는 기본 작업 두 개(매일 03시 Memory Dreaming, 30분마다 Heartbeat)가 있었다. 켜져 있는지는 눈이 아니라 `openclaw gateway status` 같은 상태 명령으로 확인한다.

**ㄷ. "Node만 지우면 OpenClaw 흔적도 사라진다"**

거꾸로다. 데몬을 그대로 둔 채 Node부터 지우면, 등록된 서비스는 남아 있는데 실행할 Node가 없는 상태가 된다. 정리는 **위에서부터** 한다. 실습 기록의 정리 순서도 그렇게 잡았다.

```bash
openclaw gateway stop        # ① 데몬 멈추기
openclaw gateway uninstall   # ② 서비스 등록 지우기
npm uninstall -g openclaw    # ③ 프로그램 지우기
rm -rf ~/.openclaw           # ④ 설정·기록 지우기
nvm alias default 22 && nvm uninstall 24   # ⑤ 마지막에 Node 24
```
