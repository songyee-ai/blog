## 한 줄 정의

> 주 에이전트가 일 한 덩어리를 떼어 맡기려고 부르는 보조 에이전트로, 자기 컨텍스트에서 일하고 결과만 돌려준 뒤 끝난다

---

## 1. 비유로 이해하기

엄마가 저녁을 만들다가 두부가 없다는 걸 알았다. 냄비를 두고 갈 수 없어서 아이에게 쪽지를 준다. "가게 가서 두부 한 모. 이 돈만 쓸 것." 아이는 가게에서 과자 진열대도 지나고, 두부가 어디 있는지 점원에게 묻기도 한다. 하지만 집에 와서 엄마에게 건네는 것은 두부와 거스름돈뿐이다. 엄마는 가게 안에서 있었던 일을 하나하나 듣지 않고 요리를 이어 간다.

심부름 쪽지가 분명할수록 심부름은 잘 된다. 쪽지에 "이 돈만"이라고 적은 것처럼 할 수 있는 일의 범위도 미리 정한다. 그리고 엄마가 "두부쯤은 내가 금방 다녀오지" 하고 직접 가 버리면, 아이에게 심부름을 맡길 준비를 해 둔 것은 아무 일도 하지 않은 셈이 된다.

그래서 실제로는, 서브에이전트는 **주 에이전트(리드)가 부를 수 있게 등록해 둔 또 하나의 에이전트**다. 부르면 자기 컨텍스트에서 따로 일하고, 마지막 결과만 리드에게 돌려준 뒤 끝난다. Claude Code와 Claude Agent SDK에서 쓰는 이름이다.

## 2. 왜 필요한가

### 리드의 컨텍스트를 깨끗하게 지킨다

버그 원인을 찾으려면 파일을 여러 개 열고 검색을 여러 번 한다. 그 출력이 모두 리드의 컨텍스트에 쌓이면 정작 "무엇을 고치려 했는지"가 뒤로 밀린다. 서브에이전트에게 탐색을 맡기면, 검색 결과와 읽은 파일은 서브에이전트 쪽에만 쌓이고 리드에게는 "파일 경로 · 함수 이름 · 한 문단 진단" 같은 보고서만 돌아온다. 심부름 간 아이의 가게 이야기가 엄마의 요리에 끼어들지 않는 것과 같다.

### 역할·도구·모델을 미리 적어 둔다

서브에이전트는 "누구에게 무엇을 맡길 수 있는지"를 미리 적어 둔 정의로 만든다. 내 실험의 C는 Agent SDK에서 파이썬으로 이렇게 등록했다(설명 문장은 줄였다).

```python
locator = AgentDefinition(
    description="Read-only locator: finds the likely cause of a bug ...",
    prompt=SYS_B_LOCATE,                 # 탐색 담당의 지시문
    tools=["Read", "Grep", "Glob"],      # 쓸 수 있는 도구
)
ClaudeAgentOptions(..., agents={"locator": locator})
```

터미널에서 쓰는 Claude Code에서는 이 등록이 엄마의 심부름 쪽지처럼 마크다운 파일 한 장이 된다. 쪽지에서 가장 중요한 줄은 "이런 일이 생기면 이 아이를 보내라"에 해당하는 `description`이다. 리드가 지금 받은 요청을 이 줄과 비교해 보고 맡길지 말지를 스스로 고르기 때문이다. 그래서 파일 맨 위 YAML 머리에는 이름표인 `name`과 이 `description`을 빼먹지 않고 적는다. "이 돈만 쓸 것" 같은 단서는 골라 붙인다. 들고 갈 도구는 `tools`, 어떤 모델이 갈지는 `model`, 몇 턴 안에 돌아올지는 `maxTurns`에 적는다. 머리 밑에 이어 쓰는 본문은 아이에게 건네는 당부로, 서브에이전트가 받는 시스템 프롬프트가 된다. 쪽지는 그 프로젝트에서만 쓰려면 `.claude/agents/` 폴더에, 내 모든 프로젝트에서 쓰려면 `~/.claude/agents/`에 넣어 둔다.

### 도구 제한은 "자동 승인"과 다르다

내 실험의 B와 C는 둘 다 "탐색 담당은 읽기만 한다"를 원했지만 방법이 달랐다.

- B는 locator를 코드가 따로 연 세션으로 돌리면서 `allowed_tools=["Read", "Grep", "Glob"]`를 줬다. 이것은 **묻지 않고 자동으로 허락할 도구 목록**일 뿐, 다른 도구를 막지 않는다. 실제로 B의 locator는 세 문제 중 두 문제에서 목록 밖의 `Bash`를 썼다(읽기·검색·재현 명령뿐이었고 파일은 고치지 않았다).
- C의 서브에이전트 정의 `AgentDefinition(tools=[...])`는 **그 도구만 쓸 수 있게** 제한한다. 다만 C에서는 locator가 한 번도 불리지 않아서, 이 제한이 돌아가는 모습은 내 기록에 없다.

### 정의해 둔다고 불리는 것은 아니다

C의 리드는 세 문제 모두 locator를 부르지 않았다. 리드가 쓴 도구는 `Bash`, `Read`, `Edit`뿐이었다. 등록이 안 돼서가 아니다. 트랜스크립트의 사용 가능한 에이전트 목록에는 `locator`가 올라 있었다. 첫 편집 전까지 쓴 도구 호출이 문제마다 1번, 2번, 4번이라, 맡길 이유가 생기기 전에 원인 위치가 잡혔다. Claude Code에서 반드시 맡기고 싶다면 프롬프트에 `@agent-locator`처럼 이름을 적어 부른다고 수업 노드 9에서 배웠다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| 서브에이전트 | 에이전트 팀의 팀원 (Claude Code 실험 기능) | 서브에이전트는 **리드가 맡기고**, 결과를 **리드에게만** 돌려주고 끝난다. 팀원은 각자 독립 세션으로, 공유 작업 목록에서 일을 **스스로 가져가고** 팀원끼리 **직접 메시지**를 보낸다 |
| 서브에이전트 | 도구 (`Read`, `Grep` 같은 것) | 도구는 정해진 동작을 **한 번** 한다. 서브에이전트는 스스로 도구를 **여러 번 골라 쓰는** 에이전트다 |
| 서브에이전트 | 내 실험 B의 locator 세션 | B의 locator는 파이썬 코드가 **따로 연 세션**이라, 부를지 말지를 리드가 정하지 않았다. 코드가 순서대로 반드시 실행했다 |
| 서브에이전트 | {% include term.html name="도구 정의서" %} | 도구 정의서는 도구 하나의 이름·설명·입력을 적은 것이다. 서브에이전트 정의는 **에이전트 하나**의 역할·지시문·쓸 도구·모델을 적은 것이다. `description`으로 "언제 쓸지"를 알린다는 점은 닮았다 |

## 5. 많이들 오해하는 지점

**ㄱ. "서브에이전트를 등록하면 리드가 알아서 나눠 쓴다"**

등록은 "부를 수 있다"는 뜻이지 "부른다"는 뜻이 아니다. 내 실험 C의 리드는 locator가 목록에 있었는데도 세 번 모두 직접 처리했다. 그래서 C는 사실상 턴 예산이 큰 에이전트 하나처럼 움직였고, 비용은 A의 1.24배였다. 서브에이전트를 썼는지는 설정 파일이 아니라 실행 기록에서 확인해야 한다.

**ㄴ. "허용 목록에 읽기 도구만 적으면 읽기 전용이 된다"**

B의 `allowed_tools`는 자동 승인 목록이라 다른 도구를 막지 않았다. 내 기록에서 locator는 목록 밖의 `Bash`를 두 문제에서 썼다. 이번에 파일을 고치지 않은 것은 도구 제한 덕분이 아니라 지시문을 따른 결과다. 도구를 정말 막으려면 서브에이전트 정의의 `tools`처럼 실제로 제한하는 설정을 써야 한다.

**ㄷ. "서브에이전트끼리 대화하면서 협업한다"**

서브에이전트는 결과를 리드에게 돌려주고 끝난다. 수업에서 다룬 Agent SDK 버전의 공개 인터페이스에는 서브에이전트끼리 직접 주고받는 방법이 없어서, 실습의 모든 연락은 리드를 거쳤다. 팀원끼리 직접 메시지를 보내는 것은 Claude Code의 에이전트 팀이라는 별도의 실험 기능이다.
