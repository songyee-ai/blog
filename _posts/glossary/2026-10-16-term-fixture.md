## 한 줄 정의

> 시험할 때마다 같은 조건에서 출발하도록 미리 똑같이 준비해 두고 다시 쓰는 고정 입력 자료

---

## 1. 비유로 이해하기

형이 퍼즐을 빨리 맞추는 새 방법을 찾았다고 한다. 테두리 조각부터 골라 놓고 시작하는 방법이다. 정말 빨라졌는지 보려면 어제와 오늘의 시간을 재서 비교하면 된다. 그런데 어제는 100조각짜리 동물 퍼즐이었고 오늘은 300조각짜리 바다 퍼즐이라면, 시간이 달라진 까닭이 방법 때문인지 퍼즐 때문인지 알 수 없다.

그래서 같은 100조각 퍼즐을 쓴다. 다 맞춘 퍼즐은 다시 상자에 쏟아 흩어 놓고, 옛 방법으로 한 번, 새 방법으로 한 번 잰다. 퍼즐이 똑같으니 시간 차이는 방법에서 왔다고 말할 수 있다.

{% include figure.html src="/assets/images/term-fixture/same-start.svg" alt="왼쪽 make_fixture.sh 상자에는 작성자 이름 고정, 커밋 날짜 고정, 같은 파일과 같은 순서, 충돌 2곳, 실패 테스트 3곳이 적혀 있다. 화살표가 오른쪽 여섯 폴더로 이어진다. 훅 끔 off-1~3과 훅 켬 on-1~3 모두 첫 커밋 해시가 05f3a78이고 브랜치 9개, 커밋 18개다" caption="그림 1. 스크립트 하나가 시도마다 같은 저장소를 새로 만든다 — 여섯 폴더의 첫 커밋 해시가 모두 같다" %}

그래서 실제로는, 픽스처는 **프로그램이나 AI 도구를 시험할 때 쓰는 같은 퍼즐 상자**다. 시험에 넣을 파일·폴더·저장소를 미리 정해 두고, 시험할 때마다 처음 상태로 되돌려 다시 쓴다. 영어 그대로 fixture라고도 많이 쓴다.

## 2. 왜 필요한가

### 차이가 어디서 왔는지 말할 수 있다

나는 이번 과제에서 Claude Code의 Stop {% include term.html name="훅" %}을 켠 조건과 끈 조건을 비교했다. 같은 요청 10개를 보냈을 때 최종 답이 영어로 나오는 횟수가 줄어드는지 보는 실험이다. 이때 조건마다 작업할 저장소가 다르면, 결과가 달라져도 훅 때문인지 저장소 때문인지 가를 수 없다. 그래서 작업 입력을 픽스처로 고정했다. 조건 사이에 다른 것은 훅 하나만 남긴다는 {% include term.html name="통제 실험" %}의 생각과 같다.

### 매번 새로 만들어도 똑같게

내 픽스처는 파일 묶음이 아니라 **깃 저장소를 만드는 스크립트** `make_fixture.sh`다. 작은 파이썬 가격 계산 모듈에 브랜치 9개, 커밋 18개를 쌓고, 일부러 충돌 2곳과 실패하는 테스트 3곳을 넣었다. 핵심은 작성자와 날짜를 고정하는 두 줄이다.

```bash
export GIT_AUTHOR_NAME="dev" GIT_AUTHOR_EMAIL="dev@example.com"
...
local d="2026-09-01T09:$(printf %02d "$N"):00+09:00"   # N번째 커밋은 9시 N분
GIT_AUTHOR_DATE="$d" GIT_COMMITTER_DATE="$d" git commit -q -m "$1"
```

{% include term.html name="Git" %}의 커밋 해시는 파일 내용뿐 아니라 작성자 이름·메일·시각까지 넣어서 계산한다. 그래서 이 값들을 고정하면 몇 번을 다시 만들어도 해시까지 같은 저장소가 나온다. 실제로 본 실험 여섯 번의 기록을 열어 보면 첫 커밋이 모두 `05f3a78 init: price and discount`였다.

### 원본은 건드리지 않고 복사해서 쓴다

요청 가운데에는 브랜치를 합치고 테스트를 고치는 일이 들어 있다. 작업이 끝나면 저장소가 바뀐다. 그래서 시도마다 새 폴더(`~/harness-runs/<시도>/`)에 스크립트로 픽스처를 다시 만들고 그 안에서 작업했다. 다 맞춘 퍼즐을 상자에 다시 쏟는 일에 해당한다. 픽스처 원본(`fixture/` 폴더)은 손대지 않는다.

### 작게 시작해도 된다

픽스처가 꼭 클 필요는 없다. 같은 날 노드 2 관찰 실습에서는 `notes.txt` 한 파일이 픽스처였다. 파이썬에서 `import this`를 실행하면 나오는 글을 붙여 넣은 21줄, 857바이트짜리 파일이다. 내용을 이미 아는 작은 파일이면 도구가 무엇을 읽고 어떻게 답했는지 확인하기 쉽다. 비밀값이나 개인 자료처럼 밖으로 나가면 곤란한 것은 넣지 않는다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| 픽스처 | {% include term.html name="시드" %} | 시드는 무작위로 뽑는 **순서**를 고정하는 숫자 하나다. 픽스처는 시험에 넣는 **자료 자체**(파일·저장소)를 고정한다 |
| 픽스처 | 테스트 코드 | 테스트 코드는 "결과가 맞는지" **확인하는** 쪽이다. 픽스처는 그 테스트나 도구가 **받아서 쓰는** 재료다 |
| 픽스처 | 실제 작업 저장소 | 실제 저장소는 날마다 바뀌고 지우면 곤란한 것이 있다. 픽스처는 언제든 버리고 **처음 상태로 다시 만들 수 있게** 만든 것이다 |
| 픽스처 | {% include term.html name="통제 실험" %}의 고정 조건 | 고정 조건은 모델·버전·규칙·도구 허용 범위처럼 **같게 두는 것 전부**다. 픽스처는 그중 **입력 자료** 한 칸이다 |

## 5. 많이들 오해하는 지점

**ㄱ. "픽스처만 같으면 공정한 비교다"**

픽스처는 고정할 것 가운데 하나일 뿐이다. 내 실험에서는 Claude Code 버전, 모델, 한국어 규칙 파일, 요청 10개와 순서, 도구 허용 범위까지 같이 고정했다. 그래도 한 번은 비교가 무너졌다. 요청을 한 줄씩 읽는 실행 스크립트의 반복문 안에서 `claude -p`가 표준 입력을 함께 읽어, 첫 요청에 나머지 요청 9개가 붙어 들어갔다. 픽스처는 같았지만 실제로 들어간 요청이 달라진 것이다. 이 시도는 무효로 돌리고, `claude`에 빈 입력(`< /dev/null`)을 주도록 고친 뒤 다시 돌렸다.

**ㄴ. "픽스처는 아무 장난감 자료나 쓰면 된다"**

픽스처는 재현하고 싶은 상황을 담고 있어야 한다. 처음 만든 픽스처는 브랜치 5개, 커밋 8개였고 요청도 4개뿐이었다. 시범으로 돌려 보니 도구 호출 28번, 2분 24초 만에 끝났고 영어 답은 0건이었다. 실제로 영어가 샌 세션은 도구 호출이 수백 번 쌓인 뒤였으니 이 길이로는 불편이 다시 나타나지 않았다. 그래서 브랜치 9개, 커밋 18개, 요청 10개로 키웠다. 그런데 키운 뒤에도 훅을 끈 기준선에서 영어 답이 0건이 나와 결과는 판정 불가였다. 픽스처의 크기와 모양이 실험에서 무엇을 볼 수 있을지를 정한다.

**ㄷ. "한 번 만든 픽스처는 조금씩 고쳐 가며 써도 된다"**

시도 중간에 픽스처를 바꾸면 바꾸기 전 시도와 바꾼 뒤 시도는 다른 퍼즐로 잰 기록이 된다. 나도 픽스처를 키운 것은 시범 실행 뒤, 본 실험 전이었다. 본 실험 여섯 번은 모두 같은 스크립트로 만든 같은 저장소에서 돌았다. 고쳐야 한다면 고친 뒤의 시도끼리만 비교한다.
