## 한 줄 정의

> OpenClaw에서 늘 켜져 있으면서 여러 채널로 들어온 메시지를 받아, 어느 세션·어느 에이전트로 보낼지 정해 넘기는 중심 프로그램

---

## 1. 비유로 이해하기

아파트 **경비실**을 떠올려 보자. 택배는 여러 택배 회사에서 온다. 기사님들은 집집마다 올라가지 않고 경비실에 맡긴다. 경비 아저씨는 상자에 적힌 동·호수를 보고 "이건 101동 302호" 하고 제자리에 놓는다. 302호 사람은 어느 택배사로 왔든 같은 경비실에서 받아 간다.

그리고 이 경비실은 **단지 안쪽으로만 창구가 나 있다.** 단지 밖 큰길에서는 창구가 보이지 않으니, 모르는 사람이 길에서 바로 말을 걸 수 없다.

{% include figure.html src="/assets/images/term-gateway/gateway-loopback.svg" alt="점선 테두리로 '이 컴퓨터 안(WSL)'을 그렸다. 안쪽 왼편의 터미널 채팅 화면과 WebChat이 화살표로 가운데 Gateway(127.0.0.1:18789)에 닿는다. Gateway 상자에는 채널 연결을 붙잡고, 받을 세션·에이전트를 고르고, 에이전트 런타임에 넘긴다는 세 줄이 있고, 아래 에이전트 런타임(모델 호출과 도구 실행)으로 화살표가 이어진다. 테두리 바깥 오른쪽 위의 Telegram은 양방향 화살표로 Gateway와 이어져 있고, 그 아래 다른 기기의 브라우저는 점선이 테두리에서 X로 막혀 기본값에선 18789번 문으로 들어오지 못한다고 적었다" caption="그림 1. 창구는 컴퓨터 안쪽에만, 택배사(채널) 연결은 Gateway가 붙잡고 있다" %}

그래서 실제로는, OpenClaw의 **Gateway**가 그 경비실이다. 택배 회사가 **채널**(WebChat, Telegram 같은 메시지 통로), 동·호수가 **세션과 에이전트**, 단지 안쪽 창구가 **127.0.0.1(loopback) 주소의 18789번 문**이다. Gateway는 메시지를 직접 처리하지 않고, 받을 곳을 정해 **에이전트 런타임**(모델을 부르고 도구를 실행하는 부분)에 넘긴다.

## 2. 왜 필요한가

### 받는 곳이 하나여야 대화가 이어진다

27회차 실습에서 터미널 채팅 화면(TUI)으로 나눈 대화가, 나중에 브라우저로 연 WebChat의 Main Session에도 그대로 보였다. 두 화면이 각자 모델을 부른 게 아니라, **둘 다 같은 Gateway에 붙어서** 같은 main 세션(`agent:<agentId>:main`)으로 들어갔기 때문이다.

창구마다 따로 받는 곳이 있으면 "아까 터미널에서 한 이야기"를 WebChat은 모른다. 받는 곳을 하나로 모으면, 어느 대화가 어느 세션으로 갔는지도 한곳에 남는다.

### 127.0.0.1:18789 — 이 컴퓨터 안에서만 여는 문

`openclaw gateway status` 결과를 요약하면 이렇다.

| 항목 | 요약 |
| --- | --- |
| Runtime | running (state active) — 돌고 있다 |
| Connectivity check | ok — 연결 확인 통과 |
| Listening | 127.0.0.1:18789 — 이 주소에서 기다린다 |

주소를 두 조각으로 읽으면 쉽다.

- `127.0.0.1` — "이 컴퓨터 자신"을 가리키는 특별한 주소(loopback). 여기에만 문을 열면 **같은 컴퓨터 안의 프로그램만** 들어올 수 있다.
- `18789` — 포트 번호. 한 컴퓨터 안에 여러 프로그램이 문을 열 수 있어서, 몇 번 문인지 번호로 나눈다.

`openclaw dashboard`로 연 WebChat도 결국 이 주소를 브라우저로 연 것이다. 진단 명령 `openclaw doctor --lint`는 `gateway.bind` 경고로 "loopback에만 열려 있다"고 알려 줬다. 휴대폰 같은 다른 기기에서 WebChat을 쓰려면 이 문을 넓혀야 하는데, 수업 자료는 문을 그냥 바깥에 여는 대신 Tailscale 같은 사설망 도구를 따로 쓰라고 안내했다. 실습에서는 다른 기기를 붙일 계획이 없어서 그대로 뒀다.

### 채널 연결을 붙잡고 있다

Telegram 같은 채널은 내 컴퓨터 밖에 있다. 그런데도 Gateway가 그 채널과의 연결을 계속 유지하고 있어서, 휴대폰으로 보낸 메시지가 들어올 수 있다. 다른 기기가 내 컴퓨터의 18789번 문을 두드리는 것과는 다른 길이다. 그래서 Gateway는 잠깐 켰다 끄는 프로그램이 아니라 {% include term.html name="데몬" %}으로 **계속 켜 두는** 프로그램이다. Gateway가 멈추면 WebChat 화면이 열려 있어도 새 메시지를 보낼 수 없다.

### 에이전트가 여럿이면 누구에게 보낼지도 정한다

노드 7에서는 Gateway 하나에 에이전트를 여럿 두는 구성을 읽었다. 예를 들어 "회사 문의용 봇 계정으로 온 메시지는 상담 담당 에이전트로, 나머지는 기본 에이전트로" 같은 규칙을 설정에 적어 둔다. 이 규칙을 **바인딩(binding)**이라고 부른다. 에이전트가 여럿인데 어느 규칙에도 맞지 않는 메시지가 오면, 그 메시지는 아무 에이전트에게도 가지 않고 `AGENT_SELECTION_REQUIRED`라는 알림이 뜬다. 그래서 "나머지는 누가 받나"를 꼭 정해 둔다({% include term.html name="멀티 에이전트" %}).

### 문에는 열쇠가 있다

Gateway에 붙으려면 토큰이 필요하다. doctor의 두 번째 경고 `gateway.auth.token`은 이 토큰이 설정 파일에 평문으로 적혀 있다는 지적이었다. 고치는 길로 `openclaw secrets configure` → `openclaw secrets audit --check`가 안내됐다. 토큰 값은 화면 캡처나 글에 남기지 않는다.

## 3. 어디서 만났나

**27회차**에서 OpenClaw를 설치하며 처음 만났다. 온보딩이 끝나자 `openclaw-gateway.service`가 systemd 사용자 서비스로 켜져 있었고(active running), `openclaw gateway status`로 `127.0.0.1:18789`에서 기다리는 것을 확인했다. CLI와 Gateway 버전이 둘 다 2026.10.5로 같다는 줄도 함께 나왔다.

OpenClaw는 처음부터 게이트웨이였다. 맨 처음 이름 Warelay는 WhatsApp 메시지를 잇는 게이트웨이 프로그램이었고, 지금도 Gateway가 구조의 한가운데에 있다. 11월 4일에 확인했을 때도 Gateway 서비스는 active였다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| Gateway (OpenClaw) | 게이트웨이 (네트워크) | 네트워크에서 말하는 게이트웨이는 보통 **공유기**처럼 집 안 망(LAN)과 바깥 인터넷 사이에서 데이터를 넘겨 주는 장치다. 집 PC 설정의 "기본 게이트웨이"가 그것이다. OpenClaw의 Gateway는 **메시지를 받아 세션·에이전트로 나눠 주는 프로그램**이다. "드나드는 길목"이라는 뜻만 같다 |
| Gateway | 채널 | 채널은 메시지가 **들어오는 통로**(WebChat, Telegram) 하나하나다. Gateway는 그 통로들을 다 붙잡고 있는 **접수처**다 |
| Gateway | 에이전트 런타임 | Gateway는 **어디로 보낼지**만 정한다. 모델을 부르고 도구를 실제로 실행하는 건 런타임이다 |
| Gateway | WebChat | WebChat은 Gateway가 열어 주는 **화면 하나**다. 화면을 닫아도 Gateway는 계속 돈다. 반대로 Gateway가 멈추면 화면이 떠 있어도 메시지를 못 보낸다 |

## 5. 많이들 오해하는 지점

**ㄱ. "WebChat 창을 닫으면 OpenClaw도 꺼진다"**

WebChat은 창일 뿐이다. 실제로 돌고 있는 건 데몬으로 등록된 Gateway라서, 브라우저 탭을 닫아도, 터미널 채팅 화면(TUI)에서 빠져나와도 서비스는 그대로 있다. 꺼졌는지는 `openclaw gateway status`로 확인하고, 끄려면 `openclaw gateway stop`을 따로 친다. 그래서 실습을 마칠 때 "Gateway 멈추기"가 별도 단계로 있다.

**ㄴ. "doctor가 경고를 냈으니 고장 난 것이다"**

실습의 `doctor --lint` 결과는 검사 36개에 **경고 2개, 오류 0개**였다. `gateway.bind` 경고는 "이 컴퓨터 안에만 열려 있다"는 **현재 상태 안내**에 가깝다. 다른 기기를 붙일 생각이 없다면 오히려 안전한 기본값이다. 경고를 보면 "고장"이 아니라 "이 상태가 내 계획과 맞나?"를 따져 본다. 마지막 줄만 보지 말고 항목을 하나씩 읽으라는 게 수업의 권고였다.

**ㄷ. "Gateway가 누가 말을 걸 수 있는지까지 정해 준다"**

Gateway의 바인딩은 들어온 메시지를 **어느 에이전트에게 보낼지**까지만 정한다. 모르는 사람이 Telegram 봇에 말을 걸어도 되는지는 별개의 문제로, 채널 쪽의 {% include term.html name="페어링" %} 승인이나 허용 목록이 맡는다. "어디로 보낼까"와 "들여보내도 될까"는 다른 문지기가 지킨다.
