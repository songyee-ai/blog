## 한 줄 정의

> 모델이 생각 한 줄을 쓰고, 도구를 한 번 쓰고, 그 결과를 읽은 뒤 다시 생각하기를 답이 나올 때까지 되풀이하게 하는 방법

---

## 1. 비유로 이해하기

생일날 아침, 엄마가 집 안 어딘가에 선물을 숨겨 두고 첫 쪽지를 건넨다. 쪽지에는 "차가운 곳을 찾아봐"라고 적혀 있다.

한 아이는 소파에 앉은 채로 머리만 굴린다. "차가운 곳이면… 냉동실? 아니 베란다? 음, 냉동실이 맞을 거야. 선물은 냉동실에 있어!" 일어나 보지도 않고 답을 외친다. 틀려도 왜 틀렸는지 모른다.

다른 아이는 이렇게 한다.

- **생각** — "차가운 곳이면 냉장고부터 보자."
- **해 보기** — 냉장고 문을 연다.
- **본 것** — 우유 옆에 두 번째 쪽지가 있다. "책이 많은 곳."
- **생각** — "그럼 거실 책장이다."
- **해 보기** — 책장 맨 아래 칸을 들여다본다.
- **본 것** — 리본 달린 상자가 있다.
- **끝** — "찾았다!"

두 번째 아이는 다음 행동을 **방금 본 것**으로 정한다. 두 번째 쪽지가 무엇이라고 할지는 냉장고를 열기 전엔 아무리 생각해도 알 수 없기 때문이다.

{% include figure.html src="/assets/images/term-react/thought-action-observation.svg" alt="'내일 서울로 소풍 가는데 우산 챙길까?'라는 질문 아래로 줄이 차례로 쌓인다. 파란 줄 Thought 1(날씨를 모르니 찾아봐야 한다)과 Action 1(날씨[서울, 내일])은 모델이 쓴다. 빨간 점선에서 프로그램이 모델의 글쓰기를 멈추고 날씨 도구를 돌린 뒤, 초록 줄 Observation 1(오후 강수확률 70%)을 붙인다. 이어서 모델이 Thought 2와 Action 2(끝[우산을 챙기는 게 좋겠다])를 쓴다. 오른쪽 화살표는 답이 나올 때까지 이 세 줄을 되풀이한다는 뜻이다" caption="그림 1. 생각·행동은 모델이 쓰고, 관찰은 프로그램이 도구를 돌린 뒤 붙여 넣는다" %}

실제로는, ReAct는 언어 모델에게 **생각(Thought)**과 **행동(Action)**을 번갈아 글로 쓰게 하고, 그 행동을 프로그램이 실제로 실행한 결과를 **관찰(Observation)**로 다시 입력 뒤에 붙여 주는 방법이다. 모델은 그 관찰까지 읽고 다음 생각을 이어 쓴다. 이름은 Reasoning(추론)과 Acting(행동)을 합친 것이고, 2022년 Yao 등의 논문(arXiv 2210.03629)이 이 방식을 정리해 이름을 붙였다.

## 2. 왜 필요한가

### 머릿속 풀이만으로는 모르는 걸 지어낸다

{% include term.html name="CoT" %}는 모델에게 중간 풀이를 먼저 쓰게 하는 방법이다. 계산 문제처럼 **필요한 정보가 이미 질문 안에 다 있을 때**는 잘 통한다. 그런데 "내일 서울 날씨"처럼 모델이 모르는 사실이 필요하면, 풀이를 아무리 길게 써도 그 사실이 생기지 않는다. 소파에 앉은 아이처럼 그럴듯한 추측을 사실처럼 이어 쓰게 된다.

ReAct 논문은 위키백과 검색 같은 아주 단순한 도구를 붙여 이 차이를 보였다. 질문에 답하려고 여러 문서를 건너 찾아야 하는 과제(HotpotQA)와 사실 확인 과제(FEVER)에서, 모델이 `Search[찾을 말]`로 문서를 찾고 `Lookup[단어]`로 그 안을 살핀 뒤 `Finish[답]`으로 끝내게 했다. 논문은 이렇게 하면 생각만 하는 방식에서 흔한 **사실 지어내기와 앞 단계 실수가 뒤로 번지는 문제**를 줄일 수 있다고 보고했다. 글로 된 가상 집안일 과제(ALFWorld)와 온라인 쇼핑 흉내(WebShop)에서도 시험했다.

논문은 생각 줄을 빼고 행동만 시키는 방식과도 비교했는데, ReAct 쪽이 대체로 나았다. 생각은 **다음 행동을 고르는 근거**가 되고, 행동은 **생각에 쓸 새 사실**을 가져온다. 둘을 엮은 게 ReAct다.

### 한 판은 이렇게 생겼다

그림 1을 글로 옮기면 이렇다.

```text
질문: 내일 서울로 소풍 가는데 우산 챙길까?
Thought 1: 내일 날씨를 모른다. 찾아봐야 한다.
Action 1: 날씨[서울, 내일]
Observation 1: 오후 강수확률 70%
Thought 2: 오후에 비가 올 가능성이 높다.
Action 2: 끝[우산을 챙기는 게 좋겠다]
```

여기서 중요한 건 **누가 어느 줄을 쓰느냐**다. Thought와 Action은 모델이 쓴다. Observation은 모델이 쓰면 안 된다. 프로그램이 `Action 1` 줄까지 받은 뒤 모델의 글쓰기를 멈추고, 날씨 도구를 실제로 돌려서, 그 결과를 `Observation 1:` 뒤에 붙인 다음 다시 모델에게 넘긴다. 그래서 흔히 "`Observation:`이 나오면 멈춰라"는 멈춤 문자열을 걸어 둔다. 이걸 빼먹으면 모델이 관찰 줄까지 제멋대로 지어 써서, 도구를 부르지도 않고 "강수확률 10%"를 만들어 낼 수 있다.

### 줄 모양은 약속일 뿐이었다 — 텍스트 규약의 약점

학교에서 엄마에게 보내는 알림장을 떠올려 보자. 선생님이 "준비물은 꼭 맨 아래 칸에 '준비물: ○○' 꼴로 적으세요"라고 정해 두었다. 엄마는 그 칸만 보고 준비물을 챙긴다. 그런데 어떤 아이가 "내일 리코더 가져오래요~"라고 다른 줄에 적어 버리면, 엄마는 그 줄을 준비물로 알아보지 못한다.

실제로는, 초기 ReAct 방식에서 모델과 프로그램 사이에는 도구 전용 통로가 없었다. 프롬프트 안에 "도구를 쓰고 싶으면 이런 꼴로 한 줄 써라"라고 **표기 약속**을 안내해 두고, 모델이 그 꼴대로 쓴 줄을 개발자 코드가 문자열로 잘라 읽는 게 전부였다.

```python
import re

m = re.search(r"Action \d+: (\w+)\[(.*)\]", model_text)
if m:
    tool_name, tool_arg = m.group(1), m.group(2)
    observation = TOOLS[tool_name](tool_arg)     # 실제 도구 실행
else:
    ...   # 모양이 어긋나면 어떤 도구를 부르려 했는지 알 수 없다
```

모델이 `Action 1: 날씨 (서울)`처럼 괄호 하나만 바꿔 써도 이 코드는 못 읽는다. 게다가 이 줄 모양은 표준이 아니라 **만드는 사람마다 달랐다.** 초기 {% include term.html name="LangChain" %}의 에이전트처럼 `Action:`과 `Action Input:`을 두 줄로 나눠 쓰는 식도 있었다. 그래서 한 모델에 맞춰 짠 해석 코드를 다른 모델에 그대로 가져다 쓸 수 있으리란 법이 없었다.

### 그 뒤의 변화 — 생각·행동 고리는 남고 표기만 바뀌었다

22회차에서 도구를 건네는 방식의 흐름을 내 말로 줄이면 이렇다.

| 때 | 방식 | 모델이 도구를 부르는 모양 | 남은 숙제 |
| --- | --- | --- | --- |
| 2022 | ReAct 같은 텍스트 규약 | 글 속의 `Action: …` 줄을 개발자가 잘라 읽음 | 모양이 어긋나면 못 읽고, 회사·구현마다 표기가 다름 |
| 2023년 6월 | OpenAI function calling (이어서 Anthropic tool use 등) | 요청에 JSON 스키마로 도구를 적어 보내면, 응답에 **구조가 정해진 호출 블록**이 따로 온다 | 앱과 도구를 짝마다 따로 이어 붙여야 함 |
| 2024년 11월 | {% include term.html name="MCP" %} 공개 | 도구를 가진 서버와 그걸 쓰는 앱이 **공통 규격**으로 연결됨 | 어떤 서버를 믿고 붙일지는 여전히 내가 판단 |

달라진 건 **"행동"을 적는 방법**이다. 글자 잘라 읽기에서 API가 따로 마련한 호출 칸으로, 다시 여러 앱이 같이 쓰는 연결 규격으로 옮겨 갔다. 반면 "생각하고 → 도구를 쓰고 → 결과를 보고 → 다시 생각한다"는 고리는 그대로다. 지금의 코딩 에이전트도 이 고리를 돈다. 22회차 실습에서 Claude Code가 남긴 기록을 보면 `ToolSearch`로 도구 설명을 불러오고, `Bash`로 설정 파일을 읽고, {% include term.html name="Qdrant" %}에 문장 세 개를 한 번에 저장한 뒤 검색했다. 한 번에 여러 호출을 묶어 보내기도 하지만, **결과를 받아 본 뒤 다음 걸음을 정하는** 모양은 같다. 다만 `Action:` 줄이 아니라 정해진 구조의 호출로 했다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| ReAct | CoT | CoT는 **머릿속 풀이만** 이어 쓴다. ReAct는 풀이 사이사이에 **도구를 실제로 써서** 바깥 사실을 가져온다 |
| ReAct | 함수 호출 (function calling, tool use) | ReAct는 생각과 행동을 번갈아 하는 **진행 방식**이다. 함수 호출은 그 "행동"을 **구조화된 블록으로 주고받는 API 기능**이다. 함수 호출 위에서도 ReAct식 고리를 돌릴 수 있다 |
| ReAct | Reflexion | ReAct는 한 번의 시도 **안에서** 관찰을 보고 다음 걸음을 고친다. Reflexion은 시도가 **끝난 뒤** 실패의 교훈을 메모로 적어 다음 시도에 들고 간다 |
| ReAct | AI 에이전트 · 하네스 | ReAct는 고리를 도는 **한 가지 방법**이다. {% include term.html name="AI 에이전트" %}는 그 고리로 일하는 **시스템 전체**, {% include term.html name="하네스" %}는 도구 실행·멈춤·결과 붙이기를 실제로 맡는 **바깥 코드**다 |

## 5. 많이들 오해하는 지점

**ㄱ. "ReAct는 계획·실행·관찰·반성의 네 단계다"**

7회차 리뷰에 나는 네 단계 고리로 적고 그 발상을 ReAct라고 불렀다. 큰 줄기는 맞지만, 논문이 보인 실제 모양은 **생각·행동·관찰 세 줄의 반복**이다. 계획은 따로 한 번에 세우는 단계가 아니라 매번의 Thought 줄 안에 조금씩 들어 있다. 실패한 뒤 교훈을 적어 다음 시도에 쓰는 "반성"은 19회차에서 본 Reflexion 쪽에 더 가깝다.

**ㄴ. "함수 호출과 MCP가 나왔으니 ReAct는 끝난 방법이다"**

끝난 건 `Action: …` 줄을 글자로 잘라 읽던 **표기 방식**이다. 생각하고, 도구를 쓰고, 결과를 보고 다음을 정하는 **고리**는 지금 에이전트들의 기본 동작으로 남아 있다. 그래서 "ReAct를 쓰느냐"보다 "내 에이전트가 도구 결과를 실제로 읽고 다음 걸음을 바꾸느냐"를 보는 편이 쓸모 있다.

**ㄷ. "Thought 줄에 적힌 이유가 곧 모델이 그 행동을 고른 진짜 이유다"**

Thought도 모델이 **글로 써낸 설명**일 뿐이라, 속에서 일어난 계산을 그대로 찍은 기록이라는 보장이 없다. CoT 글의 오해 ㄱ과 같은 이야기다. 믿을 만한 건 오히려 **Observation 쪽**이다. 프로그램이 도구를 실제로 돌려 받은 값이기 때문이다. 그래서 에이전트가 무엇을 근거로 답했는지 확인할 때는 생각 줄보다 **어떤 도구를 어떤 인자로 불렀고 무엇이 돌아왔는지** 기록부터 본다.
