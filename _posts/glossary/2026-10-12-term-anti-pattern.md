## 한 줄 정의

> 당장은 편하고 그럴듯해서 자꾸 되풀이되지만, 쌓일수록 문제를 키우는 설계 버릇

---

## 1. 비유로 이해하기

엄마가 "방 좀 치워라" 하신다. 서랍에 나눠 넣으려니 귀찮아서 장난감, 양말, 숙제 프린트를 전부 침대 밑으로 밀어 넣었다. 방은 1분 만에 깨끗해 보인다. 칭찬도 받았다.

그런데 다음 날 아침 숙제 프린트가 필요하다. 침대 밑에서 양말 더미를 헤집다가 지각할 뻔한다. 다음 주에도 똑같이 밀어 넣는다. 침대 밑은 점점 꽉 차고, 어느 날은 뭔가 썩는 냄새가 난다.

이 버릇에는 세 가지 특징이 있다.

- **당장은 효과가 있어 보인다.** 방이 깨끗해졌고 칭찬도 받았다.
- **그래서 되풀이된다.** 한 번의 실수가 아니라 습관이다.
- **나중에 더 비싸게 돌아온다.** 찾는 시간이 늘고, 문제가 눈에 띌 때는 이미 크다.

실제로는, 프로그램을 설계할 때도 이런 버릇이 있다. 처음 만들 땐 잘 돌아가고 편해서 자꾸 쓰지만, 기능이 늘고 상황이 복잡해질수록 고장과 수고를 키우는 해법. 이렇게 자주 보이는 나쁜 해법에 이름을 붙여 둔 것이 안티패턴이다.

## 2. 왜 필요한가

### 이름이 있으면 짚고 고치기 쉽다

소프트웨어 쪽에는 자주 쓰이는 좋은 설계 틀을 "디자인 패턴"이라고 부르는 전통이 있다. 안티패턴은 그 반대말로, 1990년대 중반에 생긴 말이다. 흔히 드는 예는 이렇다.

| 이름 | 무슨 버릇인가 | 왜 나중에 비싼가 |
| --- | --- | --- |
| 복사-붙여넣기 코드 | 비슷한 코드를 함수로 묶지 않고 여러 군데에 복사한다 | 한 곳의 버그를 고치면 나머지 복사본은 그대로 남는다 |
| 만능 객체 (God object) | 한 덩어리가 너무 많은 일을 다 맡는다 | 어디를 고쳐도 다른 곳이 같이 흔들린다 |
| 매직 넘버 | `if x > 37:`처럼 뜻을 알 수 없는 숫자를 코드에 박는다 | 그 숫자가 왜 37인지 아무도 모르게 된다 |

이름이 붙어 있으면 코드를 함께 볼 때 "이거 복붙이네" 한마디로 문제를 짚을 수 있고, 그 이름 옆에 정리된 대안을 바로 찾아 쓸 수 있다.

### 에이전트에서 만난 네 가지

22회차에서는 에이전트에 도구를 줄 때 자주 보이는 안티패턴 네 가지를 다뤘다. 그날 수업 전체를 꿰는 질문은 "에이전트가 실패하는 세 순간", 곧 **도구를 잘못 고를 때, 결과를 잘못 읽을 때, 같은 실수를 되풀이할 때**였다. 네 습관은 이 세 순간과 짝을 이룬다.

{% include figure.html src="/assets/images/term-anti-pattern/four-anti-patterns.svg" alt="네 줄 세 칸짜리 표. 줄은 도구 남발, 반환값 데이터 덤프, 권한 방치, 중단 없는 순환이고 칸은 잘못 고름, 잘못 읽음, 같은 실수 반복이다. 도구 남발은 잘못 고름, 데이터 덤프는 잘못 읽음, 중단 없는 순환 줄은 같은 실수 반복 칸이 진하게 칠해져 있고, 권한 방치는 세 칸을 가로지르는 긴 막대로 세 순간 모두의 피해를 키운다고 적혀 있다" caption="그림 1. 네 가지 안티패턴이 특히 크게 만드는 실패 순간" %}

**① 도구 남발 → 잘못 고름**

색연필 통에 하늘색, 물색, 파랑, 남색, 청록… 비슷한 파란 계열이 마흔 자루 꽂혀 있다. "바다를 칠해" 하면 아이는 한참 고르다가 엉뚱한 걸 집는다.

실제로는, 에이전트에 수십 개의 도구를 한꺼번에 붙이면 이름이 비슷하거나 하는 일이 겹치는 도구가 늘수록 모델이 헛짚을 확률도 커진다. 게다가 도구 설명은 전부 모델의 입력에 들어가니, 고르기 전부터 {% include term.html name="컨텍스트 윈도우" %}를 많이 차지한다. 늘 쓰는 몇 개만 처음부터 쥐여 주고, 가끔 쓰는 것은 그때그때 꺼내 주는 편이 낫다.

내 실습에서 같은 {% include term.html name="MCP" %} 서버(Qdrant)를 두 에이전트에 붙여 봤다. opencode는 첫 단계 입력이 10,355토큰이었고 시스템 지시와 도구 설명이 한꺼번에 들어갔다. Claude Code는 MCP 도구 설명을 처음부터 다 넣지 않고 `ToolSearch`로 필요할 때 불러왔다. 도구가 많아질 때 입력이 불어나는 문제를 줄이는 방식이다.

**② 반환값 데이터 덤프 → 잘못 읽음**

친구에게 "토요일에 몇 시에 만나?" 물었더니 일주일치 일기장을 통째로 건넨다. 답은 어딘가 적혀 있지만, 찾다가 금요일 칸의 시간을 읽고 엉뚱한 시각에 나간다.

실제로는, 도구가 원본 데이터를 통째로 돌려주면 모델은 그 더미 속에서 필요한 한두 값을 직접 찾아내야 한다. 그 과정에서 엉뚱한 값을 집거나, 답에 쓰면 안 되는 값을 그대로 옮긴다. 긴 입력 속에서 중요한 내용이 묻히는 문제는 {% include term.html name="맥락 부패" %} 글에도 정리했다. 돌려줄 것은 다음 판단에 쓸 값, 그 값이 어디서 왔는지, 그리고 결과가 잘렸다면 잘렸다는 표시 정도면 된다.

내 {% include term.html name="도구 정의서" %}에서 재고 조회 도구의 반환은 `sku`, `warehouse_id`, `available_quantity`, `checked_at` 네 가지로 정했고, 내부 원가 같은 원본 데이터는 돌려주지 않게 했다. 과제 설계에서도 주문 조회 도구는 상태 필드만 돌려주고 주소·연락처·결제 정보·내부 메모·작업자 이름은 돌려주지 않게 적었다.

**③ 권한 방치 → 세 순간 모두의 피해를 키움**

선생님이 "출석부 보고 누가 안 왔는지만 알려 줘" 하면서 볼펜까지 같이 건넸다. 친구는 확인만 하려다 잘못 본 이름 옆에 결석 표시를 그어 버린다.

실제로는, 읽기만 해야 하는 일에 쓰기 권한까지 주면 실수가 곧바로 실제 변경이 된다. 엉뚱한 도구를 골랐다면 엉뚱한 데이터가 바뀌고, 값을 잘못 읽었다면 틀린 값이 저장되고, 같은 호출을 되풀이하면 그만큼 여러 번 바뀐다. 그래서 이 습관은 세 순간 중 하나가 아니라 모두에 걸쳐 있다. 읽기 도구와 쓰기 도구를 나누고, 쓰기는 사람의 확인을 거치게 하며, 모델이 무엇을 요청하든 서버 쪽에서 다시 검사한다. 필요한 만큼만 권한을 주는 원칙을 {% include term.html name="최소 권한" %}이라고 한다.

내 실습에서는 이렇게 나눴다.

- 재고 조회 도구는 처음부터 "읽기만 하며, 수량은 바꾸지 않는다"로 정의했다.
- Qdrant MCP 서버는 `QDRANT_READ_ONLY=true`를 주면 쓰기 도구 `qdrant-store`가 도구 목록에서 아예 빠졌다.
- 과제의 반품 신청 도구(쓰기)는 하네스가 실행을 멈추고 고객 확인 화면을 띄운 뒤, 확인 기록이 있을 때만 신청서를 만들게 설계했다.
- 반대로 기록해 둔 장면도 있다. Claude Code에 허용 도구를 qdrant 두 개로 정했는데도 `ls`, `cat` 같은 읽기 명령이 기본 허용이라 실행됐다. 덕분에 설정 파일을 읽어 묶음 이름을 알아냈지만, 내가 정한 범위 밖의 도구가 쓰였다는 점에서 권한 쪽으로 다시 볼 대목이다.

**④ 중단 없는 순환 → 같은 실수 반복**

잠긴 교실 문 손잡이를 열 번, 스무 번 돌린다. 세게 돌려도, 반대로 돌려도 열쇠가 없으면 안 열린다. 세 번쯤 해서 안 되면 선생님을 부르러 가야 한다.

실제로는, 도구가 실패했는데 같은 호출을 그대로 되풀이하거나, 값을 아무렇게나 바꿔 가며 다시 던져 보는 것은 운에 맡기는 일이다. 몇 번까지, 얼마 동안까지만 다시 해 볼지 미리 정하고, 그 선을 넘으면 사람을 부르거나 아무것도 바꾸지 않은 채 멈춘다.

내 정의서의 실패 표에는 `TEMPORARY_ERROR`이면 **재시도 한 번 → 또 실패하면 중단**하고, "세 번 이상 되풀이하기"는 하지 말 것으로 적었다. 과제의 쓰기 도구는 아예 재시도하지 않고 "접수 여부를 확인하지 못했다"고 알린 뒤 멈추게 했다. 신청 같은 쓰기 동작은 다시 부르면 같은 신청이 두 번 들어갈 수 있어서 일반적으로 더 조심하는 부분이다.

이 습관은 사람이 프롬프트를 고칠 때도 생긴다. 여러 곳을 한꺼번에 고치며 될 때까지 돌리면 무엇이 효과를 냈는지 모른다. 내 재고 도구 실험은 설명문을 한 번에 한 문장씩만 바꿔 18개 기록을 남겼고, 그래서 "부산 3번"을 되묻던 실행(trace-12)이 다른 수정 뒤에 다시 `BUSAN-02`로 바뀌는 회귀(trace-18)를 찾을 수 있었다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| 안티패턴 | 버그 | 버그는 **의도대로 동작하지 않는** 것. 안티패턴은 지금은 **동작하지만** 설계가 나빠 나중에 문제를 키우는 것 |
| 안티패턴 | 디자인 패턴 | 디자인 패턴은 검증된 **좋은 해법**에 붙인 이름, 안티패턴은 흔하지만 **나쁜 해법**에 붙인 이름. 보통 "대신 이렇게 하라"는 처방과 함께 정리된다 |
| 안티패턴 | 한 번의 실수 | 실수는 한 번 일어나고 끝난다. 안티패턴은 그럴듯해서 **여러 사람이 되풀이하는** 버릇이다 |
| 도구 남발 | 반환값 데이터 덤프 | 둘 다 모델의 입력을 불린다. 도구 남발은 **들어가는 쪽**(도구 목록)이, 데이터 덤프는 **돌아오는 쪽**(도구 결과)이 넘친다 |

## 5. 많이들 오해하는 지점

**ㄱ. "지금 잘 돌아가니까 문제없다"**

안티패턴의 무서운 점은 처음에는 잘 돌아간다는 것이다. 침대 밑도 첫날엔 깨끗해 보였다. 내 재고 도구 실험에서도 가장 위험한 실행은 오류 하나 없이 지나갔다. "부산 3번 창고"를 물었는데 모델이 `BUSAN-02`로 바꿔 불렀고, 하네스 검사를 통과해 "현재 가용 재고는 7개입니다"라고 그럴듯하게 답했다. 겉보기에 잘 돌아가는 것과 맞게 돌아가는 것은 따로 확인해야 한다.

**ㄴ. "반대로 하면 해결된다"**

도구가 너무 많으면 전부 빼고, 반환이 너무 길면 한 줄로 줄이면 될까. 한쪽 끝에서 반대쪽 끝으로 옮기면 다른 실패가 생긴다. 내 실험에서 설명문의 허용 창고 목록을 빼자 억지 맞추기는 사라졌지만 "부산"처럼 바꿔도 되는 이름까지 거절했다(trace-14). 그걸 고치려고 코드를 다시 넣자 억지 맞추기가 돌아왔다(trace-18). 처방은 "덜"이 아니라 "필요한 만큼"이고, 고친 뒤에는 예전 문항을 전부 다시 돌려 봐야 한다.

**ㄷ. "안티패턴 하나에 실패 하나가 딱 짝지어진다"**

그림 1은 각 습관이 **가장 크게** 키우는 실패만 칠한 것이다. 권한 방치처럼 세 순간 모두에 걸치는 것도 있고, 도구 남발이 입력을 불려 결과를 잘못 읽게 만드는 데도 한몫할 수 있다. 짝은 "어디부터 의심할까"를 정하는 출발점이지, 원인을 하나로 못 박는 공식이 아니다.
