## 한 줄 정의

> 실행된 프로그램이 닿을 수 있는 파일·네트워크 범위를 울타리로 좁혀, 허락한 실행이 잘못돼도 피해가 그 안에만 머물게 하는 실행 환경

---

## 1. 비유로 이해하기

유치원 마당의 **모래놀이 상자**를 떠올려 보자. 아이가 선생님께 "삽으로 모래 파도 돼요?" 하고 묻는다. 선생님은 "삽은 괜찮아, 가위는 안 돼" 하고 대답한다. 이건 **무엇을 해도 되는지 미리 정하는 일**이다.

허락을 받은 아이는 상자 안에서 마음껏 판다. 그러다 힘이 넘쳐 모래를 휙 뿌릴 때도 있다. 그래도 모래는 상자 테두리 안에 떨어지고, 교실 바닥이나 옆 친구 가방까지는 가지 않는다. 테두리는 아이가 무엇을 할지 묻지 않는다. **무슨 일이 생기든 모래가 어디까지 퍼질지**만 정한다.

선생님의 허락이 있다고 모래가 튀지 않는 것은 아니다. 테두리가 있다고 가위를 들고 들어가도 되는 것도 아니다. 둘은 하는 일이 다르다.

{% include figure.html src="/assets/images/term-sandbox/permission-vs-sandbox.svg" alt="왼쪽 '에이전트가 하려는 행동(셸 명령 하나)'에서 화살표가 파란 '권한' 칸으로 간다. 권한 칸은 실행하기 전에 해도 되는지 정하며 allow·ask·deny, 예로 Claude Code 권한 규칙을 적었다. 거부되면 아래 빨간 칸 '실행 안 함'으로 가고, 허락되면 오른쪽 초록 점선 울타리 '샌드박스·격리'로 들어간다. 울타리 안에서는 실행 중인 명령이 실수하거나 속아도 그 안에 머물고 작업 폴더에는 닿는다. 예로 Docker 컨테이너와 Claude Code의 Bash 샌드박스를 적었다. 울타리 아래 빨간 칸은 울타리 밖 파일·네트워크로, 닿지 못하게 막힌다. 왼쪽 아래에는 권한을 촘촘히 해도 허락한 명령의 실수까지 막지는 못하고, 울타리를 쳐도 그 안에서 무엇을 해도 될지는 따로 정해야 하므로 하나가 다른 하나를 대신하지 않는다고 적었다" caption="그림 1. 권한은 실행 전에 '해도 되나'를, 샌드박스는 실행 중에 '어디까지 닿나'를 정한다" %}

그래서 실제로는, 선생님의 허락이 **권한**, 모래놀이 상자의 테두리가 **샌드박스(격리)**다. 이름도 이 모래놀이 상자(sandbox)에서 왔다. 컴퓨터에서 샌드박스는 실행 중인 프로그램이 읽고 쓸 수 있는 폴더, 접속할 수 있는 네트워크를 운영체제나 컨테이너 수준에서 좁혀 두는 환경이다.

## 2. 왜 필요한가

### 허락만으로는 막을 수 없는 것

에이전트에게 "테스트 명령은 승인 없이 돌려도 돼"라고 허락했다고 하자. 허락은 **명령을 실행하기 전**에 한 번 판단하는 일이다. 그 명령이 실행되는 동안 무엇을 건드리는지는 허락이 따라가 보지 않는다.

```
허락한 것:   테스트 실행, 빌드 폴더 정리
실제로 생길 수 있는 일:
  - 정리할 폴더 경로를 잘못 적어 엉뚱한 폴더를 지운다
  - 읽어 온 외부 문서에 숨은 지시에 속아, 허락된 명령으로 다른 파일을 읽어 밖으로 보낸다
```

두 번째가 {% include term.html name="프롬프트 인젝션" %}이다. 25회차 노드 8은 에이전트의 능력을 하나씩 떼어 보는 데서 출발했다. 문서를 읽고, 셸을 돌리고, 밖에서 온 메시지까지 받는 에이전트라면, 밖에서 들어온 글 한 줄이 셸 실행까지 곧장 이어지는 길이 생긴다. 이럴 때 샌드박스가 있으면, 명령이 실수하거나 속더라도 닿을 수 있는 파일과 네트워크가 울타리 안으로 줄어든다.

### 울타리만으로도 부족한 것

거꾸로 샌드박스만 있으면 될까. 울타리는 **안에서 일어나는 일**은 막지 않는다. 작업 중인 프로젝트 폴더가 울타리 안에 있다면, 그 폴더의 중요한 파일을 지우는 명령은 그대로 실행된다. 무엇을 바로 실행하고 무엇을 사람에게 물을지({% include term.html name="HITL" %})는 여전히 권한이 정해야 한다.

노드 8도 이 둘을 따로 세웠다. 위의 모래놀이 상자에 빗대어 내 말로 다시 정리하면 이렇다.

| 견주어 볼 것 | 권한 (선생님의 허락) | 샌드박스·격리 (상자 테두리) |
| --- | --- | --- |
| 묻는 질문 | 이 행동을 해도 되나? | 허락받은 행동이 어디까지 번질 수 있나? |
| 정하는 때 | 명령을 실행하기 **전에**, 무엇을 허락할지 | 허락된 명령이 실행되는 **동안**, 닿을 수 있는 파일·네트워크의 범위 |
| 모래놀이로 치면 | "삽은 되고 가위는 안 돼" | 모래를 뿌려도 상자 밖으로는 안 나간다 |
| 실제 예 | Claude Code 권한 규칙, opencode의 allow · ask · deny | Docker 컨테이너, Claude Code의 Bash 샌드박스 |

수업 자료의 문장대로, **하나가 다른 하나를 대신하지 않는다.**

### 도구마다 두 칸을 놓는 자리가 다르다

노드 8은 같은 질문을 세 도구로 살폈다.

| 도구 | 권한 | 격리 | 근거 |
| --- | --- | --- | --- |
| pi | 도구 안에 허락을 묻는 단계가 따로 없다. pi를 띄운 계정이 할 수 있는 일은 pi도 다 할 수 있다 | 울타리가 필요하면 {% include term.html name="Docker" %} 같은 바깥 환경을 따로 마련한다 | [벤더] 저자 에세이 |
| Claude Code | 무엇을 바로 하고 무엇을 물을지 도구 설정에서 먼저 정한다 | 셸 명령이 읽고 쓰거나 접속할 수 있는 곳을 운영체제 기능으로 좁히는 Bash 샌드박스가 있다(macOS, Linux, {% include term.html name="WSL" %}2) | [공식 문서] Anthropic |
| OpenClaw | pairing, allowFrom, 그룹 멘션 요구 세 설정으로 누가 말을 걸 수 있는지 거른다 | 대화를 에이전트·작업 공간·보낸 사람마다 따로 연다. 대화가 섞이지 않을 뿐, 실행을 가두는 컨테이너는 아니다 | 수업 자료 노드 8 |

pi와 Claude Code를 나란히 놓은 것은 승자를 가리려는 게 아니다. 허락을 어디서 판단하고 실행을 어디서 가둘지, 그 자리를 서로 다르게 잡은 두 예일 뿐이다. macOS `sandbox-exec`나 Docker를 실제로 어떻게 쓰는지는 노드 8의 범위 밖이었다.

### 막는 만큼 정상 작업도 막힌다

울타리를 좁히거나 허락을 줄이면 안전해 보인다. 하지만 필요한 파일이나 네트워크까지 막아 버리면 에이전트가 일을 끝내지 못한다. 노드 8이 소개한 AgentDojo([학술] Debenedetti et al., NeurIPS 2024)가 공격 성공률과 작업 완수율을 **함께** 재는 것도 이 때문이다. 설정을 바꿀 때는 "막힌 정상 작업"도 같이 기록해야 다음 설정을 고를 근거가 생긴다.

## 3. 어디서 만났나

**25회차** 노드 8(권한·보안: 허용 범위와 격리)에서 만났다. 하네스의 일곱 기능 가운데 권한·보안 칸을 다루면서, '해도 되나'를 묻는 일과 '잘못돼도 어디까지 번지나'를 묻는 일을 갈라 놓았고, 뒤쪽 질문의 답으로 Docker 컨테이너와 Claude Code의 Bash 샌드박스가 나왔다. 노드 7에서도 pi 비교 카드의 권한 경계 칸에 "컨테이너 같은 외부 격리 환경에 맡긴다"로 먼저 얼굴을 비쳤다.

같은 날 과제 `experiment-01`은 셸 명령과 파일 편집을 모두 승인 없이 허용하고 돌렸다. 실험 폴더는 홈 아래 `harness-runs`에 두었는데, 상위 폴더의 `CLAUDE.md`가 실험에 섞이지 않게 하려는 배치였다. 허용을 넓힐 때 실험 기록에는 이렇게 적었다.

> 원격 저장소가 없는 일회용 폴더라 밖으로 나가는 일은 없다.

지금 다시 보면 이 문장은 원격 저장소로 푸시될 일이 없다는 것만 따진 말이었다. 셸 명령이 홈 폴더나 다른 폴더로 옮겨 가는 것까지 막아 주는 울타리는 아니었다. 그러니 이 설정은 샌드박스가 아니라 **권한을 넓힌** 설정이었다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| 샌드박스 | 권한 | 권한은 실행 **전에** "해도 되나"를 정한다. 샌드박스는 실행 **중에** "어디까지 닿나"를 제한한다 |
| 샌드박스 | {% include term.html name="Docker" %} 컨테이너 | 샌드박스는 "실행 범위를 가둔다"는 **역할**의 이름이다. Docker 컨테이너는 그 역할을 맡길 수 있는 외부 격리 환경 **하나**다. Claude Code의 Bash 샌드박스처럼 컨테이너 없이 운영체제 기능으로 가두는 방식도 있다 |
| 샌드박스 | 세션 분리 | 세션 분리(OpenClaw)는 대화 상태가 섞이는 범위를 줄인다. 도구가 실행될 때 닿는 파일·네트워크를 막는 것은 아니다 |
| 샌드박스 | {% include term.html name="가상환경" %} (venv) | 가상환경은 파이썬 패키지를 프로젝트별로 나누는 정리 도구다. 실행된 코드가 다른 폴더를 읽거나 지우는 것을 막아 주지는 않는다 |

## 5. 많이들 오해하는 지점

**ㄱ. "샌드박스를 켰으니 권한은 다 허용해도 된다" (또는 그 반대)**

샌드박스는 울타리 밖을 지킬 뿐, 울타리 안의 파일은 지켜 주지 않는다. 작업 폴더 안에서 중요한 파일을 지우는 명령은 샌드박스 안에서도 그대로 실행된다. 반대로 권한 규칙을 촘촘히 짰다고 격리가 필요 없어지지도 않는다. 허락한 명령이 실수하거나 외부 문서에 속는 경우는 권한 단계에서 보이지 않기 때문이다. 노드 8의 표가 두 칸을 따로 둔 이유다.

**ㄴ. "세션을 나눴으니 격리된 것이다"**

OpenClaw가 대화를 사람마다 따로 열면, 한 사람과 나눈 이야기가 다른 사람 쪽으로 새지 않는다. 그런데 대화가 따로라고 도구까지 따로 도는 것은 아니다. 노드 8도 둘을 같은 것으로 보지 않았다. 도구가 같은 컴퓨터(host)에서 그대로 실행된다면, 그 도구가 어디까지 닿는지는 샌드박스 설정과 실행 환경을 따로 들여다봐야 알 수 있다. 모래놀이로 치면 아이마다 이름표를 붙여 준 것이지, 상자를 하나씩 나눠 준 것은 아니다.

**ㄷ. "일회용 폴더에서 돌리면 샌드박스를 쓴 것과 같다"**

`experiment-01`이 이 경우다. 원격 저장소가 없는 폴더라면 원격으로 밀려 나갈 일은 없다. 하지만 이것은 "어디서 돌릴지"를 고른 것이고, 운영체제나 컨테이너가 명령을 그 폴더 안에 붙잡아 두는 것은 아니다. 셸 명령은 얼마든지 상위 폴더나 홈 폴더로 옮겨 갈 수 있다. 위 '어디서 만났나'에서 바로잡은 대로, 그 실험은 권한을 넓힌 것이지 샌드박스를 켠 것이 아니었다.
