## 한 줄 정의

> 자동으로 돌아가는 흐름 중간에 사람이 내용을 보고 허락해야 다음 단계로 넘어가게 만든 멈춤 지점

---

## 1. 비유로 이해하기

학교에서 체험학습을 가기 전에 가정통신문이 온다. 날짜, 장소, 준비물, 비용이 적혀 있고, 맨 아래에 보호자 서명 칸이 있다. 선생님이 계획을 다 세웠어도, 보호자가 읽고 서명한 종이가 돌아와야 그 아이는 버스를 탄다. 장소가 이상하거나 날짜가 겹치면 보호자는 서명하지 않고 선생님께 물어본다.

출석 부르기나 급식 나눠 주기에는 서명을 받지 않는다. 서명은 학교 밖으로 나가는 일처럼 **한번 하면 되돌리기 어려운 일** 앞에만 둔다.

{% include figure.html src="/assets/images/term-hitl/approval-gate.svg" alt="사람 승인 지점이 있는 흐름. ① 에이전트가 wf.json 초안을 쓰고 노드와 연결을 보여 준다. ② 여기서 흐름이 멈추고 사람이 이름, URL, 연결을 읽고 판단한다. 허락하면 ③ workflow create로 서버에 실제로 만든다. 고칠 곳이 있으면 초안으로 되돌린다. 아래에는 멈춤 지점을 만들기, 보내기, 고치기, 지우기처럼 바깥 상태를 바꾸는 단계 바로 앞에 두고, 읽기만 하는 단계는 그냥 지나간다고 적었다" caption="그림 1. 만들기 직전에 멈추고, 사람이 읽고 허락하면 그때 실행한다" %}

그래서 실제로는, HITL(Human-in-the-Loop, 사람이 고리 안에 들어간다는 뜻)은 {% include term.html name="AI 에이전트" %}나 {% include term.html name="워크플로" %}가 일을 하다가 **바깥을 바꾸는 행동 직전에 멈추고 사람의 허락을 기다리게** 하는 장치다. 사람은 무엇을 하려는지 보고 "진행" 또는 "고쳐"를 고른다.

---

## 2. 왜 필요한가

### 읽는 일과 바꾸는 일은 실수의 무게가 다르다

에이전트나 워크플로가 하는 행동은 두 갈래로 나눠 볼 수 있다.

```
읽기만 하는 일   : 메일 목록 보기, 공개 페이지 가져오기, 표 읽기
바깥을 바꾸는 일 : 메일 보내기, 표 고치기, 파일 지우기, 워크플로 만들기
```

읽기에서 실수하면 다시 읽으면 된다. 보낸 메일이나 지운 파일은 되돌리기 어렵다. 그래서 멈춤 지점은 모든 칸에 두지 않고, 아래 줄의 행동 바로 앞에 둔다.

### 모델에게 고르게 할수록 더 필요해진다

워크플로는 사람이 그린 화살표대로 가니, 어느 칸에서 메일을 보내는지 미리 안다. 에이전트는 모델이 그때그때 쓸 도구를 고른다. 모델이 메일을 잘못 읽었거나, 메일 안에 숨은 지시({% include term.html name="프롬프트 인젝션" %})에 속으면 엉뚱한 도구를 고를 수 있다. 바꾸는 도구를 쓰기 직전에 사람이 한 번 보면, 그런 잘못이 바깥으로 나가기 전에 잡을 기회가 생긴다. 24회차에서는 처음에는 읽는 도구만 연결하고, 보내기·고치기·지우기 도구는 사람 승인이나 IF 조건을 통과한 뒤에만 실행되게 하라고 했다.

### 허락하려면 볼 것이 있어야 한다

멈춤 지점은 "진행할까요?" 한 줄만 띄우면 의미가 없다. 사람이 **무엇을 하려는지** 읽을 수 있어야 한다. 노드 4 실습에서는 에이전트에게 이렇게 맡겼다.

```
… 워크플로 정의를 wf.json으로 만들고,
생성 명령을 실행하기 전에 JSON의 노드와 연결을 보여 줍니다.
확인했다는 답을 받은 뒤 생성합니다.
```

에이전트가 보여 준 `wf.json`에서 두 칸의 이름, HTTP Request가 요청할 URL, 칸 사이 연결을 보고, "확인했어. 이 내용으로 워크플로를 생성해 줘."라고 답한 뒤에야 생성 명령이 실행됐다. JSON에 적힌 URL로 실제 요청이 나가니, 승인하는 사람은 그 URL을 읽어야 한다.

## 3. 어디서 만났나

**24회차** 노드 5에서 AI Agent 칸에 도구를 붙이는 이야기를 하며 이름이 나왔다. 바깥을 바꾸는 도구는 사람 승인(human-in-the-loop, HITL)이나 별도 조건을 거친 뒤 실행하라는 대목이었다.

[24회차 — 다음 행동은 누가 정하나]({{ site.baseurl }}/2026/10/15/who-picks-next-step/)

이름은 노드 5에서 처음 들었지만, 실습에서는 그 전부터 같은 방식으로 일했다. 노드 4에서 Claude Code에게 n8n 워크플로를 만들게 할 때, 생성 명령 앞에 "정의를 보여 주고 확인받은 뒤 만든다"는 멈춤 지점을 요청에 직접 넣었다. 노드 5의 메일 요약 실습 요청문에도 "JSON을 먼저 보여 주고, 확인했다고 답하면 생성해 달라"는 같은 멈춤 지점이 들어 있었다. 그때 승인 전에 검토할 항목에는 메일을 보내거나 지우는 칸이 없는지 확인하는 것이 들어 있었다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| HITL | IF 노드(분기 칸) | IF 노드는 "값이 비어 있는가"처럼 **미리 적은 조건을 기계가** 검사한다. HITL은 조건으로 적기 어려운 판단을 **사람이** 그 자리에서 한다 |
| HITL | 실행 뒤 결과 확인 | 실행 기록을 열어 보는 건 **일이 끝난 뒤** 되짚는 것이다. HITL은 **일이 일어나기 전에** 멈춰 세운다 |
| HITL | 수동 {% include term.html name="트리거" %} | 수동 트리거는 흐름을 **출발시킬지**를 사람이 정한다. HITL은 이미 출발한 흐름의 **중간**, 바꾸는 행동 직전에 사람이 허락한다 |
| HITL (이 글의 뜻) | HITL (머신러닝에서 쓰는 뜻) | 머신러닝에서는 사람이 데이터에 정답 표시를 달거나 모델 답에 피드백을 주는 일도 HITL이라 부른다. 이 글은 **실행 중간에 사람이 허락하는 멈춤 지점**만 다룬다 |
| HITL | 권한 줄이기 | 권한 줄이기는 위험한 도구를 **아예 주지 않는** 것이다. HITL은 도구는 주되 **쓸 때마다 묻는** 것이다. 둘을 함께 쓴다 |

## 5. 많이들 오해하는 지점

**ㄱ. "사람이 끼면 자동화가 아니다"**

사람이 모든 단계를 하는 게 아니다. 읽고, 정리하고, 초안을 만드는 일은 기계가 하고, 사람은 바꾸는 행동 앞의 한 지점에서만 본다. 노드 4에서도 연결 확인과 `wf.json` 작성은 에이전트가 했고, 나는 생성 직전에 한 번 확인했다. 자동화의 대부분은 그대로 두고, 되돌리기 어려운 곳에만 사람을 세운다.

**ㄴ. "승인 단계를 많이 걸수록 안전하다"**

모든 칸마다 허락을 물으면 사람이 매번 꼼꼼히 읽기 어렵다. 같은 질문이 계속 오면 내용을 보지 않고 "진행"을 누르게 되기 쉽고, 그러면 멈춤 지점은 있으나 마나다. 멈춤 지점은 적게, 꼭 필요한 곳에만 둬야 사람이 그때만큼은 제대로 읽는다.

**ㄷ. "허락 버튼을 누르면 할 일을 다 한 것이다"**

허락은 내용을 읽었다는 뜻이어야 한다. 노드 4의 승인이 의미가 있었던 건, 에이전트가 생성 전에 칸 이름·URL·연결을 보여 줬고 그걸 보고 답했기 때문이다. 무엇을 하려는지 보여 주지 않는 승인 요청이라면, 승인하기 전에 "무엇을 만들 건지 먼저 보여 줘"라고 되묻는 것까지가 사람의 몫이다.
