## 한 줄 정의

> 모델에게 건네는 도구 하나의 사용 계약서. 이름, 하는 일, 쓰는 때와 안 쓰는 때, 인자, 반환, 실패 뒤 행동을 한 장에 적는다

---

## 1. 비유로 이해하기

쉬는 시간에 선생님이 반 친구 지호에게 매점 심부름을 맡긴다. 말로 "우유 좀 사 와"라고만 하면 지호는 여러 가지를 혼자 짐작해야 한다. 어떤 우유인지, 돈은 얼마까지 써도 되는지, 매점이 닫혔으면 어떻게 할지. 그래서 선생님은 작은 카드 한 장을 쥐여 준다.

- **이름**: 우유 사 오기
- **하는 일**: 매점에서 우유 한 개를 사 온다. 다른 물건은 사지 않는다.
- **언제 하나**: 선생님이 부탁했을 때만. 매점 문이 닫혀 있으면 가지 않는다.
- **무엇을 들고 가나**: 흰우유와 초코우유 중 하나, 돈은 1,000원.
- **무엇을 들고 오나**: 우유와 거스름돈만. 매점 장부를 통째로 들고 오지 않는다.
- **잘 안 되면**: 품절이면 다른 것을 사지 말고 돌아와서 무엇으로 할지 묻는다.

카드 덕분에 지호는 짐작할 일이 거의 없다. 그런데 카드에 빈 줄이 하나라도 있으면, 지호는 그 줄을 자기 생각으로 채운다. "품절이면?" 줄이 비어 있었다면 바나나우유를 대신 사 왔을지도 모른다.

실제로는, 에이전트의 모델이 이 지호다. 모델은 도구를 직접 열어 보지 못하고 하네스가 건넨 **설명 글**만 읽고서 어떤 도구를 부를지, 어떤 값을 넣을지 정한다. 그 설명을 여섯 칸으로 빠짐없이 적은 문서가 도구 정의서다.

## 2. 왜 필요한가

### 모델이 읽는 것은 정의서뿐이다

도구를 에이전트에 붙이면, 에이전트 앱과 모델 서버가 그 도구의 이름과 설명과 인자 {% include term.html name="스키마" %}를 글자로 바꿔 모델의 입력에 함께 넣는다. 형식은 보통 {% include term.html name="JSON" %}이다. 모델 입장에서 도구 설명은 시스템 지시와 같은 입력 안에 놓인 **또 하나의 지시문**이다. 그러니 정의서 문장 하나를 고치는 것은 모델에게 주는 지시를 고치는 것과 같다.

{% include term.html name="MCP" %} 서버를 붙일 때도 같다. 서버가 "내 도구는 이렇게 생겼다"고 알려 주는 그 내용이 도구 정의다. MCP 사양에서 도구 하나는 이름(`name`), 설명(`description`), 입력 스키마(`inputSchema`)를 담는다. 수업에서는 여기에 반환 형식과 실패 뒤 행동까지 더해 여섯 칸으로 쓰자고 했다.

### 여섯 칸이 각각 막는 것

내 실습의 재고 조회 도구 `get_inventory` 정의서로 칸마다 무엇을 막는지 정리하면 이렇다.

| 칸 | 내가 쓴 내용 | 비어 있으면 생기는 일 |
| --- | --- | --- |
| 이름 | `get_inventory` | 이름만 보고 무엇을 하는 도구인지 알 수 없다. 재고를 **바꾸는** 도구와 헷갈린다 |
| 하는 일 한 문장 | 허용된 창고 한 곳에서 상품 하나의 지금 쓸 수 있는 재고 수량을 읽기만 하며, 수량은 바꾸지 않는다 | 한 도구가 여러 일을 떠안는다. 문장이 길어지면 두 동작이 섞였다는 신호다 |
| 쓰는 때와 쓰지 않는 때 | 상품 코드와 허용 창고가 둘 다 분명할 때 쓴다 / 수량 변경, 창고 미지정, 모호한 창고, 주문·배송 질문에는 쓰지 않는다 | 비슷한 도구가 여럿이면 모델이 그 사이에서 헷갈려 엉뚱한 쪽을 부른다 |
| 인자 스키마 | `sku` 문자열 3~32자 필수 / `warehouse_id`는 `SEOUL-01`·`BUSAN-02` 중 하나 | 모델이 값을 지어낸다. 고를 수 있는 값이 정해져 있으면 그 목록을 그대로 적어 둔다 |
| 반환 형식 | `sku`, `warehouse_id`, `available_quantity`, `checked_at` 네 가지만 | 원가처럼 고객에게 말하면 안 되는 값이 모델 눈앞에 놓이고, 답에 섞여 나올 수 있다 |
| 실패 정의와 뒤 행동 | `WAREHOUSE_NOT_ALLOWED` → 허용 창고를 묻는다 / `TEMPORARY_ERROR` → 재시도 한 번 뒤 중단 | 오류가 나도 다음에 할 일을 몰라 똑같이 다시 부르거나 수량을 짐작해 말한다 |

여섯 칸을 한 표에 모아 두면 좋은 점이 하나 더 있다. 나중에 실패 기록을 볼 때 "이건 몇 번 칸 문제"라고 번호로 가리킬 수 있다.

### 칸이 다 차 있어도 조용히 틀린다

수업의 경계 사례 요청은 "부산 3번 창고"였고, 노드 본문은 여기서 허용되지 않은 창고 오류가 날 것으로 보았다(강사 메모는 모델이 `BUSAN-02`로 바꿔 버릴 수도 있다고 덧붙였다). 나도 정의서를 쓰며 그 실패를 내 사례로 적어 두었다. 모델이 이 이름을 허용 목록에 있는 `BUSAN-02`로 멋대로 바꿔 조회하는 경우다. 실제로 돌려 보니 그대로 일어났다(작은 모델 `qwen3.5:2b`, 온도 0).

```text
== 요청 ==
부산 3번 창고의 A-17 재고를 알려 줘

== [1] 모델의 요청 ==
[('get_inventory', {'sku': 'A-17', 'warehouse_id': 'BUSAN-02'})]

== [2] 하네스의 실행 결과 ==
{"sku": "A-17", "warehouse_id": "BUSAN-02", "available_quantity": 7, "checked_at": "2026-08-27T01:55:00+09:00"}

== [3] 결과를 읽은 최종 답 ==
승인된 창고 (BUSAN-02) 에서 상품 A-17 의 현재 가용 재고는 **7**개입니다.
```

`BUSAN-02`는 허용 목록 안의 값이라 스키마 검사도, 하네스의 허용 목록 검사도 통과했다. 오류는 하나도 나지 않았다. "대구 창고"를 물었을 때도 같은 일이 생겼다(trace-06). 겉으로는 멀쩡한 답이지만 사용자가 물은 창고의 재고가 아니다. 심부름 카드에 없는 딸기우유를 부탁받고 초코우유를 사 온 셈이다.

### 고칠 칸은 기록을 보고 고른다

처음에는 "실패 뒤 행동" 칸에 "`WAREHOUSE_NOT_ALLOWED`이면 수량을 말하지 말고 SEOUL-01과 BUSAN-02 중 어느 창고인지 물어야 합니다"를 더했다(trace-03). 결과는 그대로였다. 오류가 아예 나지 않았으니 그 문장이 쓰일 자리가 없었다.

대신 **인자 설명** 한 문장을 바꿨다. "`SEOUL-01` 또는 `BUSAN-02`만 넣습니다"를 "사용자가 말한 창고 코드를 넣습니다"로 바꾸자, 모델은 `대구창고`를 그대로 넣었고 하네스가 막았으며 모델은 수량 없이 되물었다(06 → 08).

트레이스는 세 단계로 나뉜다. [1] 모델이 도구를 부르는 순간, [2] 하네스가 실행한 결과, [3] 결과를 읽은 답. 실패가 [1]에서 생겼다면 실패 뒤 행동 칸을 고쳐 봐야 소용이 없다. 정의서의 여섯 칸과 트레이스의 세 단계를 함께 놓고 봐야 고칠 칸이 보인다.

### 정의서로 못 막는 것은 하네스로 옮긴다

설명문에 "창고 이름이 하나의 코드로만 대응되지 않으면 부르지 말고 물어야 한다"를 넣어도 2B 모델은 따르지 못했다(trace-04·09). 허용 코드를 설명에서 빼면 억지 맞추기는 사라졌지만 "부산"처럼 바꿔도 되는 이름까지 거절했고(trace-14), 다시 넣으면 "부산 3번"을 또 `BUSAN-02`로 바꿨다(trace-18).

그래서 내 정의서의 설계를 이렇게 바꿨다. 인자 `warehouse_id`는 "사용자가 말한 창고 이름이나 코드를 그대로 넣는다"로 하고, 이름을 코드로 바꾸는 일과 모호한 이름을 거절하는 일은 {% include term.html name="하네스" %}가 정해진 대응표로 맡는다. 정의서는 모델에게 주는 안내이고, 실제로 막는 일은 코드가 해야 한다는 뜻이다. (이번 실습에서는 설계만 바꾸고 구현하지 않았다.)

### 정의서는 채점 기준이 된다

정의서를 쓰고 나면 실행 전에 통과 기준을 정할 수 있다. 스키마 준수, 호출 성공, 결과 사용 가능성, 실패 처리. 그런데 위 실험을 채점해 보니 "스키마 준수"만 보면 가장 위험한 실행(02·06·18)이 통과로, 되물은 안전한 실행(08·12)이 실패로 보였다. 그래서 기준을 하나 더했다.

| 기준 | 통과의 정의 |
| --- | --- |
| 의미 일치 (실험 뒤 추가) | 호출 인자의 창고·상품이 사용자가 말한 대상과 같다(허용 목록 안의 다른 값으로 바꾸지 않았다) |

## 3. 어디서 만났나

**22회차**는 "도구를 준다는 것"이 무엇인지 다뤘다. 도구 설명도 모델에게는 지시문이라는 데서 출발해, 재고 조회 도구 하나의 계약을 여섯 칸으로 쓰고, 그 정의서를 기준으로 실패 사례가 어느 칸에서 왔는지 되짚는 실습을 했다. 이어서 같은 도구를 실제로 돌려 경계 사례 18개를 기록하고 채점했다. 위 2절의 "부산 3번" 기록이 그 결과다.

[22회차 — 도구를 준다는 것]({{ site.baseurl }}/2026/10/12/tool-contract-and-harness/)

과제에서는 주문제작 반려동물 용품 가게의 반품·교환 안내 에이전트를 설계하며 도구 네 개(정책 검색, 주문 상태 조회, 반품 가능 판정, 반품 신청)의 정의서를 같은 여섯 칸으로 썼다. 설계 문서는 공개 저장소 [songyee-ai/my-service-agent](https://github.com/songyee-ai/my-service-agent)의 `design-packet.md`에 있다.

## 4. 헷갈리는 개념

| 이 용어 | 비슷하지만 다른 것 | 차이 |
| --- | --- | --- |
| 도구 정의서 | 스키마 | 스키마는 정의서의 **한 칸**(인자의 모양)이다. 스키마만으로는 언제 쓰는지, 실패하면 무엇을 하는지 알 수 없다 |
| 도구 정의서 | 함수 코드 | 함수 코드는 **실제로 일하는 몸**이고, 정의서는 모델에게 보여 주는 **사용 설명**이다. 모델은 코드를 보지 못하고 정의서만 본다 |
| 도구 정의서 | MCP | MCP는 정의서를 서버에서 에이전트로 **전달하는 규격**이다. 정의서를 잘 쓰는 일은 MCP를 쓰든 안 쓰든 내 몫이다 |
| 도구 정의서 | API 문서 | API 문서는 **사람 개발자**가 읽고 코드를 짠다. 도구 정의서는 **모델**이 읽고 그 자리에서 호출을 고른다. 그래서 "쓰지 않는 때"처럼 판단을 돕는 칸이 중요하다 |

## 5. 많이들 오해하는 지점

**ㄱ. "스키마 검사를 통과했으면 제대로 부른 것이다"**

스키마는 **모양**만 본다. "부산 3번 창고"를 `BUSAN-02`로 바꾼 호출은 모양이 완벽했다. 사용자가 말한 대상과 같은지는 따로 봐야 해서, 나는 채점 기준에 "의미 일치"를 더했다.

**ㄴ. "실패 뒤 행동 칸을 채우면 실패가 줄어든다"**

그 칸은 **오류가 났을 때** 쓰인다. 내 실험에서 오류 없이 지나간 억지 맞추기(02 → 03)에는 효과가 없었고, 오류가 실제로 난 경우(10 → 11, 14 → 16)에만 답이 달라졌다. 실패가 호출 전에 생겼는지, 오류 뒤에 생겼는지부터 기록에서 확인해야 한다.

**ㄷ. "설명문에 규칙을 적어 두면 모델이 지킨다"**

설명문은 안내다. 내 실험의 2B 모델은 "부르지 말고 물어라"를 따르지 못했다. 다만 이건 2B 모델로 실험마다 한 번씩 돌린 결과이고, 큰 모델은 다르게 행동할 수 있다. 어느 모델이든 꼭 지켜야 하는 규칙(허용 창고, 쓰기 권한)은 설명문에만 두지 말고 하네스와 서버에서 다시 검사한다.
