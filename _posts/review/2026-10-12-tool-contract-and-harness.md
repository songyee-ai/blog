## 한 줄 요약

> 모델은 도구를 실행하지 않고 호출 요청만 쓴다. 그 요청은 도구 설명을 읽고 고른 것이라, 설명이 곧 프롬프트다. 가장 위험한 실패는 오류 없이 그럴듯하게 지나갔다.

## 1. 오늘 배운 것

20회차에는 지시를, 21회차에는 맥락을 봤다. 오늘은 모델이 **바깥 세상에 손을 뻗는 길**인 도구를 봤다. 재고 조회 도구 하나를 놓고 계약을 쓰고, 직접 돌려 보고, 남이 만든 검색 도구({% include term.html name="Qdrant" %})를 {% include term.html name="MCP" %}로 붙여 보는 실습 위주의 하루였다. 마지막에는 서비스 안내 챗봇을 설계하는 과제를 냈다.

> **오늘의 핵심 한 문장**
> 도구 하나를 붙이면 정할 것이 넷 생긴다. **언제 쓰는지(계약), 무엇을 했는지 남길 곳(기록), 어디까지 허락할지(권한), 언제 손을 뗄지(중단).** 하나라도 비면 답은 그럴듯해도 믿을 수 없다.

| 순서 | 무엇에 답하는가 |
| --- | --- |
| 도구 호출의 한 바퀴 | 모델은 도구를 직접 실행하나 |
| 설명은 모델이 읽는 지시 | 도구 설명은 어디로 들어가나 |
| 도구 정의서 여섯 칸 | 도구 계약에는 무엇을 적나 |
| 최소 하네스의 여섯 지점 | 도구 바깥에는 무엇이 필요한가 |
| 권한과 신뢰 경계 | 읽기와 바꾸기를 어떻게 나누나 |
| 전후 판정과 회귀 | 고친 게 정말 나아졌는지 어떻게 아나 |
| 네 가지 안티패턴 | 자주 빠지는 나쁜 설계는 무엇인가 |
| 왜 필요한가 | 앞으로 무엇을 먼저 보게 되나 |

### 1-1. 도구 호출의 한 바퀴 — 손님은 주문서만 쓴다

식당에서 손님은 주문서에 "김치찌개 1, 덜 맵게"라고 적을 뿐, 직접 부엌에 들어가 요리하지 않는다. 주방이 주문서를 확인하고, 요리하고, 접시를 손님 앞에 놓는다. 손님은 나온 음식을 보고 "맛있다"고 말한다. 그래서 실제로는 **모델은 "이 도구를 이 인자로 불러 달라"는 요청만 쓰고, 실제 실행은 {% include term.html name="하네스" %}가 맡는다.** 하네스는 그 도구가 허락된 것인지, 인자 모양이 맞는지 확인하고 실행한 뒤 결과를 다시 모델에게 넣어 준다.

```text
[1] 모델의 요청      get_inventory(sku='A-17', warehouse_id='BUSAN-02')
[2] 하네스의 실행    {"sku": "A-17", "warehouse_id": "BUSAN-02", "available_quantity": 7, "checked_at": "2026-08-27T01:55:00+09:00"}
[3] 결과를 읽은 답   승인된 창고 (BUSAN-02) 에서 상품 A-17 의 현재 가용 재고는 7개입니다.
```

이 한 바퀴에서 실패가 일어날 수 있는 순간은 셋이다.

| 순간 | 식당으로 치면 | 도구로 치면 |
| --- | --- | --- |
| 잘못 고름 | 찌개 대신 볶음밥을 주문 | [1]에서 엉뚱한 도구나 엉뚱한 인자를 고름 |
| 잘못 읽음 | 덜 맵게 해 달라고 했는데 매운 걸 보고도 "덜 맵다"고 함 | [2]의 수량·창고·시각을 [3]에서 다르게 말함 |
| 같은 실수 반복 | 품절이라는데 같은 메뉴를 계속 주문 | 실패한 호출을 기록·판정하지 않아 같은 요청을 또 보냄 |

비슷하게 들리는 네 낱말도 식당 그림에 놓으면 갈린다. 메뉴를 고르는 손님의 머리가 모델이고, 손님이 "점심 해결"이라는 목적을 갖고 주문부터 계산까지 해내면 에이전트다. 주문서를 받아 확인하고 요리해 내오는 주방이 하네스이고, 반찬을 더 시키고 또 받는 되풀이가 루프다. 실패가 어느 층에서 났는지 가르려면 이 낱말부터 섞지 않아야 한다.

### 1-2. 도구 설명은 모델이 읽는 지시다

자판기 버튼 옆에 붙은 작은 설명 스티커를 떠올리면 된다. 버튼에 "콜라"만 적혀 있으면 헷갈리지 않지만, "음료 2"라고만 적혀 있으면 아무거나 누르게 된다. 그래서 실제로는 **도구의 이름과 설명 문장이 그대로 모델 입력에 들어가고, 모델은 그 문장을 읽고 어떤 도구를 누를지 고른다.**

노드의 실측 랩이 이걸 숫자로 보여 줬다. 코랩 연결 도구 하나를 모델에 붙이고 요청을 보냈을 때 서버가 읽은 입력은 289토큰이었다. 같은 내용을 모델의 채팅 템플릿으로 직접 글자로 만들어 보내니 288토큰이었다. 거의 같다는 건, 도구 설명이 따로 특별한 통로로 가는 게 아니라 **system 블록 안의 평범한 글**로 들어간다는 뜻이다. 노드는 이걸 "계약을 쓰는 일은 곧 프롬프트를 쓰는 일"이라고 정리했다.

도구를 모델에게 건네는 방식도 변해 왔다.

| 시기 | 방식 | 남은 문제 |
| --- | --- | --- |
| 초기 | 시스템 프롬프트에 사용법을 글로 적고, 모델이 쓴 `Action: 검색` 같은 문장을 개발자가 직접 해석({% include term.html name="ReAct" %} 계열) | 표기가 제각각이라 다른 실행기가 읽는다는 보장이 없다 |
| 2023~ | API가 도구 선언과 호출 구조를 정해 준다 (OpenAI function calling, Anthropic tool use) | 앱 M개 × 도구 N개를 따로 이어야 한다 |
| 2024.11~ | MCP — 도구 서버와 에이전트를 같은 규약으로 잇는다 | 인증·권한·운영은 여전히 따로 챙겨야 한다 |

### 1-3. 도구 정의서 여섯 칸

심부름을 맡길 때 "가게 가서 사 와"만 적으면 무엇을, 어느 가게에서, 돈이 모자라면 어떻게 할지가 비어 있다. 그래서 실제로는 **도구 하나마다 여섯 칸을 채운 {% include term.html name="도구 정의서" %}를 쓴다.**

| 칸 | 정하는 것 | 비어 있으면 |
| --- | --- | --- |
| 이름 | 동사+대상 (`get_inventory`) | `process_data`처럼 흐릿하면 무엇에 쓰는지 짐작해야 한다 |
| 하는 일 한 문장 | 도구 하나에 동작 하나 | 조회와 변경이 한 도구에 섞이면 읽으려다 바꿔 버릴 수 있다 |
| 쓰는 때·안 쓰는 때 | 언제 부르고 언제 부르지 않나 | 창고를 말하지 않은 질문에도 일단 불러 본다 |
| 인자 {% include term.html name="스키마" %} | 필수 여부, 자료형, 허용값 | 모델이 빈칸을 지어낸다 (2-4의 `collection_name`) |
| 반환 형식 | 답의 근거가 될 필드만 | 내부 원가 같은 값이 답에 따라 나온다 |
| 실패와 뒤 행동 | 실패마다 재시도·질문·중단 중 무엇을 할지 | 오류가 나도 무엇을 할지 몰라 같은 호출을 다시 보낸다 |

실습 1에서 이 표로 재고 조회 도구를 직접 썼다. 내가 생각한 실패 사례도 하나 넣었다. 사용자가 "부산 3번 창고"라고 했는데 모델이 허용 목록에 있는 `BUSAN-02`로 바꿔 조회하는 경우다. 이게 실습 2에서 실제로 일어났다(2-3).

### 1-4. 최소 하네스의 여섯 지점

자전거는 페달만 있다고 탈 수 없다. 핸들, 브레이크, 기어, 바퀴가 함께 있어야 원하는 곳에 가고 멈출 수 있다. 그래서 실제로는 **도구 하나의 설명만 잘 써서는 부족하고, 도구가 돌아가는 자리 전체를 여섯 지점으로 설계한다.**

| 지점 | 정하는 것 | 빠지면 |
| --- | --- | --- |
| ① 시스템 지시 | 역할, 우선순위, 금지 행동 | 조회 없이 그럴듯하게 짐작해 답한다 |
| ② 도구(계약) | 입력·반환·실패·사용 경계 | 실습 2처럼 허용 목록에 맞춰 엉뚱한 창고를 넣는다 |
| ③ 권한 | 계약상 가능한 것 중 실제로 허락하는 범위 | 2-4처럼 허락하지 않은 명령까지 쓰인다 |
| ④ 실행 환경 | 폴더, 네트워크, 자격 증명, 시간·비용 한도 | 엉뚱한 파일을 읽거나 실패한 시도가 비용을 계속 쓴다 |
| ⑤ 관찰 | 도구 이름, 입력, 판정, 반환값, 후속 판단의 기록 | 트레이스가 없었다면 02→03이 왜 안 바뀌었는지 못 찾았다 |
| ⑥ 중단 | 멈출 조건과 사람에게 넘길 조건 | 같은 실패가 계속 되풀이된다 |

19회차의 "같은 모델, 다른 실행 조건"과 이어지는 이야기다. 노드는 약 100줄짜리 에이전트(mini-swe-agent)의 높은 점수를 예로 들며, 벤치마크 숫자는 모델 혼자가 아니라 **모델과 하네스를 묶은 결과**라고 설명했다.

### 1-5. 권한과 신뢰 경계 — 보는 열쇠와 바꾸는 열쇠

학급 사물함 열쇠를 반 친구 모두에게 나눠 주더라도, 출석부를 고칠 수 있는 열쇠는 선생님만 갖는다. 그래서 실제로는 **{% include term.html name="최소 권한" %} 원칙에 따라 읽는 도구와 바꾸는 도구를 나누고, 바꾸는 도구는 따로 승인을 거치게 한다.**

실습 2가 이걸 보여 줬다. 도구 설명에 "부산 3번이면 부르지 말고 물어라"를 적어도 모델은 따르지 않았고, 하네스의 허용 목록 검사는 `BUSAN-02`가 목록 안이라 그냥 통과시켰다. 설명은 부탁이고, 실제로 막는 건 하네스가 무엇을 검사하느냐다. 그래서 과제 설계에서는 주문 주인 확인, 판정 번호 일치, 고객의 확인 버튼 기록을 모델이 아니라 하네스가 검사하게 했다. 21회차에 본 {% include term.html name="프롬프트 인젝션" %} 방어 네 겹 가운데 **③ 최소 권한과 ④ 사람 승인**이 실제 행동 바로 앞에 남는 마지막 막이다. 되돌리기 어려운 일에는 {% include term.html name="게이트" %}를 두어 사람이 대상과 사유를 확인한 뒤에만 실행한다.

### 1-6. 전후 판정과 회귀 — 고친 뒤 예전 문제도 다시 푼다

수학 시험에서 틀린 문제를 고쳤는데, 새 공식을 쓰다 보니 원래 맞던 문제가 틀려 버리는 일이 있다. 그래서 실제로는 **계약을 하나 고치면 그 문제만이 아니라 예전 문항 전체를 다시 돌려, 맞던 게 틀려지지 않았는지(회귀) 확인한다.**

판정은 답이 얼마나 매끄러운지가 아니라 도구 단계마다 한다. 실습 2에서 내가 쓴 채점 칸은 이랬다.

| 채점 칸 | 확인할 곳 |
| --- | --- |
| 스키마 준수 | 호출 인자 |
| 호출 성공 | 도구 응답 |
| 결과 사용 | 최종 답의 수량·시각이 반환값과 같은가 |
| 실패 처리 | 물어야 할 때 수량을 말하지 않았는가 |
| 의미 일치 (실험 뒤 추가) | 인자가 사용자가 말한 대상과 같은가 |

"부산 3번"을 묻고 "재고 7개"를 들은 답은 문장으로는 멀쩡했다. 칸별로 나눠 보니 결과 사용, 실패 처리, 의미 일치에서 걸렸다(2-3).

### 1-7. 네 가지 안티패턴

{% include term.html name="안티패턴" %}은 자주 되풀이되는 나쁜 설계 습관이다. 오늘은 넷을 봤고, 각각 1-1의 실패 순간 하나를 특히 키운다.

| 안티패턴 | 학교에서 비슷한 장면 | 키우는 실패 |
| --- | --- | --- |
| 도구 남발 | 필통에 펜 서른 자루를 넣어 두면 정작 빨간 펜을 못 찾는다 | 잘못 고름 |
| 반환값 데이터 덤프 | 시험 범위를 물었는데 교과서 전체를 건넨다 | 잘못 읽음 |
| 권한 방치 | 모두에게 교무실 열쇠를 준다 | 세 실패 모두를 피해로 바꾼다 |
| 중단 없는 순환 | 안 열리는 문을 계속 같은 힘으로 민다 | 같은 실수 반복 |

### 1-8. 왜 필요한가

- **도구를 붙일 때** — 이름보다 "쓰는 때·안 쓰는 때"와 실패 뒤 행동부터 적는다. 남이 만든 도구라면 그 설명 문장부터 읽는다. 그 문장이 내 프롬프트에 들어온다.
- **실패를 볼 때** — 기록에서 실패가 [1] 부르기 전에 생겼는지, [3] 오류 뒤에 생겼는지부터 가린다. 고칠 칸이 다르다.
- **오류가 안 났을 때** — "오류 없음"은 "맞음"이 아니다. 인자가 사용자가 말한 대상과 같은지 본다.
- **고친 뒤에** — 고친 문항만 보지 않고 예전 문항 전체를 다시 돌린다.
- **꼭 막아야 할 때** — 설명문에 부탁하지 않고 하네스와 권한으로 막는다.

## 2. 실습 / 코드

실습 폴더(`training/1012_tool_lab`)는 깃 저장소가 아니라 이 절에 정리한다. 과제는 공개 저장소로 제출했다.

| 항목 | 값 |
| --- | --- |
| 환경 | WSL2 Ubuntu, Python 3.14.4, uv |
| 서버·모델 | {% include term.html name="Ollama" %} 0.40.1 (CPU), `qwen3.5:2b`, temperature 0, `reasoning=False` |
| 호출 | {% include term.html name="LangChain" %}의 `langchain-ollama`, `@tool` + `bind_tools` |

### 2-1. 실측 랩 — 도구 설명이 들어가는 자리 (해설만 읽음)

노드 2의 실측 랩은 직접 실행하지 않았다. 예시 답안의 해설과 강사 메모만 읽고 넘어갔다. 그래서 아래는 내가 돌린 결과가 아니라 노드에 실린 흐름이다.

1. MCP 서버(colab-mcp)에서 도구 정의를 받아 모델에게 넘길 JSON으로 출력한다. 영어 설명 문장이 JSON 안에 그대로 들어가 있다.
2. 모델에 "코랩을 브라우저로 연결해 줘"를 보내면 `tool_calls: [('open_colab_browser_connection', {})]`가 돌아온다. 모델은 요청만 쓰고, 코랩은 실제로 열리지 않는다. 이때 읽은 입력이 289토큰이다.
3. 모델 파일(GGUF)에서 채팅 템플릿을 꺼내 같은 입력을 직접 글자로 만든다. 도구 JSON이 system 블록 안 `<tools>` 칸에 들어가고, 그 아래 호출 형식 규칙과 사용자 질문이 붙는다. 이걸 그대로 보내면 288토큰이다.

강사 메모에서 하나를 따로 적어 뒀다. 노드의 정의로는 프롬프트를 조립하고 모델 응답을 해석하는 건 Ollama 같은 **모델 서버**의 일이고, 하네스는 그 뒤 "허용 목록 확인 → 인자 검사 → 실행 → 결과 재입력"을 맡는다. 하네스의 정의는 자료마다 조금씩 다르다.

실습 기록의 준비 메모에서 주의할 점도 하나 읽었다. PyPI에 같은 이름(`colab-mcp`)으로 올라간 다른 패키지(0.1.0)가 있어서, 구글 공식 저장소(`googlecolab/colab-mcp`)에서 받아야 한다. 이름만 보고 설치하면 엉뚱한 도구를 붙이게 된다.

### 2-2. 실습 1 — 재고 조회 도구 정의서

`get_inventory`의 여섯 칸을 채웠다. 1-3의 표에서 몇 칸을 더 구체적으로 적었다.

- **쓰는 때·안 쓰는 때** — 창고 두 곳을 함께 물으면 창고마다 따로 부른다. 수량 변경 요청, 창고를 말하지 않은 요청, 허용 목록 밖이거나 어느 코드인지 분명하지 않은 창고에는 부르지 않는다.
- **인자** — `warehouse_id`는 `SEOUL-01`·`BUSAN-02` 중 하나. 창고 이름은 "부산"→`BUSAN-02`처럼 하나로만 대응될 때만 바꾸고, "부산 3번"처럼 분명하지 않으면 바꾸지 않고 묻는다.
- **실패와 뒤 행동** — `WAREHOUSE_NOT_ALLOWED`·`INVALID_SKU`·`MISSING_ARGUMENT`는 질문, `TEMPORARY_ERROR`는 한 번 재시도 뒤 중단. 실패마다 "하지 말 것"도 적었다(같은 코드로 다시 부르기, 다른 창고 수량을 대신 답하기 등).

노드 코드가 실제로 돌려주는 오류는 `WAREHOUSE_NOT_ALLOWED` 하나뿐이다. `INVALID_SKU`는 노드의 도구 설명문에만 나오고, `MISSING_ARGUMENT`·`TEMPORARY_ERROR`는 설계상 붙인 이름이다.

### 2-3. 실습 2 — 재고 도구를 돌리고, 한 곳씩 바꿔 보기

노드 원본 코드는 노드에 실린 결과와 같았다. `get_inventory(A-17, BUSAN-02)` → 재고 7 → "가용 재고는 7개"(답의 7에 굵은 글씨 표시만 붙음). 이것을 실행 기록(트레이스) `trace-01`로 남기고, 요청 문장과 도구 설명문을 **한 번에 한 곳만** 바꿔 가며 17번을 더 돌렸다.

| 설명문 | 원본과 다른 점 |
| --- | --- |
| original | 노드 원본 ("warehouse_id에는 SEOUL-01 또는 BUSAN-02만 넣습니다") |
| fail_ask | + 허용 밖이면 수량을 말하지 말고 어느 창고인지 물어라 |
| name_rule | + 창고 이름이 코드 하나로만 대응되지 않으면 부르지 말고 물어라 |
| with_time | + 답할 때 확인 시각도 알려라 |
| no_list | 허용 목록 문장을 "사용자가 말한 창고 코드를 넣는다"로 바꿈 |

결과에서 가장 크게 남은 건 이 표다.

| trace | 설명문 | 요청 | 모델이 넣은 창고 | 스키마 준수 | 의미 일치 |
| --- | --- | --- | --- | --- | --- |
| 02 | original | 부산 3번 창고 | `BUSAN-02` | O | **X** |
| 06 | original | 대구 창고 | `BUSAN-02` | O | **X** |
| 08 | no_list | 대구 창고 | `대구창고` | X | O |
| 12 | no_list | 부산 3번 창고 | `부산 3 번 창고` | X | O |
| 14 | no_list | 부산 창고 | `부산창고` | X | O |
| 18 | no_list + fail_ask | 부산 3번 창고 | `BUSAN-02` | O | **X** |

**가장 위험한 실패는 오류 없이 지나갔다.** "부산 3번 창고"도, "대구 창고"도 모델이 허용 목록 안의 `BUSAN-02`로 바꿔 불렀다. 값이 목록 안이니 하네스 검사도 통과했고, 답은 "가용 재고는 7개"였다. 그럴듯하지만 쓸 수 없는 답이다. 1-1의 "잘못 고름"이 도구가 아니라 **인자**에서 일어났다.

**고칠 칸은 실패 뒤 행동이 아니라 인자 설명이었다.** 노드가 예로 든 대로 "허용 밖이면 물어라"(fail_ask)를 더해 봤지만 02→03에서 변화가 없었다. 오류가 아예 안 났으니 그 문장이 쓰일 자리가 없었다. "부르지 말고 물어라"(name_rule)도 2B 모델은 따르지 못했다(04·09). 반대로 인자 설명에서 허용 코드 목록을 빼자(06→08) 모델이 "대구창고"를 그대로 넣었고, 하네스가 막았고, 모델이 되물었다.

```text
[1] get_inventory(sku='A-17', warehouse_id='대구창고')
[2] {"error": "WAREHOUSE_NOT_ALLOWED"}
[3] 죄송합니다. 대구창고가 승인된 창고 목록에 포함되어 있지 않아, 해당 창고의 가용 재고를 확인할 수 없습니다.
    다른 창고 코드를 알려주시면 다시 확인해 드리겠습니다.
```

**고치자 다른 곳이 깨졌다.** 목록을 빼니 "부산"처럼 바꿔도 되는 이름까지 거절했다(14). 그걸 고치려고 실패 뒤 행동 문장에 코드를 다시 넣자 12에서 되묻던 "부산 3번"을 18에서 다시 `BUSAN-02`로 억지로 바꿨다. 1-6의 회귀가 그대로 나왔다.

그래서 두 가지를 바꿨다.

1. **채점 기준에 "의미 일치"를 더했다.** "스키마 준수"만 보면 가장 위험한 02·06·18이 통과(O)이고, 가장 안전한 08·12가 실패(X)로 보인다. 인자가 사용자가 말한 대상과 같은지를 따로 본다.
2. **설계를 하네스 쪽으로 옮겼다.** 설명문만으로는 끝까지 막지 못했다. 창고 이름을 코드로 바꾸고 모호하면 거절하는 일은 모델이 아니라 하네스가 정해진 대응표로 맡는 게 맞다. 이번에는 설계만 하고 구현하지 않았다.

확인 시각을 답에 넣는 건 설명문 한 문장(with_time)으로 바로 해결됐다(01→15). 실험마다 한 번씩만 돌렸고 2B 모델 기준이다.

### 2-4. 실습 2 4단계 — Qdrant 검색 도구를 두 에이전트에 붙이기

남이 만든 검색 도구 서버(`mcp-server-qdrant`)를 Claude Code와 opencode에 노드 설정 그대로 붙이고, 같은 요청을 보냈다. 환불·배송·회원 등급에 관한 문장 세 개를 저장하고, "환불 기한이 어떻게 돼?"와 비슷한 문장을 찾아 달라는 요청이다.

| | Claude Code | opencode |
| --- | --- | --- |
| 버전·모델 | 2.1.296, 기본 모델 | 1.19.0, `opencode/big-pickle`(기본 무료) |
| 서버 연결 | 폴더의 `.mcp.json`을 사람이 한 번 승인해야 씀 | 바로 연결 |
| 호출 | 도구 검색으로 필요할 때 불러온 뒤, 설정 파일을 읽고 store ×3 → find ×1 | store ×3 → find ×1 |
| `collection_name` 인자 | `policies` (설정 파일을 읽어서 알아냄) | `memories` (짐작) |
| 검색 1위 | 환불 문장 | 환불 문장 |

같은 도구, 같은 질문인데 인자가 달랐다. 서버가 내놓은 도구 정의를 꺼내 보니 `collection_name`이 필수인데 기본값도 허용값도 없었다. 1-3 표에서 본 "인자 칸이 비면 모델이 빈칸을 지어낸다"가 남이 만든 도구에서도 그대로 일어났다.

그런데 진짜 원인은 더 앞에 있었다. 설치된 `mcp-server-qdrant` 0.8.1은 노드 설정에 적힌 `QDRANT_COLLECTION`, `EMBEDDER_PROVIDER`, `FASTEMBED_MODEL`을 읽지 않고 `COLLECTION_NAME`, `EMBEDDING_PROVIDER`, `EMBEDDING_MODEL`을 읽는다. 노드의 세 설정은 **오류 없이 무시**됐고, 실제 쓰인 임베딩 모델도 설정에 적은 것이 아닌 기본값(`all-MiniLM-L6-v2`)이었다. `COLLECTION_NAME=policies`를 주면 `collection_name` 인자가 도구 정의에서 아예 사라져 모델이 짐작할 자리가 없어지고, `QDRANT_READ_ONLY=true`를 주면 쓰기 도구(`qdrant-store`)도 빠진다. 2-3의 재고 실험과 같은 모양의 실패다. 설정이 틀렸다는 경고 없이 결과는 그럴듯하게 나왔다.

그 밖에 기록해 둔 것.

- **남이 쓴 설명이 내 프롬프트에 들어온다.** `qdrant-find` 설명에는 사용자의 개인 정보를 얻을 때 쓰라는 문장(`Get some personal information about the user`)도 들어 있었다. 붙이기 전에 그 도구의 설명을 읽어야 하는 이유다(1-5).
- **도구를 넣는 방식이 에이전트마다 달랐다.** Claude Code는 MCP 도구 설명을 처음부터 다 넣지 않고 필요할 때 검색해 불러왔다. 노드는 도구 설명이 세션을 시작할 때 컨텍스트 창에 자동으로 들어간다고 설명했는데, 지금 버전의 동작은 그와 달랐다. opencode는 첫 단계 입력이 10,355토큰으로, 지시와 도구 설명이 한꺼번에 들어갔다.
- **허용하지 않은 도구도 쓰였다.** Claude Code는 qdrant 두 도구만 허용했는데도, 기본으로 허용되는 읽기 명령(`ls`, `cat`)으로 설정 파일을 열어 봤다. 덕분에 맞는 이름을 찾았지만, 권한 관점에서는 적어 둘 일이다.

### 2-5. 과제 — 서비스 가이드 챗봇 설계

주문제작 반려견 옷·하네스·소품 가게(가상의 "꼬리옷장")의 반품·교환·환불 안내 챗봇을 설계했다. 코드는 짜지 않고, 무엇을 맡기고 무엇으로 판단할지를 문서로 적는 과제다.

[songyee-ai/my-service-agent](https://github.com/songyee-ai/my-service-agent) — README, 설계 패킷(`design-packet.md`), 실습 1·2 산출물(`my-agent/`)

| 도구 | 읽기/쓰기 | 하는 일 |
| --- | --- | --- |
| `search_return_policy` | 읽기 | 정책 조항 찾기 |
| `get_order_status` | 읽기 | 본인 주문 상태 보기 |
| `check_return_eligibility` | 읽기(판정만) | 지금 가능한 처리를 판정 |
| `create_return_request` | 쓰기(신청서만) | 판정이 허용한 처리의 신청서 작성. 고객 확인 뒤에만, 실제 처리는 담당자 승인 |

설계에서 실습 결과를 바로 가져다 쓴 곳이 둘 있다.

- **판정과 신청을 나눴다.** 판정 번호가 있어야만 신청할 수 있게 해서, 모델이 정책을 문장으로 해석해 판정 없이 신청하는 길을 막았다. 주문 주인 확인, 판정 번호 일치, 확인 버튼 기록은 모델이 아니라 하네스가 검사한다. 2-3에서 2B 모델이 허용값으로 억지로 맞추고 "부르지 말고 물어라"도 못 지킨 것이 근거다.
- **정책 검색을 Qdrant로 붙일 때의 설정을 정했다.** `COLLECTION_NAME`으로 묶음을 고정하고 `QDRANT_READ_ONLY=true`로 쓰기를 뺀다(2-4).

다음에 측정할 지점으로는 테스트 문항 8개를 실제 모델로 돌려 전후를 비교하는 것을 남겼다.
