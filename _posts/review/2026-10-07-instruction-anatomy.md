## 한 줄 요약

> 지시는 역할·과업·맥락·형식·제약 다섯 칸으로 나눠 쓰고, 결과를 보기 전에 채점 기준부터 정한다. 실패하면 그 기준에 걸린 칸 하나만 고쳐 같은 조건으로 다시 잰다.

---

## 1. 오늘 배운 것

19회차는 모델이 읽는 입력 전체를 넓게 봤다. 오늘은 그중 **지시 한 덩어리를 쪼개서 들여다봤다.** 지시를 어떤 칸으로 나눠 쓰는지, 모델이 왜 지시를 따르게 됐는지, 따랐는지를 무엇으로 재는지, 틀리면 어디부터 고치는지까지 이어졌다.

실습은 두 개를 직접 했다. 스텝 2는 작은 모델에 같은 질문을 말만 바꿔 보내 본 기초 실험이고, 스텝 6은 고객 문의 하나에 지시 세 개를 붙여 미리 정한 기준으로 채점한 실험이다. 두 실습 모두 **한 번만 돌렸으면 틀린 결론을 냈을 장면**이 있었다.

> **오늘의 핵심 한 문장**
> 지시가 "잘 먹혔다"는 느낌은 증거가 아니다. **기준을 먼저 적고, 여러 번 돌리고, 한 칸만 바꿔서** 비교해야 무엇이 효과였는지 말할 수 있다.

| 순서 | 무엇에 답하는가 |
| --- | --- |
| 지시의 다섯 칸 | 지시는 무엇으로 이루어지고, 한 칸이 비면 어떻게 틀리나 |
| 같은 질문, 다른 말투 | 말만 바꾸면 답의 무엇이 바뀌나 |
| 학습의 계보 | 모델은 왜 지시를 따르게 됐나 |
| 출처와 우선권 | 같은 문장도 어디에 있느냐에 따라 왜 다르게 읽히나 |
| 기법은 가설이다 | few-shot·역할·CoT는 언제 써야 하나 |
| 답의 모양과 재는 법 | 형식은 어떻게 약속하고, 결과는 무엇으로 재나 |
| 실패 다섯 유형 | 틀린 답을 보고 어디부터 고치나 |
| 왜 필요한가 | 앞으로 무엇을 다르게 하게 되나 |

### 1-1. 지시의 다섯 칸 — 한 칸이 비면 틀리는 방식도 다르다

엄마가 심부름 쪽지를 써 준다고 해 보자. "동생이 먹을 거니까(누구를 위해) 우유 한 통 사 와(할 일). 냉장고 옆 할인 전단지 보고(참고할 것) 영수증은 봉투에 넣어 와(가져올 모양). 저지방 말고, 돈이 모자라면 그냥 와(하지 말 것·모를 때)." 그래서 실제로는 **지시도 이 다섯 칸으로 나눠 쓸 수 있다.**

| 칸 | 정하는 것 | 비었을 때 생기는 일 |
| --- | --- | --- |
| 역할 | 누구 관점에서, 누가 읽을 답인가 | 내용은 맞는데 읽는 사람에게 안 맞는다 (손님에게 보낼 글이 내부 보고서처럼 나온다) |
| 과업 | 무엇을 하고, 어디서 끝나는가 | 모델이 할 일을 스스로 고른다 (정리해 달랬는데 감상문이 온다) |
| 맥락 | 판단에 쓸 자료와 그 범위 | 자료 대신 그럴듯한 일반 상식으로 채운다 |
| 형식 | 결과를 어떤 모양으로 넘기나 | 매번 모양이 달라 사람이 다시 옮겨 적는다 |
| 제약 | 하지 말 것, 길이, 모를 때 할 일 | 빈칸을 추측으로 메우거나 묻지 않은 것까지 덧붙인다 |

칸을 나누는 이유는 고칠 곳을 찾기 위해서다. 답이 엉뚱한 사람을 향하면 역할을, 모양이 흔들리면 형식을, 없는 사실을 지어내면 제약을 본다. 반대로 칸을 다 채운다고 좋아지는 것도 아니다. 조건이 많아지면 "짧게"와 "빠짐없이"처럼 서로 부딪히는 문장이 생기고, 그 다툼을 누가 정리할지가 새 문제가 된다.

세 회사의 공식 안내도 칸 이름만 다를 뿐 방향이 같았다. 수업 자료에 적힌 요약을 내 메모로 옮기면 이렇다.

| 회사 문서 | 강조하는 것 |
| --- | --- |
| Anthropic | 성공 기준을 먼저 정하고, 경험적으로 시험해 본다 |
| OpenAI | 지시·예시·맥락을 나눠 쓰고, 평가와 함께 다룬다 |
| Google | 목표를 직접 쓰고, 필요한 정보·제약·출력 형식을 밝힌다 |

셋 다 "잘 쓰는 문장"보다 **나눠 쓰기와 재 보기**를 앞세운다. 스텝 6이 이 방식대로 진행됐다. 기준을 먼저 적고, 칸을 하나씩 더해 가며 쟀다.

### 1-2. 같은 질문, 다른 말투 — 모양은 확실히 바뀌고, 정답은 따로 본다

받아쓰기 시험에서 글씨를 아무리 반듯하게 써도 틀린 글자는 틀린 것이다. 그래서 실제로는 **"지시한 모양을 지켰나"와 "내용이 맞나"를 따로 채점**해야 한다. 수업 자료의 실측과 내 실습(2-1) 모두 이 둘이 자주 갈렸다. {% include term.html name="JSON" %} 배열로 달라고 하자 모양은 지켰는데, 안에 든 강 이름이 가짜였다.

말을 바꾸는 것 말고 **생성 설정**도 답을 바꾼다. 모델은 다음 {% include term.html name="토큰" %}을 고를 때 후보마다 점수({% include term.html name="로짓" %})를 매기고, 이를 {% include term.html name="소프트맥스" %}로 확률로 바꾼 뒤 하나를 뽑는다. {% include term.html name="temperature" %}는 확률로 바꾸기 전에 점수를 나누는 값이다.

| 후보 점수 2 / 1 / 0 | 1등 | 2등 | 3등 |
| --- | --- | --- | --- |
| temperature 0.5 (점수 4 / 2 / 0) | 0.87 | 0.12 | 0.02 |
| temperature 1 (그대로) | 0.67 | 0.24 | 0.09 |
| temperature 2 (점수 1 / 0.5 / 0) | 0.51 | 0.31 | 0.19 |

값이 낮으면 1등이 거의 다 가져가고, 높으면 고르게 퍼진다. 메모의 "temperature가 높을수록 같은 프롬프트에도 문장이 달라진다"와 같은 이야기다. {% include term.html name="top_k/top_p" %}는 뽑기 전에 후보 목록 자체를 잘라 내는 손잡이다. 중요한 점은 이 손잡이들이 **순위를 바꾸지 못한다**는 것이다. 모델이 틀린 답에 1등 점수를 줬다면, 온도를 낮출수록 그 틀린 답이 더 꼬박꼬박 나온다.

메모에도 "실험할 때는 환경 설정까지 적는다"가 있다. 모델 이름, 서버, thinking 여부, temperature, 반복 횟수를 같이 남기지 않으면 결과 차이가 지시 때문인지 설정 때문인지 가를 수 없다. 호출 도구마다 열어 주는 설정도 다르다. 스텝 6에서 쓴 Claude Agent {% include term.html name="SDK" %} 경로는 temperature를 정할 수 없었다.

### 1-3. 학습의 계보 — 모델은 왜 지시를 따르게 됐나

책을 엄청 많이 읽은 아이가 있다. 문장 뒤에 올 말은 기막히게 맞히지만, "이거 해 줘"라고 하면 그 문장 다음에 올 법한 이야기를 이어 쓸 뿐 심부름을 하지는 않는다. 그래서 실제로는 **다음 말 맞히기만 배운 사전학습 모델(base LM)은 지시를 '수행'하도록 배운 적이 없다.**

그 뒤에 붙는 단계가 지시를 따르는 습관을 만든다.

| 단계 | 무엇으로 배우나 | 무엇이 바뀌나 |
| --- | --- | --- |
| 사전학습 | 엄청난 양의 글에서 다음 토큰 맞히기 | 언어와 넓은 지식 |
| {% include term.html name="SFT" %} | 사람이 쓴 "지시 + 모범 답" 짝 | 요청을 끝까지 수행하는 기본 습관 |
| 선호 학습 ({% include term.html name="RLHF" %}, {% include term.html name="DPO" %} 등) | 두 답 중 사람이 더 낫다고 고른 쪽 | 말투, 거절 방식, 도움 되는 정도 |
| 대화 템플릿 | 역할 표시 토큰과 순서 | system·user·assistant 구분을 읽는 방식 |

InstructGPT는 SFT 다음에 사람이 매긴 순위로 보상 모델을 만들고 강화학습을 돌렸다. FLAN은 여러 과업을 지시문 모양으로 바꿔 미세조정하면 처음 보는 과업의 지시에도 어느 정도 옮겨 간다는 걸 보였다. DPO는 보상 모델과 강화학습 단계를 빼고 "고른 답 / 안 고른 답" 짝으로 바로 조정한다. GRPO는 한 문제에 답을 여러 개 만들어 그 안에서 상대적으로 점수를 비교한다.

설계하는 쪽에서 남길 판단은 세 가지였다. 모델이나 대화 템플릿({% include term.html name="Hugging Face" %}의 chat template 같은 것)을 바꾸면 **잘 되던 지시도 다시 재야 한다.** 형식이 틀렸을 때 지시문 한 줄만 탓하지 않는다. 그리고 모델이 거절을 잘하는 것처럼 보여도 **권한 검사는 프로그램이 따로 한다.**

### 1-4. 출처와 우선권 — 같은 문장도 놓인 자리가 다르다

교실 칠판에 선생님이 "오늘 숙제 없음"이라고 쓴 것과, 복도 바닥에 떨어진 쪽지에 같은 말이 적힌 것은 무게가 다르다. 그래서 실제로는 **같은 문장도 누가 어느 {% include term.html name="메시지 역할" %}에 넣었느냐에 따라 규칙이 되기도 하고 그냥 자료가 되기도 한다.**

system·developer·user를 따로 두는 API라면 서비스 규칙(system) > 제품 업무 규칙(developer) > 이번 요청(user) > 자료 순으로 생각할 수 있다. 첨부 파일이나 검색 결과 안에 "앞 규칙을 무시해" 같은 문장이 있어도 그건 **분석할 데이터**다. 이 경계를 노리는 공격이 19회차에 본 {% include term.html name="프롬프트 인젝션" %}이다.

우선권도 정해 놓고 끝이 아니라 **시험해야 한다.** 정상 요청만 넣지 말고, 사용자가 직접 규칙에 반하는 요청을 할 때, 문서 속에 명령이 숨어 있을 때, 대화가 길어진 뒤에 충돌이 올 때를 각각 넣어 본다. 모델이 "그건 못 해요"라고 답해도, 프로그램에서 그 기능이 실제로 막혀 있는지는 따로 확인해야 한다.

### 1-5. 기법은 가설이다 — 이름보다 "무엇이 줄 것인가"를 먼저 쓴다

"이 약 먹으면 낫는다"는 말은 먹어 보기 전엔 예상일 뿐이다. 그래서 실제로는 **{% include term.html name="퓨샷" %}, 역할 부여, {% include term.html name="CoT" %}도 "이렇게 하면 이 실패가 줄 것"이라는 가설로 적고 비교해서 확인한다.**

| 기법 | 언제 후보가 되나 | 무엇과 비교하나 |
| --- | --- | --- |
| few-shot | 범주의 경계를 말로 설명하기 어려울 때 | 예시 0개({% include term.html name="제로샷" %}) 기준선 |
| 역할 | 누가 읽고 어디까지 책임질지 흔들릴 때 | 역할 문장만 뺀 같은 지시 |
| CoT·생각 설정 | 여러 단계를 이어야 하는 문제 | 답만 요구한 기준선, 낮은/높은 effort |

비교할 때는 모델·입력·온도·채점 기준을 고정하고 한 조건만 바꾼다. 예시는 너무 많거나 한쪽으로 치우치면 겉모습만 따라 하게 만들 수 있고, 긴 풀이는 틀린 결론도 그럴듯해 보이게 할 수 있다. 여러 번 뽑아 다수결하는 {% include term.html name="셀프 컨시스턴시" %}도 마찬가지로, "한 답 안에서 세 번 풀어 봐"라고 부탁하는 것과는 다른 조건이라 따로 비교해야 한다. 수업 자료는 2023년 미국 법원이 존재하지 않는 판례를 인용한 서면에 제재를 내린 사건(Mata v. Avianca)을 들었다. "실재하는 판례만 써"라는 지시는 원문 확인을 대신하지 못한다.

### 1-6. 답의 모양과 재는 자 — 모양은 스키마로, 내용은 지표로

시험지에 답란 칸이 그어져 있으면 채점하는 사람이 답을 찾느라 헤매지 않는다. 그래서 실제로는 **프로그램이 받아 쓸 답이면 필드·자료형·빈값 표현을 {% include term.html name="스키마" %}로 미리 약속한다.** 약속을 지켰는지는 validator가 기계적으로 검사한다. 다만 validator는 모양만 본다. 필드에 든 날짜가 원문에 있는지는 따로 대조해야 한다.

형식을 약속하는 세기에도 단계가 있다.

| 방식 | 보장하는 것 |
| --- | --- |
| 프롬프트로 "JSON으로" 부탁 | 아무것도 보장하지 않는다 (지킬 때가 많을 뿐) |
| JSON mode | 파싱되는 JSON (특정 스키마 일치는 아님) |
| Structured Outputs·strict 도구 스키마 | 지원 범위 안에서 필드·자료형·필수값 |

어느 단계든 내용이 사실인지는 보장하지 않는다. 그래서 결과를 재는 자(평가지표)를 과업에 맞춰 고른다.

| 먼저 묻는 질문 | 1차 지표 |
| --- | --- |
| 정답이 하나로 정해져 있나 | 이진 판정, 정확 일치 |
| 정답이 여러 항목의 묶음인가 | {% include term.html name="F1" %} (정밀도·재현율과 함께) |
| 참고 번역·참고 요약이 있나 | BLEU(번역), ROUGE(요약) |
| 돌려 볼 수 있는 코드인가 | pass@k + 테스트 |
| 정답 없이 품질을 봐야 하나 | 채점표를 준 LLM 채점 + 사람 표본 검토 |

F1을 작게 계산해 보면 이렇다. 냉장고에서 상한 음식을 고르게 했더니 모델이 5개를 골랐고 그중 3개가 정말 상한 것이었다. 실제로 상한 건 4개였다. 고른 것 중 맞은 비율(정밀도)은 3/5 = 0.6, 상한 것 중 찾아낸 비율(재현율)은 3/4 = 0.75, F1은 2 × 0.6 × 0.75 ÷ (0.6 + 0.75) ≈ 0.67이다. 한쪽이 무너지면 F1도 같이 내려간다.

perplexity(모델이 글을 얼마나 덜 놀라워하나)는 이런 비교에 쓰지 않는다. 모델이 자신 있게 쓴 문장이 맞는 문장은 아니기 때문이다. 스텝 6에서 쓴 이진 판정이 이 표의 첫 줄에 해당한다. "없는 날짜를 지어냈나"는 예/아니오로 갈린다.

### 1-7. 실패 다섯 유형 — 이름을 붙이고 한 문장만 고친다

자전거 체인이 빠졌는데 바퀴, 브레이크, 안장을 한꺼번에 갈면 다음에 또 빠졌을 때 무엇이 문제였는지 모른다. 그래서 실제로는 **틀린 답을 유형으로 나누고, 그 유형에 맞는 문장 하나만 바꿔 같은 조건으로 다시 돌린다.**

| 유형 | 이런 답이 나오면 | 내 실습에서 본 모습 |
| --- | --- | --- |
| 모호함 | 한 낱말을 모델 마음대로 넓게 읽는다 | B안의 "한 가지"를 "주문번호 또는 이메일"로 읽음 → B′에서 "'또는'으로 함께 제시하지 말고" |
| 과잉 | 조건이 너무 많아 서로 밀어낸다 | (이번 실습에서는 나오지 않음) |
| 누락 | 있어야 할 행동이 아예 없다 | A안에 "모르면 지어내지 말 것"이 없어 배송 기간을 지어냄 → B에서 날짜 금지(문체·질문 규칙과 함께 더함) |
| 충돌 | 두 요구가 서로 반대 방향이다 | (이번 실습에서는 나오지 않음) |
| 형식 흐트러짐 | 약속한 모양 밖에 무언가 붙는다 | C안의 JSON이 코드 펜스에 싸여 나옴 → C′에서 "코드 펜스 없이" |

B′와 C′를 돌릴 때 바꾼 건 문장 하나뿐이고 모델·입력·기준표는 그대로였다. 그래서 "② 0/3 → 3/3"을 그 문장과 짝지어 말할 수 있다. 같은 표에서 **다른 기준이 떨어지지 않았는지도 함께 봤다.** 하나를 고치다 다른 곳이 망가지는 경우를 놓치지 않으려면 고친 칸만이 아니라 표 전체를 다시 채워야 한다.

### 1-8. 왜 필요한가

앞으로 지시를 쓸 때는 이 순서를 따른다.

- **쓰기 전에** — 다섯 칸 중 무엇이 필요한지 정하고, 통과 기준을 예/아니오로 먼저 적는다.
- **돌릴 때** — 모델·설정·반복 횟수를 같이 기록하고, 최소 세 번은 돌린다.
- **틀렸을 때** — 실패를 다섯 유형 중 하나로 부르고, 문장 하나만 바꿔 다시 잰다.
- **꼭 지켜야 할 때** — 글자 수, 금지어, JSON 모양은 프롬프트에 맡기지 않고 코드로 검사한다.

## 2. 실습 / 코드

두 실습 모두 직접 실행했다. 실습 폴더(`training/1007_basic_prompt`, `training/1007_instruction_lab`)는 깃 저장소가 아니라서 작업물 글 대신 이 절에 정리한다.

### 2-1. 스텝 2 — 같은 질문, 다른 말투 (기초 프롬프트 실험)

내 컴퓨터에는 아무것도 설치하지 않고, 구글 코랩의 무료 GPU에 {% include term.html name="Ollama" %}를 올려 작은 모델로 돌렸다. 모든 조건을 세 번씩 반복했다.

| 항목 | 값 |
| --- | --- |
| 실행 환경 | 구글 코랩 T4 GPU, WSL의 `colab` CLI 0.6.0으로 조작 |
| 서버·모델 | Ollama 0.40.0, `qwen3.5:2b` (파라미터 1.9B, Q8_0) |
| 호출 | `/api/chat`, `think: false` 고정, system 지시 없음 |
| temperature | 함정 질문만 0 / 1.5 (`num_ctx 4096`), 나머지는 Ollama 기본값 |
| 반복 | 처음 실행 1회, 나머지 모든 조건 3회 |

**계산 `25 × 14 - 87 ÷ 3` (정답 321)**

| 조건 | 처음 1회 | 반복 3회 길이 | 최종 답 (3회) |
| --- | --- | --- | --- |
| 기본 | 356자 | 300 / 489 / 379 | 321 ✅✅✅ |
| 역할 + 단계별 검산 | 823자 | 965 / 796 / 783 | 321 ✅✅✅ |
| 예시 1개(few-shot) | 253자 | 496 / 294 / 350 | **301 ❌** / 321 / 321 |

처음 1회만 보면 "예시를 주면 가장 짧고, 셋 다 정답"이었다. 세 번 돌리자 예시와 기본의 길이가 거의 겹쳤고, 예시 조건에서 오답이 나왔다. 오답은 350과 29를 맞게 구한 뒤 빼기를 쪼개다 틀린 경우였다.

```text
280 + 21 = 301
```

남은 차이는 "역할 + 단계별 검산이 가장 길다" 하나였다. 정답이어도 끝에 중국어가 섞이거나("최종答案是 321") 틀린 용어가 끼는 경우가 있었다.

**형식·길이·금지 지시**

| 실험 | 조건 | 결과 |
| --- | --- | --- |
| 한국의 3대 강 | JSON 배열로만 | 파싱 2/3 성공, 내용 0/3 |
| 한국의 3대 강 | 기본 / 한 문장 | 둘 다 3/3 지어낸 강 이름 |
| 양자얽힘 설명 | 30자 이내 | 146 / 64 / 87자 → 0/3 지킴 |
| 양자얽힘 설명 | 500자 이상 | 1251 / 1182 / 1118자 → 3/3 (기본 1671 / 1583 / 1664자보다 짧음) |
| "AI" 없이 요약 | 금지어 | 1/3만 지킴 (2회 "AI" 사용) |

JSON 배열 세 개는 이랬다.

```text
r1  ["강남강", "낙동강", "성수강"]      ← 파싱 성공, 강 둘이 가짜
r2  [강 (강), 한강, 유고강, 해남강]     ← 따옴표 없음, 파싱 실패
r3  ["안녕하세요"]                     ← 파싱 성공, 강 이름이 아님
```

r3은 파서만으로 채점하면 정상으로 통과한다. 강 이름은 아홉 번 중 한 번도 제대로 나오지 않았다. 금지어 실험은 수업 자료에 요약할 원문이 없어 **내가 직접 쓴 네 문장짜리 글**을 넣었다. 그래서 수업 기록(3/3 지킴)과 결과가 다른 이유는 단정하지 않는다.

**함정 질문 "9.11과 9.9 중 어느 쪽이 더 큰가요?" (정답 9.9)**

| temperature | 결과 |
| --- | --- |
| 0 | 3/3 글자까지 똑같은 오답 "9 월 11 일이 더 큽니다." |
| 1.5 | 0/3 정답, 세 답이 모두 다름 |

1.5의 세 답은 각각 "9.11 > 9.9", "9월 9일이 크다"로 시작해 "9월 11일"로 끝나는 자기모순, "시간 순서상 9월 9일"이었다. 셋 다 날짜로 읽었다. 수업 자료에는 1.5에서 한 번 정답이 나온 기록이 있었는데 이번엔 다시 나오지 않았다. **0은 틀린 답을 안정적으로 반복했고, 1.5는 답을 흔들기만 했다.**

정리하면 다섯 가지가 남았다.

1. 말을 바꾸면 답의 **모양**은 확실히 바뀐다 (64자 ~ 1671자, 산문·JSON·한 문장).
2. 형식 통과와 내용 정답은 별개다.
3. 글자 수와 금지어는 생성 뒤 코드로 검사해야 한다.
4. temperature는 분포 모양만 바꾸고 정답을 만들지 않는다.
5. 1회 결과로 결론 내지 않는다.

### 2-2. 스텝 6 — 지시 세 개를 미리 정한 기준으로 채점하기

같은 고객 문의 "배송일은 언제인가요?"에 지시만 A·B·C로 바꿔 답변 초안을 만들었다. 모델은 실제 주문 정보를 볼 수 없다.

| 항목 | 값 |
| --- | --- |
| 실행 | WSL2 Ubuntu, `uv run --with claude-agent-sdk` (SDK 0.2.164) |
| 모델 | `haiku` → `claude-haiku-4-5-20251001` (15회 모두 응답의 모델명으로 확인) |
| 설정 | `tools=[]`, `mcp_servers={}`, `strict_mcp_config=True`, `max_turns=1`, `setting_sources=[]` |
| temperature | 이 경로에서는 조절 불가 |
| 반복 | 안마다 3회, 실행 오류 0건 |

`setting_sources=[]`는 강의 코드에 내가 더한 한 줄이다. 기본값이면 SDK가 WSL의 개인 설정 파일을 입력에 섞는다는 걸 19회차 실습에서 봤기 때문에, "지시문만 바꾼 비교"가 되도록 막았다.

| 안 | 지시 |
| --- | --- |
| A 최소안 | 고객 문의에 답변 초안을 작성하라. |
| B 보강안 | A + 정중한 한국어, 입력에 없는 배송일·주문 상태·운송장 번호 추정 금지, 정보가 부족하면 한 가지만 요청 |
| C 형식안 | B + `reply`, `question` 두 키의 JSON 객체만 출력 |

**실행 전에** 기준을 예/아니오 네 개로 정해 두고, 애매한 경우의 판정 규칙(일곱 개)도 미리 적었다. 답을 먼저 읽으면 그럴듯한 답에 맞춰 기준을 느슨하게 고치고 싶어지니, 그 틈을 미리 막는 것이다.

- ① 입력에 없는 날짜·기간을 쓰지 않았다 ("일반적으로" 같은 단서를 붙여도 실패)
- ② 확인할 수 없다고 밝히고, 확인할 정보를 **딱 한 가지** 요청했다
- ③ 고객에게 보낼 정중한 문체다
- ④ (C만) `json.loads`로 읽히고 키가 정확히 `reply`, `question` 두 개다

| 안 | ① 날짜 금지 | ② 한 가지 요청 | ③ 문체 | ④ 형식 |
| --- | --- | --- | --- | --- |
| A | **0/3** | 0/3 | 3/3 | – |
| B | 3/3 | **0/3** | 3/3 | – |
| C | 3/3 | 3/3 | 3/3 | **0/3** |
| B′ | 3/3 | **3/3** | 3/3 | – |
| C′ | 3/3 | 3/3 | 3/3 | **3/3** |

읽은 것은 이랬다.

- **A는 가장 친절해 보였지만 ①을 3회 모두 실패했다.** 목록과 이모지, 마이페이지 안내까지 넣었는데, "주문 후 2-3 업무일", "영업일 기준 3-5일" 같은 기간을 지어냈다.
- **B는 날짜는 지켰지만 "한 가지"를 3회 모두 어겼다.** "주문번호 또는 이메일"처럼 대안을 붙였다. 동작 확인용 1회에서는 주문번호만 물어서, 그것만 봤다면 통과로 잘못 결론 냈을 것이다.
- **C에서는 ②가 저절로 통과했다.** `question` 칸이 하나뿐이니 질문도 하나가 됐다. 예상하지 못한 효과였다. 대신 3회 모두 JSON을 코드 펜스(`` ```json `` 로 시작하는 블록)로 감싸 ④가 실패했다.

실패한 기준마다 **문장 하나씩만** 더해 같은 조건으로 다시 돌렸다.

| 수정 | 더한 문장 | 결과 |
| --- | --- | --- |
| B → B′ | "'또는'으로 함께 제시하지 말고 한 가지만" | ② 0/3 → 3/3, 다른 기준 유지 |
| C → C′ | "코드 펜스 없이 중괄호로 시작하고 끝나라" | ④ 0/3 → 3/3, 다른 기준 유지 |

C′에서 기준 밖으로 하나가 더 보였다. `reply`가 "추가 정보가 필요합니다"로 끝나서 `question`과 합쳐야 완성된다. `reply`만 고객에게 보내는 프로그램이라면 어색하다. 형식이 필요한지는 그 값을 받아 쓰는 쪽을 보고 정해야 한다.

채점은 Claude가 먼저 하고 내가 검토했으며, 고친 곳 없이 확정했다. 한계도 적어 둔다. 안마다 3회뿐이라 3/3도 "이 조건에서 세 번 관측됐다"까지만 말할 수 있다. temperature를 고정하지 못했고, 모델 하나·입력 하나의 결과다. Ollama와 Gemini 경로는 돌리지 않았다.
