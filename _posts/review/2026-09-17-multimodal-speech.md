## 한 줄 요약

> 멀티모달은 입력을 많이 넣는 기술이 아니라, 판단에 필요한 증거를 어느 형태에서 가져올지 고르는 일이다. 소리를 글자로 옮기면 억양과 침묵이 사라지고, 요약을 한 번 거치면 받아쓰기 오류까지 매끄럽게 숨는다.

## 1. 오늘 배운 것

지난 사흘은 그림을 한 가지 방향씩 다뤘다. 13회차엔 문서에서 글자를 꺼내고 사진에서 물건을 찾았고, 14회차엔 없던 그림을 만들었다. 오늘은 **글과 그림과 소리를 한 모델이 함께 받는 쪽**으로 넘어왔다. 그리고 소리를 글자로, 글자를 소리로 바꾸는 도구까지 다뤘다.

노드를 따라가며 한 문장으로 정리해 봤다. **텍스트, 이미지, 음성, 영상처럼 종류가 다른 정보를 이어서 한 맥락 안에서 이해하고 판단하는 AI.** 그런데 정리하고 보니 "무엇을 받을 수 있나"보다 더 중요한 질문이 따로 있었다.

> **오늘의 핵심 한 문장**
> 중요한 건 **입력을 많이 넣는 것**이 아니라, 문제를 푸는 데 필요한 **증거를 어느 형태에서 가져올지** 정하는 것이다.

| 순서 | 무엇에 답하는가 |
| --- | --- |
| 모달리티 | 이 일의 증거는 어떤 모양으로 있나 |
| 정렬 | 그림과 글을 어떻게 한 모델이 함께 다루나 |
| 소리를 글자로 | 받아쓰기 기계는 무엇을 넘어 지금이 됐나 |
| 크기 고르기 | 내 노트북에서는 어느 크기를 써야 하나 |
| 옴니 모델과 실행 도구 | 모델이 받는다고 내가 넣을 수 있나 |
| 목소리 만들기 | 목소리를 고르는 것과 복제하는 것은 어떻게 다른가 |
| 회의록 실습 | 녹음이 회의록이 되는 동안 무엇이 틀어지나 |
| 왜 필요한가 | 앞으로 무엇을 다르게 판단하게 되나 |

### 1-1. 모달리티 — 증거가 어떤 모양으로 있나

반 친구가 아파 보여서 보건실에 데려갔다고 해 보자. 보건 선생님은 "배 아파요"라는 말만 듣고 끝내지 않는다. 얼굴색을 보고, 목소리에 힘이 있는지 듣고, 체온계 숫자를 읽는다. **말, 얼굴, 목소리, 숫자**가 모두 다른 종류의 증거다. 그래서 실제로는 이렇게 정보가 담긴 형식 하나하나를 **모달리티**라고 부르고, 여러 모달리티를 함께 쓰는 것을 {% include term.html name="멀티모달" %}이라고 한다.

그런데 선생님이 매번 모든 검사를 하지는 않는다. 넘어져서 무릎이 까졌으면 체온은 안 잰다. 노드가 준 연습도 이 감각이었다. 세 가지 일을 놓고 "글만으로 충분한가"를 먼저 가려 보는 것이다.

| 업무 | 글만으로 충분한가 | 더 필요한 증거 |
| --- | --- | --- |
| 고객 상담 요약 | 내용 요약은 된다 | 침묵, 말 끊김, 목소리 톤이 품질 기준이면 **음성** |
| 공장 설비 이상 진단 | 작업자 메모로는 부족할 수 있다 | 설비 소리, 계기판 **사진**, 경고등 **영상** |
| 학생 발표 피드백 | 논리 구조는 발표문으로 본다 | 말 속도, 망설임, 시선은 **음성·영상** |

입력을 늘리면 비용이 늘고, 개인정보 걱정이 늘고, 틀렸을 때 설명하기도 어려워진다. **더 많이 넣는 게 늘 정답은 아니다.** 판단에 필요한 증거가 어디 있는지부터 본다.

### 1-2. 정렬 — 번역이 아니라 같은 지도에 놓기

처음엔 멀티모달을 이렇게 상상했다. 그림을 먼저 설명문으로 바꾸고, 언어 모델이 그 설명문을 읽는다. 이런 방식도 실제로 쓰인다. 하지만 설명문으로 옮기는 순간 **글로 옮기지 못한 단서는 사라진다.** 설비 사진이 "기계 사진입니다"가 되면 녹슨 위치는 더 물어볼 수 없다.

{% include figure.html src="/assets/images/multimodal-speech/translate-vs-align.svg" alt="위쪽은 설비 사진을 한 줄 설명문으로 바꾼 뒤 언어 모델에 넘기는 번역 방식으로, 녹슨 위치 정보가 중간에 사라진다. 아래쪽은 개 사진과 '개 사진'이라는 글을 각각 인코더로 숫자로 바꿔 같은 임베딩 공간에 놓는 정렬 방식으로, 짝이 맞는 둘은 가깝고 '고양이 사진'은 멀리 있다" caption="그림 1. 번역하기와 같은 지도에 놓기" %}

다른 길은 **짝 맞추기 카드 게임**과 비슷하다. 그림 카드와 글 카드를 잔뜩 섞어 놓고, 맞는 짝은 가까이 붙이고 틀린 짝은 멀리 떼어 놓는 연습을 수없이 한다. 그래서 실제로는 그림과 글을 각자 {% include term.html name="인코더" %}로 숫자 목록({% include term.html name="임베딩" %})으로 바꾸고, **짝이 맞는 그림과 글이 같은 공간에서 가까워지도록 학습**한다. 이걸 번역과 구분해 **정렬**이라고 부른다.

이 발상을 크게 밀어붙인 게 14회차 연표에서 스쳐 간 **CLIP**이다. 오픈AI가 2021년에 인터넷의 그림–설명 쌍 4억 개로 "어느 글이 어느 그림에 붙나"를 맞히게 했다. 이렇게 맞는 짝은 당기고 틀린 짝은 밀어내는 학습을 **대조 학습**이라고 한다. 학습이 끝나면 처음 보는 사진도 "빨간 자동차"라는 글 가까이에 놓인다. **가까이 있다는 것 자체가 뜻이 비슷하다는 신호**가 된 셈이다. 다만 가깝다고 같은 건 아니다. 그 거리는 학습 데이터에서 배운 통계라서, 내 업무에서 진짜 중요한 차이를 다 잡는다는 보장은 없다.

붙이는 방식은 크게 세 갈래였다. 한 모델이 두 가지를 겹쳐 쓰기도 한다.

| 갈래 | 쉽게 말하면 | 강한 곳 | 조심할 곳 |
| --- | --- | --- | --- |
| 연결형 | 그림 담당 인코더가 언어 모델에게 **통역해서** 넘긴다 | 기존 언어 모델을 그대로 쓴다. 공개 모델이 많다 | 통역하다 세밀한 단서가 빠질 수 있다 |
| 공유 임베딩형 | 모두 **같은 지도**에 올린다 | 사진으로 글 찾기, 글로 사진 찾기 | 가깝다 ≠ 정답 |
| 네이티브 | 처음부터 **한 머리로** 보고 듣고 읽는다 | 대화 중 화면·소리·문맥을 함께 | 비용, 속도, 검증이 복잡하다 |

세 번째의 대표가 GPT-4o와 Gemini다. 둘 다 가중치가 공개되지 않은 상용 서비스다. 13회차에 만난 {% include term.html name="VLM" %}은 이 흐름 중 그림과 언어를 잇는 쪽이다.

### 1-3. 소리를 글자로 — 고무줄 문제의 역사

말을 글자로 바꾸는 걸 **음성 인식(STT)**, 글자를 말소리로 바꾸는 걸 **음성 합성(TTS)**이라고 한다. 둘을 묶어 {% include term.html name="STT/TTS" %}로 정리해 두었다.

받아쓰기가 어려운 이유부터 봤다. 같은 사람이 "안녕하세요"를 두 번 말해도 소리 모양(파형)은 한 번도 똑같지 않다. 그래서 먼저 소리를 **그림**으로 바꾼다. 짧은 순간마다 높은 소리, 낮은 소리가 얼마나 센지 재서 가로는 시간, 세로는 높낮이로 펼친 그림, **스펙트로그램**이다. 모음마다 줄무늬 배치가 달라서 파형에선 안 보이던 차이가 무늬로 보인다. 지금 모델들도 이 그림을 입력으로 받는다. 소리를 듣는 모델은 **소리의 무늬를 읽는 모델**이기도 하다.

진짜 벽은 **길이**였다. 느리게 말하면 3초, 빠르게 말하면 1초인데 정답은 둘 다 다섯 글자다. 고무줄에 글자 다섯 개를 적어 놓고 늘였다 줄였다 하는 것과 같다. 그래서 실제로는 **소리 조각 수와 글자 수가 매번 달라서 앞에서부터 하나씩 짝지을 수 없다.** 어느 소리 조각이 어느 글자인지 알아야 하는데, 바로 그게 모르는 부분이었다. 이 짝 맞추기를 **시간 정렬**이라고 한다. 1-2의 정렬과 이름은 같지만, 이건 소리 하나 안에서 구간과 글자를 맞추는 이야기다.

| 시기 | 무엇이 바뀌었나 | 쉽게 말하면 |
| --- | --- | --- |
| 1970년대 | 규칙 대신 확률 | "이 소리면 이 글자" 규칙을 사람이 적다가, 데이터에서 확률을 배우게 했다 |
| 2000년대 | 네 부품 조립 | 소리 판별기, 사람이 손으로 쓴 발음 사전, 다음 단어 맞히기, 조립기. 새 언어면 전부 새로 |
| 2012 | 부품 하나를 신경망으로 | 소리 판별기만 바꿨는데 오류가 27.4% → 18.5%, 3분의 1이 줄었다 |
| 2006 발상, 2012 이후 쓰임 | CTC | 어느 짝이 맞는지 고르지 말고, **가능한 짝을 전부 더해** 버린다. "빈칸" 기호를 하나 넣어 가능하게 했다 |
| 2020 | wav2vec 2.0 | 아기처럼 **그냥 듣고** 먼저 배운다. 받아쓴 자료 1시간으로, 전에 100시간 쓰던 성능을 넘었다 |
| 2022 | Whisper | 인터넷의 잡다한 음성 68만 시간으로 학습. 오늘 실습 도구 |

Whisper의 성적표가 인상적이었다. 깔끔하게 낭독한 시험지에서는 이전 방식과 **2.7 대 2.7로 소수점까지 같았다.** 그런데 회의 녹음(헤드셋) 37.0 → 16.9, 전화 통화 28.3 → 13.8처럼 다른 시험지에서는 **오류가 절반**이었다. 같은 시험지만 잘 보는 학생과 처음 보는 문제도 푸는 학생의 차이다. 이걸 **강건함**이라고 부른다.

같은 표에 숨은 이야기도 있었다. 같은 모델, 같은 회의인데 각자 헤드셋을 쓰면 16.9, 회의실에 마이크 하나 놓으면 36.4였다. **마이크만 멀어져도 오류가 두 배가 넘는다.** 낡은 모델은 한 번 바꾸면 끝이고, 그다음부터 가장 큰 손잡이는 모델이 아니라 마이크다.

### 1-4. 크기 고르기 — 운동화는 발에 맞아야 한다

Whisper는 tiny부터 large까지 크기가 여러 가지다. 운동화처럼 큰 게 좋은 게 아니라 **내 노트북에 맞고 내 언어에 맞아야** 한다. 그래서 실제로는 무게(메모리·시간)와 정확도를 함께 보고, 내 기기에서 돌아가는 것 중 한국어 오류율이 견딜 만한 크기를 고른다.

{% include figure.html src="/assets/images/multimodal-speech/whisper-size.svg" alt="Whisper 크기별 한국어 글자 오류율 막대그래프. tiny 36.6%, base 40.6%, small 17.5%, medium 13.9%, large-v3 8.0%. 아래에 따로 한국어로 다시 학습한 base가 8.7%로 large-v3에 거의 붙었다고 표시돼 있다" caption="그림 2. 크기보다 그 언어를 봤느냐가 먼저다" %}

- **tiny, base는 한국어에서 못 쓴다.** 열 글자 중 네 글자가 틀리면 받아쓰기가 아니라 소설이다. 영어 예제에서 흔한 크기라 그대로 따라 하면 첫 실습부터 막힌다.
- **한국어로 다시 배운 base가 8.7%**였다. 148MB짜리가 3.1GB짜리 large-v3(8.0%)에 거의 붙었다. 크기보다 **그 언어를 배웠느냐**가 먼저다.
- 램 8GB면 small까지 편하고, 16GB면 medium이 편하다. 12회차 노드에서 {% include term.html name="Ollama" %} 모델 크기를 한 칸씩 올려 보라던 "크기 사다리"와 같은 판단이다.

오류율을 **무엇으로 셌는지**도 봐야 한다. 같은 결과가 어떤 문서엔 3%대, 어떤 문서엔 14%대로 적혀 있었다. 단어 단위로 세면 "할 수 있다"를 "할수있다"로 받아쓴 것도 전부 오답이 되기 때문이다. **한국어는 글자 단위로 센다.** "정확도 97%"라는 광고를 보면 무엇을 기준으로 몇 번 잰 값인지 먼저 묻는다.

같은 모델도 **어떤 판본으로 받느냐**에 따라 달랐다. Qwen3-ASR 0.6B로 33초 녹음을 돌렸더니 기본 판은 9.6초, 애플 기기용 8비트 판은 0.7초였다. 같은 모델, 같은 기기인데 **열네 배**다. 기기에 맞춰 다시 포장한 파일 형식이 따로 있다. 애플 기기면 MLX, 그 밖에는 12회차에 스친 GGUF다. 둘 다 {% include term.html name="양자화" %}로 가볍게 만든 판이 많다. 배포 페이지에서 이 이름이 붙은 판부터 찾는다.

### 1-5. 옴니 모델과 실행 도구 — 게임 팩과 게임기

소리를 글자로 바꾼 뒤 언어 모델에 넘기는 대신, **한 모델이 다 받게 하는** 길도 있다. 이런 모델을 **옴니 모델**이라고 부른다. GPT-4o의 o가 그 뜻이다. 노트북에서 직접 만져 볼 수 있는 것으로는 구글이 가중치를 공개한 **Gemma 4**가 있다. 글, 이미지, 영상은 모든 크기가 받고, 소리는 E2B·E4B·12B가 받는다. 노트북에서 시작한다면 E4B가 무난하다고 했다.

```bash
ollama run gemma4:e4b
```

여기서 함정이 하나 있었다. **같은 게임 팩이라도 꽂는 게임기에 따라 켜지는 기능이 다르다.** 모델 가중치는 숫자가 잔뜩 든 파일일 뿐이고, 그걸 메모리에 올려 실제로 돌려 주는 프로그램이 따로 있다. 이걸 {% include term.html name="추론 엔진" %}이라고 한다. 그래서 실제로는 **같은 모델 파일이라도 어떤 엔진으로 돌리느냐에 따라 받는 입력과 속도가 달라진다.**

| 무엇으로 돌리나 | 넣을 수 있는 것 |
| --- | --- |
| 간편한 로컬 도구 (Ollama 등) | 글, 이미지 |
| 서버용 추론 엔진 (vLLM 등) | 글, 이미지, 소리, 영상 |

모델은 소리를 받을 수 있는데 그 도구가 아직 입력을 열어 주지 않은 것이다. 그래서 **"이 모델이 무엇을 할 수 있나"와 "내 환경에서 무엇이 되나"는 따로 확인**해야 한다. 엔진의 갈래도 목적이 다르다. 내 노트북에서 혼자 쓰는 도구는 설치가 쉽고 그래픽카드가 없어도 돈다. 서버에서 여럿이 쓰는 엔진은 요청을 겹쳐 밀어 넣어 그래픽카드를 쉬지 않게 한다. "초당 몇 토큰"이라는 속도 비교를 보면 **어느 엔진으로 쟀는지**부터 본다.

한 모델이 다 받으면 좋은 점과 대가가 함께 온다. 소리를 그대로 받으니 **긴 침묵 뒤의 낮은 "네, 알겠습니다"**를 물어볼 수 있다. 대신 받아쓰기와 요약 사이의 중간 결과가 사라져서 **어디서 틀렸는지 짚을 자리도 사라진다.** 그래서 선택은 정확도가 아니라 **무엇을 검증해야 하는가**로 갈린다. 나중에 근거를 되짚어야 하는 회의록이면 나눠 두는 편이 낫고, 실시간으로 상황을 파악해야 하면 한 번에 받는 편이 낫다.

### 1-6. 목소리 만들기 — 고르기, 복제하기, 허락받기

TTS에도 받아쓰기와 같은 자리에 함정이 있었다. **내려받기 1위 모델의 지원 언어 아홉 개에 한국어가 없다.** 유명하다고 고르면 막힌다.

노드는 한국어가 되고 노트북에서 도는 합성기와, 목소리 복제가 되는 큰 모델을 나란히 놓았다.

| | 노트북용 합성기 (supertonic) | Fish Audio S2 Pro |
| --- | --- | --- |
| 크기 · 어디서 | 385MB · 노트북 CPU | 11GB · 그래픽카드 |
| 목소리 | **정해진 열 개 중에서 고른다** | 10~30초 녹음으로 **복제한다** |
| 감정 | 정해진 표현 태그 열 개(`<laugh>`, `<sigh>` 등) | "방송하듯 또박또박" 같은 문장으로 지시 |
| 라이선스 | 조건부 상업 사용 가능 | 연구·비상업만 무료. **사내 업무도 상업**으로 본다 |
| 상태 | 2026년 7월 아카이브 공지 | 활발 |

재미있는 확인법도 있었다. 목록에 없는 `<angry>`를 넣었더니 화난 목소리가 아니라 **"앵그리"라고 글자를 읽었다.** 그리고 만든 음성을 다시 받아쓰기에 넣어 원문으로 돌아오는지 보면 품질을 잴 수 있다. 다만 그건 **알아들을 수 있다**까지만 보여 준다. 자연스러운지는 직접 들어 봐야 안다.

복제는 기술보다 **허락**의 문제다. 친구 목소리를 흉내 내 녹음을 만들려면 친구에게 먼저 물어봐야 하는 것과 같다. 10~30초 샘플로 말투와 감정 버릇까지 잡힌다는 건, 거꾸로 **누구든 내 목소리를 만들 수 있다**는 뜻이다. 국내 AI 기본법의 "AI로 만든 것임을 표시하라"는 의무는 서비스를 제공하는 사업자에게 걸리지만, 만드는 사람에게는 **모델 라이선스와 목소리 주인의 권리**가 걸린다. 국내 확정 판례는 아직 없다. 판례가 없다는 건 안전하다는 뜻이 아니라 **기준이 아직 없다**는 뜻이다.

### 1-7. 회의록 실습 — 요약이 오류를 세탁한다

마지막 노드는 녹음 → 받아쓰기 → 회의록 → 노션 저장을 **코딩 에이전트에게 단계별로 시키는** 실습이었다. 직접 해 보진 못했지만(2-1), 설계에서 배울 점이 많았다.

1. **30초는 손으로 받아 적어 둔다.** 설정을 바꿔 가며 좋아졌는지 재려면 자가 필요하다. "아까보다 나은 것 같다"로는 판단이 안 선다.
2. **한 번에 하나씩 바꾼다.** 소리 쪽(16kHz 변환, 음량 고르기, 무음 자르기, 잡음 억제)과 설정 쪽(한국어 지정, 고유명사 목록, 모델 크기)을 하나씩 켜 보고 기록표를 채운다. 넷을 한꺼번에 켜고 좋아지면 무엇 덕분인지 모른다.
3. **한 번 잰 값을 믿지 않는다.** 노드의 33초 녹음에서도 small의 오류율이 0.7%~4.1%를 오갔다.

그리고 이 실습의 핵심 장면이 있었다.

{% include figure.html src="/assets/images/multimodal-speech/summary-launder.svg" alt="실제로 한 말 '제안입니다'가 받아쓰기에서 '제한입니다'로 틀렸다. 그냥 회의록으로 정리하라고 하면 어색함이 다듬어져 흔적이 사라지고 녹취에 없던 날짜까지 생긴다. 의심스러운 곳을 원문 그대로 인용해 표시하라고 넣으면 같은 모델이 틀린 곳을 표시했다" caption="그림 3. 요약이 받아쓰기 오류를 숨기는 과정" %}

받아쓰기에서 **제안이 제한**으로 바뀌었다. 글자 하나다. 받아쓴 글에서는 문장이 어색해서 눈에 띈다. 그런데 "회의록으로 정리해 주세요"라고만 시키면 요약이 그 어색함을 매끄럽게 다듬어 버린다. 틀린 받아쓰기를 예쁜 글씨로 옮겨 적으면 틀린 줄 모르게 되는 것과 같다. 녹취에 없던 날짜까지 생겼다. 반대로 **"의심스러운 곳은 다듬지 말고 원문 그대로 인용해 표시하라"**는 항목을 넣었더니 같은 모델이 틀린 곳을 짚었다. 큰 모델은 안 시켜도 알아서 표시할 때도 있었는데, 운에 맡길 수 없으니 {% include term.html name="프롬프트" %}에 적는다.

노션에 남길 때도 기준은 하나였다. **회의록만 보고 원본의 어느 지점을 다시 들어야 하는지 알 수 있는가.** 그래서 확인이 필요한 곳마다 녹취 시각을 남기고, 맨 아래에 어느 모델과 설정으로 만든 회의록인지 적는다.

### 1-8. 왜 필요한가

앞으로 AI에게 무언가를 맡길 때 질문이 바뀐다. "이 모델이 이미지도 받나?" 대신 이렇게 묻게 된다.

| 예전 질문 | 오늘 이후의 질문 |
| --- | --- |
| 이 모델이 소리도 받나? | 이 일의 **증거는 어느 모달리티에** 있나 |
| 가장 큰 모델이 뭐지? | **내 언어**로 배운 모델, **내 기기**에 맞는 판이 있나 |
| 모델 카드에 된다고 적혀 있나? | **내 실행 도구**에서도 되나 |
| 요약이 매끄럽나? | 요약만 보고 **못 잡는 오류**를 어떻게 남기나 |
| 공짜로 공개된 모델인가? | 라이선스가 **내 용도**를 허락하나, 목소리 주인이 **동의**했나 |

입력이 많을수록 결론은 더 그럴듯해 보인다. 그래서 **근거가 원본의 어디에 있는지 같이 내게 하고, 마지막 판단은 사람이** 한다.

### 2-3. 수업 중 메모 — Claude Code의 스킬은 어디에 두나

수업 중에 Claude Code 스킬을 둘 수 있는 자리를 다섯 곳으로 받아 적었다. 나중에 공식 문서와 대조해 보니 **스킬 폴더와 설정 파일이 섞여 있었다.** 스킬은 `skills/<이름>/SKILL.md` 폴더이고, 5번은 스킬이 아니라 **{% include term.html name="MCP" %} 서버 설정 파일**이다.

**스킬이 놓이는 곳**

| 메모 | 실제 경로 | 어디서 쓰이나 |
| --- | --- | --- |
| 3. 사용자 폴더의 `.claude` | `C:\Users\<사용자명>\.claude\skills\` | **모든 프로젝트**에서 (개인 스킬) |
| 1·2. 작업 폴더·루트의 `.claude` | `<프로젝트>\.claude\skills\` | 그 프로젝트에서. 저장소 루트까지 위 폴더를 거슬러 찾고, 하위 폴더 것은 그 폴더 파일을 만질 때 불려온다 |
| (메모에 없음) | 플러그인 안의 `skills\` | 플러그인을 켠 곳에서 |

**설정 파일 — 스킬이 아니다**

| 메모 | 실제 파일 | 하는 일 |
| --- | --- | --- |
| 4. 프로젝트 폴더의 json | `.mcp.json` (프로젝트 MCP), `.claude\settings.json` (프로젝트 설정) | 이 프로젝트에서 쓸 MCP 서버, 권한 같은 설정 |
| 5. 설정 > 개발자 > MCP | `claude_desktop_config.json` | **Claude 데스크톱 앱**의 MCP 서버 목록. 데스크톱 앱 Code 탭의 로컬 세션도 이걸 읽는다 |

개인 MCP 설정은 `~\.claude.json`, 개인 설정은 `~\.claude\settings.json`에 있다. 한 줄로 줄이면 **`skills\` 폴더면 스킬, `.json`이면 설정**이다. 7회차에 배운 스킬·MCP 이야기가 실제로 어디에 사는지 알게 됐다.

### 2-4. 수업 중 메모 — OCR 교정 팁

13회차 OCR과 이어지는 팁을 하나 들었다. **스캔본 이미지를 로컬에서 OCR해 PDF로 만든 뒤, 그 PDF를 LLM에 넣고 문맥을 보고 교정해 달라고 한다.** OCR은 글자 모양만 보고, LLM은 앞뒤 문맥으로 틀린 글자를 찾으니 서로 약한 곳을 메운다. 다만 오늘 1-7에서 본 것처럼 교정도 요약처럼 오류를 매끄럽게 덮을 수 있으니, **고친 곳을 표시해 달라고** 함께 시키는 게 좋겠다.
