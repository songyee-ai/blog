## 한 줄 요약

> 이론 대신 서로의 코드를 읽었다. 다섯 항목으로 남의 코드를 판정해 보고, 같은 잣대로 내 코드가 판정받았다.

---

## 1. 오늘 배운 것

오늘은 새 이론이 없었다. 한 단원이 끝나는 시점이라 **두 가지를 했다.** 앞서 만든 과제로 서로의 코드를 리뷰했고, 지금까지 배운 것을 한 번에 정리했다.

지금까지는 내가 만든 것을 내가 확인했다. 오늘은 **남이 내 코드를 열어 보고, 내가 남의 코드를 열어 봤다.** 이게 생각보다 다른 일이었다.

> **오늘의 핵심 한 문장**
> 코드 리뷰는 코드를 고쳐 주는 자리가 아니라, **읽고 판단한 근거를 남기는 자리**다.

| 순서 | 무엇에 답하는가 |
| --- | --- |
| 피어 리뷰란 | 왜 둘이 짝을 지어 역할을 바꿔 가며 하는가 |
| 다섯 항목 | 남의 코드에서 무엇을 보는가 |
| 진행 절차 | 남의 저장소를 어떻게 건드리지 않고 리뷰만 더하는가 |
| 잣대가 안 맞을 때 | 템플릿이 내 프로젝트 종류와 다르면 어떻게 하는가 |
| 단원 정리 | 지금까지 배운 것이 결국 어디에 놓이는가 |

### 1-1. 피어 리뷰 — 한 사람이 두 역할을

2인이 한 조가 되고, **한 사람이 코더와 리뷰어를 번갈아** 맡는다. 내 코드를 남이 읽어 주고, 곧바로 내가 남의 코드를 읽는다.

시작은 양쪽 다 **자기 프로그램을 설명하는 것**이었다. 코드를 바로 열지 않는다. 무엇을 만들려 했는지 먼저 듣고 나서 읽는다.

이 순서가 중요했다. 설명을 먼저 들으면 리뷰가 **"의도한 것이 코드가 되었는가"**를 보게 된다. 설명 없이 코드부터 읽으면 취향 이야기가 되기 쉽다.

### 1-2. 다섯 항목 — 무엇을 보는가

리뷰 템플릿은 다섯 항목이었고, 각 항목에 해당하면 `[x]`로 표시하고 **근거가 되는 코드를 캡처해 붙이고, 왜 그렇게 판단했는지** 적는다.

| # | 항목 | 묻는 것 |
| --- | --- | --- |
| 1 | 완성 | 요구한 기능이 실제로 작동하는가 |
| 2 | 설명 | 복잡한 부분이 주석·문서만 보고 이해되는가 |
| 3 | 기록 | 문제를 푼 과정이나 추가 실험이 남아 있는가 |
| 4 | 회고 | 만든 사람의 배운 점·아쉬운 점이 적혀 있는가 |
| 5 | 구조 | 중복을 줄이고 모듈로 나눴는가 |

체크 표시 자체는 중요하지 않다. **"이렇게 판단한 이유"가 본문**이다. 근거 없이 `[x]`만 찍으면 리뷰가 아니라 설문 응답이 된다.

### 1-3. 진행 절차 — 남의 저장소를 건드리지 않는 방법

절차가 잘 설계돼 있었다. 2회차에서 배운 {% include term.html name="GitHub" %} 흐름이 여기서 실제로 쓰였다.

1. 상대 저장소를 **포크**해 내 계정으로 가져온다
2. 내 컴퓨터에 **클론**한다
3. 미리 받아 둔 리뷰 파일을 그 폴더에 복사한다
4. 에이전트에게 그 폴더를 지정하고 리뷰 파일을 채우게 한다
5. **리뷰 파일만** 커밋해서 푸시하고 **PR**을 보낸다
6. PR을 받은 원본자가 **다른 파일이 함께 바뀌지 않았는지 확인한 뒤** 머지한다

결과적으로 상대 저장소에 더해지는 것은 **리뷰 파일 한 개뿐**이다. 6번의 더블 체크가 그걸 보장하는 장치다. 에이전트에게 폴더를 통째로 맡기면 의도하지 않은 파일이 따라 바뀔 수 있으니, **머지 전에 사람이 확인한다.**

### 1-4. 잣대가 내 프로젝트와 안 맞을 때

리뷰 템플릿은 원래 **파이썬·딥러닝 과제 기준**으로 만들어져 있었다. 5번에 "PEP8을 준수했는지", 4번에 "딥러닝 모델의 경우 인풋부터 아웃풋까지 도식화했는지" 같은 항목이 있다.

그런데 이번에 리뷰한 두 프로젝트는 둘 다 **TypeScript 웹 서비스**였다. PEP8은 파이썬 스타일 규칙이니 해당하지 않는다.

여기서 배운 게 있다. 제가 받은 리뷰는 이 지점을 그냥 넘기지 않고 **첫머리에 명시**했다. 파이썬 프로젝트가 아니므로 PEP8 항목은 **ESLint·타입 검사·프로젝트 자체 규칙 검사로 대체해 판단했다**고.

항목을 지우지도, 억지로 끼워 맞추지도 않고 **"같은 것을 묻는 다른 잣대"로 바꿔 놓고 그 사실을 적는 것.** 이게 오늘 가장 인상 깊었던 태도였다.

### 1-5. 왜 필요한가

내 코드는 내가 만들었으니 나에게는 당연히 읽힌다. 그래서 **읽히는지 아닌지를 내가 판정할 수 없다.**

특히 지금처럼 AI와 함께 만들면 더 그렇다. 8회차에서 "이해 못 한 코드는 배포하지 않는다"를 배웠는데, 이해했는지를 확인하는 가장 확실한 방법이 **남에게 설명하고 남이 읽어 보게 하는 것**이었다. 7회차의 러버덕이 혼자 하는 버전이라면, 오늘은 진짜 사람이 듣는 버전이었다.

### 1-6. 한 단원을 닫으며 — 1~8회차 정리

수업은 지금까지 배운 것을 한 번에 훑는 시간으로 끝났다. 낱개로 배울 때는 안 보이던 배치가 보였다.

| 묶음 | 회차 | 다룬 것 |
| --- | --- | --- |
| **작업할 자리 만들기** | 1 | 기록을 남기는 틀 정하기 |
| | 2 | {% include term.html name="Git" %}·{% include term.html name="GitHub" %}, 터미널, Node·npm |
| | 3 | {% include term.html name="PATH" %}, 프로세스·스레드, 동기·비동기, 프론트와 백엔드의 경계 |
| **서비스의 뼈대** | 4 | 변수·함수·객체, 프레임워크, {% include term.html name="API" %}, 목업 데이터, PRD |
| | 5 | 도메인·DNS·포트, HTTPS, 상태 코드, 인증·인가, 배포 |
| | 6 | 표·관계·키, 정규화, 트랜잭션, SQL 주입, 백업 |
| **AI와 함께 만들기** | 7 | 에이전트, 모델 + 하네스, MCP, 스킬, 권한과 안전 |
| | 8 | MVP와 범위 좁히기, 다섯 단계, 되돌리는 규율 |

이렇게 놓고 보니 **줄기가 세 개**였다.

**첫째, 무엇을 만들지는 내가 정하고 어떻게 만들지는 AI가 정한다.** 4회차의 PRD에서 시작해 8회차에서 "PRD에 기술 선택을 넣지 않는다"로 정리됐다. 내가 할 일은 의도를 정확히 말하고 결과를 확인하는 것이다.

**둘째, 규칙은 지켜지는 자리에 둔다.** 6회차에서 트랜잭션을 배우고 8회차에서 "정원은 화면이 아니라 DB에서 지킨다"로 이어졌다. 5회차의 인증·인가, 6회차의 SQL 주입 방어도 같은 이야기였다. **화면에서 막는 것은 막는 게 아니다.**

**셋째, 되돌릴 지점을 남긴다.** 2회차의 커밋에서 시작해 8회차의 "작동하면 저장"으로, 그리고 오늘 리뷰의 3번 항목("문제를 푼 기록이 남았는가")까지 이어진다. 기록은 나중의 나와 남을 위한 것이다.

비전공자로 시작해 매번 모르는 용어가 쌓이는 게 가장 힘들었는데, 오늘 이 지도를 그려 보니 **용어가 아니라 판단이 남았다**는 걸 알았다.

## 2. 실습 / 코드 — 두 방향의 리뷰

### 2-1. 내가 받은 리뷰 — 그루뽑기

5회차에 만든 **그루뽑기**(학습 조에서 이끄미와 시간지키미를 공정하게 뽑는 서비스)가 대상이었다.

리뷰어는 코드를 읽기만 한 게 아니라 **직접 돌려 봤다.** 저장소를 클론해 `npm install` 후 테스트·린트·타입 검사를 실행하고, 배포본에 요청을 보내 응답 코드를 확인하고, 커밋 로그까지 열어 봤다. 다섯 항목 전부 `[x]`를 받았다.

좋게 본 지점이 세 개였는데, 내가 의도한 것과 정확히 겹쳐서 놀랐다.

- **주석이 "무엇을 하는지"가 아니라 "왜 이렇게 했는지"를 적고 있다** — 특히 "오늘 기록을 가중치에 넣으면 다시 뽑기가 직전 결과를 두 번 처벌한다" 같은 주석은, 그 한 줄이 없으면 조건문이 왜 있는지 보이지 않는다고 했다
- **못 맞춘 구간을 감추지 않고 테스트 이름에 남겨 뒀다** — 5명 조에서 최악값이 3까지 벌어지는 걸 기준을 낮춰 통과시키지 않고, 실측값을 그대로 적어 둔 점
- **폴더 경계를 사람의 기억이 아니라 검사가 지킨다** — 화면 코드에서 서버 키를 만지면 테스트가 실패하게 해 둔 것

지적받은 것도 셋이었다.

| 지적 | 내용 |
| --- | --- |
| **clone 직후 타입 검사가 깨진다** | `npm run typecheck`가 새 환경에서 바로 실패한다. 코드가 틀린 게 아니라 **선행 단계가 스크립트에 안 적혀 있는 것**. 한 줄이면 고쳐진다 |
| **개인 회고가 없다** | 판단 기록은 충분한데, 무엇이 예상과 달랐는지·다시 만들면 어디를 바꿀지 같은 **사람의 기록**이 문서 어디에도 없다 |
| **공정성 수치는 트레이드오프** | 가중치를 더 세게 주면 5·7명 조는 나아지지만 12명 조가 나빠진다. 실제 조 인원 분포를 보고 정할 일 |

첫 번째가 제일 뼈아팠다. **"clone 하고 문서에 적힌 명령을 그대로 쳤는데 빨간불"**이라는 표현이 정확했다. 나는 이미 한 번 실행해 본 환경에서만 확인했으니 영영 못 봤을 문제다. **남이 처음 받아 보는 상황은 남만 만들 수 있다.**

### 2-2. 내가 한 리뷰 — 회사 소개 자료 생성 서비스

짝의 프로젝트는 **회사명과 회사 정보(텍스트 또는 소개서 파일)를 넣으면 12장짜리 자료를 만들어 내려받는 서비스**였다. 지금은 본인의 코덱스 CLI를 연결해 쓰는 구조다.

읽으면서 좋게 본 것은 **실측으로 정한 값**이었다. AI 생성에 걸리는 시간을 실제로 재고(약 400자에 111초, 9,803자에 139초) 그 값을 근거로 제한 시간을 240초로 정한 기록이 코드에 남아 있었다. 숫자 없이 "넉넉히 잡았다"가 아니라는 점이 3번 항목의 근거가 됐다.

구조도 역할별로 나뉘어 있었다. 생성·렌더링·스키마·백엔드 실행이 각각 다른 파일이고, 입력 검증은 한 군데로 모여 있었다.

**4번(회고)만 체크하지 않았다.** 설계 문서와 PRD 검토 기록은 상당히 구체적인데, 프로젝트를 진행하며 배운 점·아쉬운 점을 정리한 **회고 글 자체**는 찾지 못했다. 이 판단을 내리면서 좀 망설였다. 문서가 이렇게 많은데 체크를 안 하는 게 맞나 싶었다.

제안은 두 개를 적었다.

- **자동 테스트 추가** — 잘못된 입력, 파일 크기 초과, 비로그인, 시간 초과처럼 실패하는 경로부터
- **실행 환경 분리** — 지금은 로컬 CLI에 직접 의존해서 원격 배포 환경에서는 돌지 않는다. 중간에 인터페이스를 하나 두면 로컬과 원격을 갈아 끼울 수 있다

두 번째는 제 프로젝트에서 배운 걸 그대로 옮긴 것이다. 그루뽑기에서 `Math.random`을 타입 뒤로 밀어낸 덕에 테스트가 가능해졌는데, 같은 구조가 여기에도 쓸 수 있어 보였다.

### 2-3. 양쪽에서 같은 지적이 나왔다

리뷰를 주고받고 나서 알았다. **4번 회고가 양쪽 다 비어 있었다.**

내 프로젝트는 `[x]`를 받긴 했지만 "개인의 배운 점·느낀 점은 문서 어디에도 없다"는 단서가 붙었고, 짝의 프로젝트는 같은 이유로 내가 체크하지 않았다. 둘 다 설계 문서와 판단 기록은 많았는데 사람의 기록만 없었다.

이유도 비슷할 것 같다. **AI와 만들면 문서가 저절로 쌓인다.** PRD, 설계 문서, 커밋 메시지, 결정 기록. 그래서 "기록은 충분하다"고 느끼는데, 그건 전부 **프로젝트에 대한 기록**이지 **나에 대한 기록**이 아니다.

### 2-4. 이 절에 덧붙일 것

- [ ] 그루뽑기 README에 `## 돌아보며` 추가 — 무엇이 예상과 달랐는지, 다시 만들면 어디부터 바꿀지

## 4. 막혔던 점과 해결

| 막힌 지점 | 궁금했던 이유 | 정리한 답 |
| --- | --- | --- |
| 리뷰 항목이 내 프로젝트 종류와 안 맞으면 어떻게 하나? | 5번은 파이썬 스타일 규칙(PEP8)을 묻는데 내 건 TypeScript 웹 서비스였다 | **항목을 지우지도, 억지로 끼워 맞추지도 않는다.** 그 항목이 결국 무엇을 묻는지(형식이 일관되고 정적 검사를 통과하는가)를 보고 **같은 것을 묻는 다른 잣대**로 바꾼 뒤, 바꿨다는 사실을 리뷰 첫머리에 적는다 |
| 설계 문서가 이렇게 많은데 왜 회고가 아닌가? | 짝의 4번을 체크하지 않으면서, 문서가 충분한데 인색한 판정인가 싶었다 | **둘은 다른 기록이다.** 설계 문서는 *프로젝트가 왜 이렇게 됐는지*를 남기고, 회고는 *만든 사람이 무엇을 배웠는지*를 남긴다. 앞의 것이 아무리 두꺼워도 뒤의 것을 대신하지 못한다. 실제로 내 프로젝트도 같은 이유로 같은 지적을 받았다 |
| 내 환경에서는 잘 되는데 왜 남은 안 되나? | clone 직후 타입 검사가 깨진다는 지적을 받았는데 나는 한 번도 못 봤다 | **내가 이미 한 번 실행해 본 환경에서만 확인했기 때문이다.** 필요한 파일이 실행 과정에서 생기고 그게 버전 관리에서 빠져 있으면, 처음 받는 사람만 그 자리에서 막힌다. 코드가 틀린 게 아니라 **선행 단계가 문서와 스크립트에 안 적혀 있는 것**이다 |
| 리뷰는 점수를 매기는 일인가? | 체크 표시가 있어서 채점처럼 느껴졌다 | **체크가 아니라 근거가 본문이다.** 받은 리뷰에서 가장 쓸모 있었던 건 `[x]` 다섯 개가 아니라 "이렇게 판단한 이유"와 개선 제안 세 개였다. 그리고 리뷰어는 코드를 대신 고치지 않는다. **읽고, 확인하고, 근거와 함께 제안까지만** 한다 |
