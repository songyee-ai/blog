## 한 줄 요약

> 자동화를 고를 때 먼저 물을 것은 'AI를 쓸까'가 아니라 '다음 행동은 누가 정하나'다. 규칙으로 적을 수 있는 건 워크플로에, 해석이 필요한 곳만 좁힌 도구를 쥔 에이전트에 맡기고, 판정은 실행 기록으로 확인한 사실로 내린다.

## 1. 오늘 배운 것

23회차에는 챗봇 하나를 처음부터 끝까지 만들었다. 오늘은 방향이 달랐다. 무엇을 만들지보다 **반복 업무를 어디까지 기계에 맡길지**를 정하는 날이었다. 도구로는 {% include term.html name="n8n" %}을 썼는데, 노드(수업)는 이걸 "만드는 도구"라기보다 "관찰하는 도구"로 소개했다. 흐름이 그림으로 보이고, 실행할 때마다 무엇이 오갔는지 기록이 남기 때문이다.

실습은 만드는 방법을 바꿔 가며 진행됐다. 처음엔 n8n 화면에서 손으로 칸을 잇고, 같은 흐름을 코딩 에이전트에게 CLI로 다시 만들게 했다. 마지막에는 메일 요약이라는 새 흐름을 만들고, 그 한가운데에 AI가 판단하는 칸을 넣었다. 그러고 나서 "이 업무를 맡길까?"를 판정문으로 정리했다.

> **오늘의 핵심 한 문장**
> 결과 화면은 셋 다 똑같이 "알림 보냄"일 수 있다. 차이는 **문제가 생겼을 때 어디를 열어 봐야 하는지**에서 난다. 그래서 맡기기 전에 다음 행동을 누가 정하는지부터 가른다.

| 순서 | 무엇에 답하는가 |
| --- | --- |
| 다음 행동은 누가 정하나 | 사람·워크플로·에이전트는 무엇이 다른가 |
| 규칙으로 적을 수 있는 일인가 | 무엇을 자동화 후보로 고르나 |
| 그래프와 실행 기록 | 흐름은 어떻게 생겼고, 지나간 일은 어디서 보나 |
| 도구를 고르는 다섯 질문 | 기능 수 말고 무엇으로 비교하나 |
| 코딩 에이전트에게 n8n 맡기기 | 에이전트가 만들 때 내가 확인할 곳은 어디인가 |
| IF 노드와 AI Agent 노드 | 규칙과 판단을 한 흐름에 어떻게 섞나 |
| 도입·보류·거절 판정문 | 맡길지 말지를 무엇으로 정하나 |
| 왜 필요한가 | 앞으로 무엇을 먼저 보게 되나 |

### 1-1. 다음 행동은 누가 정하나 — 현장학습 길 찾기

현장학습에서 박물관까지 가는 방법을 세 가지로 떠올려 보자.

- 선생님이 갈림길마다 "여기서 왼쪽" 하고 하나씩 알려 준다.
- 출발 전에 지도에 빨간 펜으로 길을 그어 두고, 아이들은 그 선만 따라간다.
- 아이들에게 "박물관으로 가"라는 목표만 주고, 표지판을 읽어 가며 길을 스스로 고르게 한다.

셋 다 박물관에 도착할 수 있다. 하지만 길을 잃었을 때 따져 볼 곳이 다르다. 첫째는 선생님의 말을, 둘째는 지도에 그은 선을, 셋째는 아이가 어떤 표지판을 보고 무엇을 골랐는지를 봐야 한다.

그래서 실제로는 **다음 행동을 정하는 주체에 따라 사람이 직접 지시, {% include term.html name="워크플로" %}, {% include term.html name="AI 에이전트" %}로 나뉜다.** 워크플로는 사람이 미리 그어 둔 순서와 조건대로 가고, 에이전트는 앞 단계 결과를 읽은 모델이 다음에 쓸 도구와 길을 고른다.

{% include figure.html src="/assets/images/who-picks-next-step/who-decides.svg" alt="다음 행동을 정하는 주체가 세 칸으로 나뉜 그림. 사람이 직접 지시하는 칸은 사람이 하나씩 정하고, 문제가 생기면 입력과 판단 기준을 본다. 워크플로 칸은 미리 이어 둔 그래프가 정하고, 어느 조건에서 다른 길로 갔는지를 본다. 에이전트 칸은 모델이 도구와 경로를 고르고 그 결과를 읽어 다시 고르는 반복이 있으며, 쥐여 준 도구, 도구 결과, 반복 한도, 승인 규칙을 본다. 아래 화살표는 오른쪽으로 갈수록 선택이 모델에게 넘어가고 확인할 곳이 늘어난다는 뜻이다" caption="그림 1. 오른쪽으로 갈수록 모델이 고르는 몫이 커지고, 문제가 생겼을 때 열어 볼 곳도 늘어난다" %}

"n8n은 워크플로 도구, Claude Code는 에이전트"처럼 도구마다 이름표를 붙이고 싶어지기 쉽다. 그런데 한 도구 안에서도 칸마다 고르는 쪽이 바뀐다. 그래서 이 구분은 **도구가 아니라 단계마다 붙인다.** 우열을 가리는 말도 아니다. 빨간 선을 따라가는 길은 다음에 똑같이 다시 가 보기 쉽고, 표지판을 읽는 길은 공사 중인 골목을 만나도 돌아갈 수 있다. 대신 표지판을 읽을 때마다 모델을 부르니 비용이 들고, 한 번 잘못 읽으면 그 뒤가 줄줄이 어긋난다.

### 1-2. 규칙으로 적을 수 있는 일인가 — 처음 온 급식 당번

새 급식 당번에게 일을 설명한다고 해 보자. "식판은 번호 순서로 놓아. 우유는 한 사람에 하나씩." 여기까지는 막힘없이 말할 수 있다. 그런데 "밥은 적당히 퍼 줘"라고 하려는 순간 당번이 묻는다. "적당히가 얼마예요?" 여기서 "그냥 알아서 해"라고 답하게 되면, 그 부분은 아직 규칙이 아니다.

그래서 실제로는 **자동화 후보는 "항상", "매번"으로 조건과 결과를 이어 적을 수 있는 일이다.** "새 문의에 접수 번호를 붙인다"는 적을 수 있지만 "친절하게 답한다"는 사람의 판단이 들어간다. 당번 이야기로 돌아가면, 기계는 "적당히"라는 말을 들어도 되묻지 않는다. **설명서에 없는 장면을 만나면 멈추거나, 엉뚱하게 지나간다.**

이 기준은 23회차의 PRD와 닮았다. 거기서도 모르는 칸은 `[결정 필요]`로 남기라고 했다. 둘 다 "아직 말로 못 적은 곳"을 먼저 찾아내는 일이다.

### 1-3. 그래프와 실행 기록 — 보드게임 판과 기록지

보드게임 판에는 칸이 있고, 칸 사이에 화살표가 있고, "출발" 칸이 있고, 주사위 결과에 따라 갈라지는 갈림길이 있다. 게임이 끝나면 기록지에 누가 어느 칸을 거쳐 어디서 멈췄는지가 남는다.

그래서 실제로는 **워크플로는 행동 칸(노드)과 연결선으로 그린 그래프이고, 실행할 때마다 칸별 입력과 출력이 실행 기록으로 남는다.** 여기서 말하는 노드는 수업 자료의 단원이 아니라 그래프의 칸이다.

| 그래프 요소 | 보드게임으로 치면 | n8n에서 |
| --- | --- | --- |
| 노드 | 칸 하나 | HTTP Request, Gmail, AI Agent 같은 행동 하나 |
| 연결선 | 칸 사이 화살표 | 앞 칸의 출력이 뒤 칸으로 가는 길 |
| {% include term.html name="트리거" %} | 출발 칸 | Manual Trigger(버튼), 정해진 시각, 새 메일 도착 |
| 분기 | 갈림길 | IF 노드의 true / false |
| 실행 기록 | 게임 기록지 | Executions 탭의 실행 한 건 |

첫 실습은 이 판에 칸 두 개만 놓는 것이었다. 버튼을 누르면 시작하는 Manual Trigger 뒤에, 위키백과의 공개 요약 {% include term.html name="API" %}를 부르는 HTTP Request를 이었다. 실행한 뒤 Executions 탭에서 그 실행 한 건을 열어, 칸마다 무엇을 받고 내보냈는지 따라가 보는 순서였다.

노드가 짚은 건 **실행 기록으로 알 수 있는 것과 없는 것의 구분**이었다. 요청·응답·상태 코드는 기록에 남는다. 하지만 그 데이터가 어디에 저장되는지, 내 계정이 어떤 권한을 가졌는지는 기록만 봐서는 모른다. 그리고 상태 코드는 기본으로 보이지 않는다. HTTP Request의 옵션에서 응답 헤더와 상태를 포함하도록 켜야 출력이 `statusCode`·`headers`·`body`로 나뉜다.

### 1-4. 도구를 고르는 다섯 질문 — 자유이용권과 기구별 표

놀이공원 입장권을 고를 때 "놀이기구가 몇 개냐"만 보면 손해 보기 쉽다. 자유이용권은 몇 번을 타든 한 장이고, 기구별 표는 탈 때마다 한 장씩 든다. 하루에 무엇을 몇 번 탈지에 따라 싼 쪽이 바뀐다.

그래서 실제로는 **자동화 도구도 기능 수가 아니라 내 업무에 대고 다섯 가지를 물어 비교한다.** 노드가 붙인 이름은 통제·관측·이식성·비용·데이터 경로인데, 놀이공원 질문으로 바꿔 보면 외우기 쉽다.

| 이름 | 놀이공원이라면 | 자동화 도구라면 |
| --- | --- | --- |
| 통제 | 기구를 멈추는 버튼은 누가 누르나 | 시작·멈춤·승인·쓰기를 누가 정하나 |
| 관측 | CCTV에 무엇이 찍히나 | 무엇을 받고, 무엇을 부르고, 어디서 실패했는지 남나 |
| 이식성 | 다른 놀이공원에서도 이 표를 쓸 수 있나 | 다른 환경으로 옮기면 무엇을 다시 챙겨야 하나 |
| 비용 | 한 장에 몇 번 탈 수 있나 | 무엇을 "한 번"으로 세어 돈을 받나 |
| 데이터 경로 | 내 가방은 어느 보관함을 거치나 | 입력·기록·결과·비밀값이 어느 서비스를 지나가나 |

비용 칸의 예가 놀이공원과 똑같았다. n8n은 워크플로 전체가 한 번 돌면 칸이 몇 개든 실행(execution) 1회로 센다. Zapier는 실행된 액션 단계마다 task 1개로 센다. 트리거 뒤에 액션이 4개인 흐름을 한 번 돌리면 n8n은 1, Zapier는 4다. **요금표 숫자를 나란히 놓고 비교하면 안 되는 이유**다.

표를 채우다가 공식 문서로 답이 안 되는 칸이 생기면, 그 칸에 "미확인"이라고 적으라고 했다. 그 빈칸이 바로 업무에 쓰기 전에 알아봐야 할 목록이 된다.

### 1-5. 코딩 에이전트에게 n8n 맡기기 — 설계도를 먼저 보여 줘

목수에게 책장을 맡기면, 좋은 목수는 나무를 자르기 전에 설계도를 먼저 보여 주고 "이대로 만들까요?" 하고 묻는다. 잘라 버린 나무는 되돌릴 수 없기 때문이다.

그래서 실제로는 **에이전트에게 워크플로를 만들게 할 때도, 만들기 전에 정의 파일({% include term.html name="JSON" %})의 칸과 연결을 보여 주고 확인받은 뒤에만 만들게 한다.** JSON에 적힌 주소로 실제 요청이 나가기 때문이다.

| 누가 | 하는 일 |
| --- | --- |
| 에이전트 | n8n {% include term.html name="CLI" %} 호출, 워크플로 정의 작성·생성·조회 |
| 나 | 만들기 전 JSON 검토와 승인, 만든 뒤 화면에서 다시 대조, 실행 근거 확인 |

에이전트에게 CLI 사용법을 알려 주는 공식 스킬도 있었다. 그리고 CLI로는 **새 실행을 시작할 수 없다.** 그래서 첫 실행은 n8n 화면에서 버튼으로 하고, 에이전트에게는 그 실행 기록을 찾아 상태와 응답을 보여 달라고 맡긴다. 실행까지 맡기고 싶으면 n8n이 제공하는 {% include term.html name="MCP" %} 서버를 붙이는 길이 있다고만 소개됐다.

API 키를 다루는 규칙도 분명했다. 키는 에이전트에게 보내는 요청문이나 화면 캡처에 남기지 않는다. Gmail·Gemini 같은 자격 증명도 에이전트에게 주지 않고 n8n 화면에서 내가 직접 등록한다.

### 1-6. IF 노드와 AI Agent 노드 — 신호등과 길 묻기

길을 건널 때 신호등은 언제나 같은 규칙으로 움직인다. 빨간불이면 멈추고 초록불이면 건넌다. 그런데 "이 동네 맛집이 어디예요?" 같은 질문은 신호등이 답해 줄 수 없다. 이럴 땐 지나가는 사람에게 물어야 하고, 대답은 누구에게 묻느냐에 따라 달라진다.

그래서 실제로는 **IF 노드는 미리 적어 둔 조건으로 길을 가르는 신호등이고, AI Agent 노드는 입력의 뜻을 해석해 쓸 도구를 고르는 길 묻기다.** 둘은 서로를 대신하지 않고, 한 흐름 안에서 함께 쓴다.

Manual Trigger에서 HTTP Request로 위키백과 요약을 받고, IF 노드가 title과 description이 모두 있는지 검사한다. true면 AI Agent 노드가 한 문장 요약을 만들고, false면 확인이 필요하다는 기록을 남긴다. 순서는 그래프가 정하고, AI Agent 칸 안에서만 모델이 판단한다. AI Agent에 붙이는 도구는 처음엔 읽기 전용만 두고, 보내기·고치기·지우기 같은 바꾸는 도구는 사람 승인을 거친 뒤에만 실행한다" caption="그림 2. 순서와 조건은 그래프가, 해석은 AI Agent 칸 하나가 맡는다" %}

둘을 가르는 가장 쉬운 시험은 **같은 입력을 두 번 넣어 보는 것**이다. 신호등은 같은 시각에 같은 색을 보여 준다. 길을 물으면 두 번째 사람은 다른 길을 알려 줄 수도 있다. 그래서 "응답에 제목이 비었나"처럼 값으로 답이 나오는 건 IF에, "이 메일이 무슨 이야기인가"처럼 읽어야 답이 나오는 건 AI Agent에 맡긴다. 나중에 기록을 볼 때도 IF 칸은 어느 길로 갔는지만, AI Agent 칸은 어떤 도구를 무엇으로 불렀고 무엇을 돌려받았는지까지 봐야 한다.

IF 노드의 false 쪽을 비워 두지 말라는 말도 있었다. 잘못된 입력이 여기서 걸러지는 것이니, 오류 기록이나 사람 확인 단계로 이어 두는 편이 낫다.

AI Agent에 도구를 붙일 때는 **처음엔 읽기만 하는 도구, 적은 호출 횟수**로 시작한다. 메일 보내기·고치기·지우기처럼 바깥 상태를 바꾸는 도구가 필요하면, 사람이 승인하거나({% include term.html name="HITL" %}) 별도 IF 조건을 통과한 뒤에만 실행되게 둔다. 22회차에서 도구에 권한을 줄 때 "읽기와 바꾸기를 나눈다"고 했던 것과 같은 이야기다.

### 1-7. 도입·보류·거절 판정문 — 확인한 것과 못 한 것

학급 회의에서 "교실에 화분을 둘까?"를 정한다고 해 보자. 누가 물을 줄지, 햇빛이 드는지는 확인했다. 그런데 방학 동안 누가 돌볼지는 아직 모른다. 그러면 "좋다/싫다"가 아니라 "방학 당번이 정해지면 다시 정하자"가 맞는 결론이다.

그래서 실제로는 **판정은 도입·보류·거절 셋 중 하나이고, 판정문에는 확인한 사실과 확인 못 한 사실을 따로 적고, 무엇이 확인되면 다시 판정할지를 남긴다.**

| 판정 | 화분 회의로 치면 |
| --- | --- |
| 도입 | 물 당번·햇빛·방학 돌보미까지 다 정해졌다 → 둔다 |
| 보류 | 두면 좋겠는데 방학 돌보미가 아직 없다 → 정해지면 다시 |
| 거절 | 교실에 햇빛이 아예 안 든다 → 지금 조건에선 안 둔다 |

판정 전에 업무를 한 문장으로 좁히라고 했다. "고객 지원 자동화"는 너무 넓어서 판정할 수가 없다. "매일 오전 새 공개 문의를 읽고 담당자가 확인할 세 줄 요약을 만든다"처럼 좁히면 읽는 대상, 결과를 받는 사람, 사람이 확인하는 지점이 드러난다.

판정이 사람마다 달라도 괜찮다고 했다. 같은 업무라도 누구는 실행 기록으로 충분하고, 누구는 데이터 보관 위치부터 확인해야 한다. 판정문에 근거를 적어 두면, 서로 다른 판정을 나란히 놓고 **무엇을 다르게 봤는지** 비교할 수 있다.

마지막 선택 심화는 셀프 호스팅이었다. 수업용 서버 대신 내 컴퓨터에 n8n을 띄우면 실행 환경·데이터 보관·업데이트·장애 대응을 내가 맡는다. 로컬에서 혼자 볼 때는 {% include term.html name="Docker" %}로 띄우고 데이터는 컨테이너 바깥 볼륨에 남기는 최소 구성을 보여 줬다. 구성은 규모가 아니라 **멈췄을 때 누가 고칠 수 있는가**에 맞춰 고른다고 했다.

### 1-8. 왜 필요한가

앞으로 "이거 AI로 자동화하면 되겠다"는 생각이 들면, 먼저 그 일을 처음 온 당번에게 설명해 볼 것 같다. "알아서"가 나오는 곳이 AI Agent 칸 후보이고, 나머지는 신호등 같은 규칙으로 적을 수 있다. **모델에게 맡기는 칸이 작을수록 문제가 생겼을 때 열어 볼 곳도 작아진다.**

또 하나는 결과 화면을 믿는 정도다. "알림을 보냈다", "요약을 시트에 적었다"는 결과만으로는 맞게 했는지 알 수 없다. 실행 기록에서 입력과 출력을 나란히 놓고 봐야 한다. 23회차에 답의 문장을 원문까지 거꾸로 따라갔던 것과 같은 습관이다.

## 2. 실습 / 코드 — n8n 흐름 두 개, 만드는 방법 세 가지

이날 한 실습은 노드 3(화면), 노드 4(코딩 에이전트), 노드 5(Gmail 요약)이다. 노드 4는 Claude Code 세션 기록이 남아 있어 자세히 적고, 노드 3과 노드 5는 했다는 사실만 적는다. 결과 숫자나 화면은 따로 남기지 않아 여기에 옮기지 않았다. 노드 6 판정문과 노드 7 Docker 실습은 하지 않았다.

### 2-1. 화면에서 두 칸 잇기 (노드 3)

n8n 화면에서 Manual Trigger와 HTTP Request를 이어 위키백과 요약을 받고, Executions 탭에서 실행 기록을 열어 봤다.

### 2-2. 코딩 에이전트로 만들기 (노드 4)

먼저 Claude Code에게 n8n CLI를 설치하고 연결을 확인하게 했다.

| 단계 | 결과 |
| --- | --- |
| 설치 | `npm install -g @n8n/cli` → `@n8n/cli` 0.22.0 |
| 확인할 것 | 앞에 `@n8n/`이 없는 `n8n-cli`는 이름이 같은 다른 패키지라서, `--version` 출력이 `@n8n/cli/`로 시작하는지 본다 |
| 접속 설정 | 이미 저장돼 있어 `login`은 하지 않음 |
| 연결 확인 | `workflow list --limit=1` → 기존 워크플로 하나가 돌아옴 |

그다음 "에이전트에게 맡기지 않고 혼자 하려면?"을 물어 단계별 설명을 받고, 다른 컴퓨터에서 직접 따라 해 봤다. 거기서 오류인 줄 알았던 화면이 있었는데, 사실은 `n8n-cli login`이 주소 입력을 기다리는 상태였다(4번 표 참고).

마지막으로 수업 자료에 실린 요청문을 그대로 넣었다. 연결 확인 → `wf.json` 작성 → **만들기 전에 노드와 연결 보여 주기** → 내가 확인했다고 답한 뒤 생성.

```json
{
  "name": "Wikipedia N8n 요약 가져오기",
  "nodes": [
    { "name": "Manual Trigger", "type": "n8n-nodes-base.manualTrigger" },
    { "name": "HTTP Request", "type": "n8n-nodes-base.httpRequest",
      "parameters": { "method": "GET", "url": "https://en.wikipedia.org/api/rest_v1/page/summary/N8n" } }
  ],
  "connections": { "Manual Trigger": { "main": [[{ "node": "HTTP Request" }]] } }
}
```

(실제 파일에서 `typeVersion`·`position`·`settings`는 줄였다.)

에이전트는 생성한 뒤 서버에서 다시 읽어 와 내가 확인한 내용과 같은지까지 대조했다. 그리고 **CLI에는 새 실행을 시작하는 명령이 없으니 화면에서 Execute workflow를 누르라**고 안내했다. 이후 화면에서 실행했다.

### 2-3. Gmail 요약을 시트에 정리하기 (노드 5)

Gmail에서 오늘 받은 메일을 가져와 AI Agent(Google Gemini Chat Model)로 요약하고 Google Sheets에 적는 흐름을 Claude Code에게 만들게 해서 돌렸다. 이 실습에서 노드가 짚은 확인 항목은 이렇다.

- 트리거가 수동인지, 정해진 시각인지
- "오늘 받은 메일"을 어떤 필터로 고르는지, 기본값이 **읽지 않은 메일만**이라 이미 읽은 메일이 빠질 수 있는지
- 간단히 보기 옵션 때문에 본문이 요약에 안 들어가지 않는지
- 메일을 보내거나 지우는 칸이 섞여 있지 않은지
- JSON에 키·비밀번호가 없는지
- 무료 등급 API에 메일 내용이 넘어간다는 점(데이터 경로)

## 4. 막혔던 점과 해결

앞의 두 줄은 노드 4를 하며 세션 기록에 남은 일이고, 나머지 세 줄은 자료를 읽으며 초보자가 막힐 만한 지점으로 골랐다.

| 막힌 지점 | 궁금했던 이유 | 정리한 답 |
| --- | --- | --- |
| 직접 따라 하던 컴퓨터에서 오류가 난 것처럼 보임 | 마지막 줄에 주소를 묻는 문장이 떠 있었다 | 오류가 아니라 `n8n-cli login`이 입력을 기다리는 상태였다. 설정이 이미 있어 `Ctrl + C`로 취소하면 됐다 |
| 같은 명령인데 표로 나오기도, JSON으로 나오기도 함 | 설명에는 "JSON이 나오면 정상"이라고 들었다 | 터미널에서 직접 치면 표로, 다른 프로그램이 받아 가면 JSON으로 나온다. 둘 다 연결된 것이다 |
| CLI로 만든 워크플로를 CLI로 돌릴 수 있나 | 만들기·조회가 되니 실행도 될 것 같다 | CLI에는 새 실행을 시작하는 명령이 없다. 첫 실행은 화면에서 하고, CLI로는 실행 기록을 조회한다 |
| 흐름에 AI 칸을 넣으면 에이전트가 되나 | 모델이 들어가니 에이전트 같았다 | 순서를 그래프가 정하면 여전히 워크플로다. 구분은 제품이 아니라 단계에 붙는다 |
| n8n과 Zapier 요금 비교 | 요금표의 숫자가 둘 다 "실행 횟수" 같았다 | n8n은 흐름 전체 1회, Zapier는 액션 단계마다 1개로 센다. 같은 숫자라도 세는 단위가 다르다 |
