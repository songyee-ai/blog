## 무엇을 만들었나

> 12.81초짜리 폰 영상에서 점 337만 개를 뽑아 3D 가우시안 스플랫으로 만들고, 형식만 바꿔 219MiB를 13.89MiB로 줄여 웹에 올렸다. 처음으로 WSL 우분투 안의 Claude Code가 코랩 GPU를 빌려 계산을 돌렸다.

16회차 3D 수업의 노드 8 과제다. 과제는 **남에게 보여도 되는 공간을 밖에서 하나 골라**, 수업에서 배운 길(찍기 → 점 → 알갱이 → 줄여서 올리기)로 올리고 주소를 제출하는 것이었다. 앞의 작업물들이 화면을 직접 만들거나 이미지를 생성했다면, 이번 것은 **실제 공간을 재서 옮긴 것**이다. 그리고 처음으로 계산을 내 노트북이 아니라 **에이전트가 빌린 코랩 GPU**에서 돌렸다.

## 1. 만들기 전 스케치

고른 곳은 **청주동물원 추모관**이다. 동물원에서 생을 마감한 동물들을 기억하는 공개 추모 공간으로, 곡면으로 휜 벽에 동물 이름을 새긴 나무 명패가 걸려 있고 아래에 국화가 놓여 있다.

공개해도 된다고 본 근거는 README에 세 줄로 적었다.

- 관람객에게 열려 있고 촬영이 허용된 **공개 추모 공간**이다
- 찍힌 건 명패와 헌화뿐이다. **사람 얼굴, 번호판, 문패, 서류는 없다** — 뽑은 사진 24장을 전부 확인했다
- 명패의 이름은 **동물의 이름**이고, 애초에 기억되라고 공개적으로 걸어 둔 것이다

## 2. 만드는 과정 — 프롬프트 기록

### 그 전에 — 환경부터 만들었다

수업 중에는 PowerShell로 우분투를 설치하고 그 안에 Claude를 깐 다음부터 따라가지 못했다. 그래서 다음 날 윈도우 쪽 Claude Code 세션에서 **"코랩 GPU로 바이브 코딩을 이어 가고 싶은데 어떻게 하면 되냐, 실행하지 말고 의견만"** 물었다.

- 처음에는 **코랩 MCP**(브라우저 노트를 에이전트가 옆에서 모는 방식)를 알아봤다
- 내가 **WSL + Colab CLI 방식과 장단점을 비교해 달라**고 했고, 브라우저 없이 터미널에서 GPU를 빌리는 CLI 쪽으로 정했다
- 막상 해 보니 전날 깔아 둔 `colab-cli`는 **구글 것이 아니라 GPU 실행 기능이 없는 다른 패키지**였다. 지우고 구글 공식 `google-colab-cli`(명령 `colab`)를 새로 깔았다
- 그 CLI도 첫 GPU 시험에서 죽었다. 딸려 오는 라이브러리 최신판이 이름을 바꾼 탓이라 **옛 판으로 고정**해서 넘어갔다
- VS Code를 WSL에 붙이는 동안 버튼 위치를 몰라 화면을 여러 번 찍어 보내며 물었다. 한 번은 "나 진짜 뭐 해야 하는지 모르겠어"라고 적었다
- 구글 인증은 내가 직접 했고, 무료 등급 **T4를 빌리고 반납하는 데 22초**였다

이때 "앞으로 설명에는 항상 쉬운 비유를 붙여 달라", "GPU는 무료 T4만 쓴다"를 메모리에 저장해 달라고도 했다.

### 시도 1 — 과제 전체를 한 번에 넘기기

WSL 쪽 새 세션에서 **과제 지침을 배경부터 전부 적은 긴 프롬프트**로 시작했다. 요점은 이랬다.

- "너는 이 수업 내용을 모르니까 배경부터 전부 적는다. 먼저 끝까지 읽고, 질문이 있으면 **코드를 쓰기 전에** 물어봐"
- 제일 먼저 수업 지침 묶음(`room-3d` 스킬)을 에이전트 스킬 폴더에 깔고 읽을 것
- 4단계 흐름, 단계별 판정 숫자, 조용히 실패하는 함정 목록, 뷰어 요구 사항, README 양식

노드가 단계마다 준 지시문 예시가 따로 있었지만 나는 그 순서로 나눠 시키지 않고, 이렇게 한 번에 넘겼다. Claude는 코드를 짜기 전에 질문 세 개를 돌려줬다. 영상이 8.8초라 짧은데 어떻게 할지(A 그대로 / B 다시 찍기 / C 일단 재 보고 결정), 갤러리가 공개해도 되는 곳인지, 저장소 이름을 뭘로 할지였다. 나는 **"C로 가보자"**라고 했다.

### 그 사이 — 갤러리에서 추모관으로

Claude는 T4를 빌려 GPU를 확인하고(bf16이 없는 카드라 **fp16 조건 확인**), 설치하고, 모델 4.91GB를 받는 동안 뷰어 페이지를 먼저 만들었다. 갤러리 영상의 카메라 퍼짐은 **0.3365**로 통과했다. 영상이 가로인 줄 알았는데 **회전 표시가 붙은 세로 영상**이었다는 정정도 스스로 했다.

그런데 갤러리 영상엔 전시 작품이 여러 장면에 또렷이 찍혀 있어서 공개는 보류하자는 의견이 나왔다. 그래서 영상을 바꿨다.

> video2.mp4로 영상을 바꿔서 다시 진행해 봐 줘. 이건 청주동물원의 추모관에서 촬영한 영상이야.

12.81초, 1080×1920 세로, 번진 사진 0장. 복원은 **10.0초, 최대 GPU 메모리 6.74GB**였고 카메라 퍼짐은 **0.1699**로 기준선 0.1을 넘겼다. 갤러리보다 낮은 이유는 하늘과 나뭇잎이 아주 먼 점으로 잡혀 장면 대각선이 커졌기 때문이다.

### 시도 2 — 뷰어를 열어 보고 고치기

알갱이 파일을 만들고 로컬에서 뷰어를 열었다. 내가 본 것을 세 줄로 적어 보냈다.

- 단계 목록이 전부 초록색이다
- **명패가 좌우 반전된 것 같다.** '허'가 'ㅏㅎ'처럼 보인다
- 알갱이 크기를 말해 달라는데 뭘 보고 말해야 할지 모르겠다

좌우 반전은 Claude가 숫자로 먼저 가렸다. **좌표는 거울이 아니었다**(부호 뒤집기 행렬식이 +1). 문제는 뷰어의 시작 카메라가 **촬영한 쪽에서 92도 어긋나 벽 옆에서** 보고 있었던 것이다. 그래서 카메라 24대의 평균 자리와 시선으로 **"촬영 자리에서 시작"**하게 바꿨다.

### 시도 3 — 알갱이 크기 K를 눈으로 고르기

기본값 K=1.4는 명패 글씨가 뭉개졌다. 하늘과 나무 때문에 장면의 가장 긴 변이 8.04에서 11.995로 부풀어 반지름도 같이 커졌기 때문이다. Claude가 K를 바꾼 파일 여러 개를 만들어 줬는데, 나는 처음에 **로컬 주소 하나만 열어 보고** "여전히 슬라이더를 최소로 내려야 글씨가 또렷하다"고 했다가 멈췄다.

> 아 잠깐만. 내가 로컬 주소만 켜서 하나만 확인했는데? 뭐 파일이 다양해?

파일들을 나란히 열어 보고 나서야 설명이 와닿았다. "구멍이 뚫린다"는 말은 이해 못 했지만 **0.4가 제일 선명**했고, 0.3부터는 다른 의미로 번져 보였다. 같은 명패가 두세 겹 겹쳐 보이는 것도 내 눈으로 찾았다. 사진 24장의 깊이가 조금씩 어긋나 쌓인 것이고, 알갱이가 적당히 크면 그 어긋남을 덮어 준다. 그래서 **0.4와 0.6 사이**가 좋겠다고 했고, 추천받은 **K=0.5**로 정했다.

### 시도 4 — 형식 비교, 공개, 정리

형식 셋으로 변환해 크기를 쟀다. 네 파일 모두 알갱이는 3,377,115개로 같았다.

| 형식 | 크기 | 알갱이당 바이트 | 100MiB 한계 |
| --- | ---: | ---: | :---: |
| `.ply` | 219.01 MiB | 68.00 | 초과 |
| `.compressed.ply` | 52.44 MiB | 16.28 | 통과 |
| `.spz` | 21.29 MiB | 6.61 | 통과 (뷰어에서 안 열림) |
| **`.sog`** (올린 것) | **13.89 MiB** | **4.31** | 통과 |

점을 줄일 필요가 없었다. 형식만 바꿔 깃허브 한계의 7분의 1이 됐다. 공개 저장소로 올리기로 고르고, Claude가 비교용 파일까지 넣어 둔 걸 보고 **과제 양식대로 네 가지(`index.html`, `scene.sog`, `README.md`, `shots/viewer.png`)만 남겨 달라**고 했다. `.nojekyll`이 뭐냐고도 물었다. 깃허브 페이지가 파일을 가공하지 않고 그대로 내보내게 하는 빈 파일이다. 작업 폴더는 **중간 산물만 지우는** 쪽을 골라 537MB를 131MB로 줄였다.

### 이틀 뒤 — 남의 폰에서 잰 값

과제 양식의 마지막 빈칸은 폰에서 첫 화면까지 걸린 시간이었다. 내 폰은 처음 7초, 다시 열면 3초 이내였다. 이틀 뒤 **다른 사람 폰에서 약 5초** 걸렸다는 값을 받아 README를 채웠다.

## 4. 코드에서 배운 부분

### 4-1. 점을 알갱이로 바꿀 때는 "되돌려서" 넣는다

```python
xyz[:, 1] *= -1                     # Y가 아래인 모델 → Y가 위인 웹
xyz[:, 2] *= -1
f_dc = (color / 255.0 - 0.5) / 0.28209479177387814   # 색 → 0차 구면 조화 계수
opacity = math.log(0.9 / (1 - 0.9))                  # 0.9 → 약 2.1972
radius = K * longest_side / math.sqrt(N)              # K=0.5
log_radius = math.log(radius)                         # 크기는 로그로
```

그리는 쪽은 색 칸에 0.2821을 곱하고 0.5를 더해 색을 만들고, 불투명도 칸엔 시그모이드를, 크기 칸엔 지수를 씌운다. 그래서 넣을 때는 **거꾸로 계산한 값**을 넣는다. 거스름돈을 받으려면 물건값을 알아야 하는 것처럼, 받는 쪽이 무슨 계산을 할지 알아야 맞는 값을 줄 수 있다. 확인은 곱셈으로 했다. 값 17개 × 4바이트 = 68바이트가 README 숫자와 정확히 맞았다.

### 4-2. 판정 숫자를 코드가 먼저 찍게 한다

```
카메라 퍼짐 2.952  /  장면 대각선 17.370  =  0.1699   (기준선 0.1 → 통과)
```

화면을 열기 전에 **걸어 다니며 찍었는지**가 숫자 하나로 갈린다. 좌우 반전 소동 때도 Claude는 화면을 보고 추측하지 않고 부호 뒤집기의 행렬식(+1이면 거울이 아님)부터 계산했다. 체온계가 있으면 이마를 짚어 보기 전에 체온부터 재는 것과 같다.

### 4-3. 뷰어가 스스로 어디까지 됐는지 말하게 한다

단계 다섯(라이브러리 → 렌더러 → 파일 받기 → 알갱이로 풀기 → 크기 재기)을 화면에 띄우고, 크기를 잴 때는 three.js의 `Box3.setFromObject`가 **빈 상자를 준다**는 사실까지 화면에 적어 두었다(그림 2). 알갱이 덩어리는 일반 물체가 아니라서 Spark가 주는 자로 따로 재야 한다. 검은 화면 하나만 남기는 대신 "어디서 멈췄는지"를 남기면, 막혔을 때 볼 줄이 바로 정해진다.

## 5. 막혔던 점과 해결

| 막힌 지점 | 원인 | 해결 방법 |
| --- | --- | --- |
| 수업 중 우분투에 Claude를 깐 뒤로 진행 못 함 | 윈도우에서 Colab CLI를 쓰려면 WSL을 거쳐야 하고, 설정할 곳이 여럿이었다 | 다음 날 Claude에게 방법을 비교받고 WSL + CLI로 정해 하나씩 설정 |
| 깔아 둔 `colab-cli`로 GPU가 안 돌 것 같음 | 이름이 비슷한 **다른 사람의 패키지**였고 GPU 실행 기능이 없었다 | 지우고 구글 공식 `google-colab-cli` 설치 |
| Colab CLI가 첫 GPU 시험에서 죽음 | 딸린 라이브러리 최신판이 클래스 이름을 바꿈(구글 저장소에 알려진 문제) | 그 라이브러리만 **옛 판으로 고정** |
| 모델 받기에서 명령이 끊길 위험 | `colab exec`는 기본 30초만 기다리는데 모델 받기는 약 3분 | 대기 시간을 늘리고, 끝나면 매번 `colab stop`으로 반납 |
| bf16이면 메모리 초과 | T4에는 bf16 회로가 없어 계산표를 통째로 펼침(31.18GB) | 처음부터 **fp16**으로 못 박음 → 6.74GB |
| 명패가 좌우 반전돼 보임 | 좌표 문제가 아니라 시작 카메라가 촬영 방향에서 92도 어긋나 있었음 | 카메라 24대 평균 자리·시선으로 **촬영 자리에서 시작** |
| 기본 K=1.4에서 글씨가 뭉개짐 | 하늘·나무의 먼 점 때문에 장면 최장변이 11.995로 부풀어 반지름도 커짐 | 여러 K를 나란히 보고 **0.5** 선택 (더 낮추면 명패가 여러 겹으로 보임) |
| `.spz`가 뷰어에서 안 열림 | 변환 도구는 gzip 없이 SPZ 4판으로 쓰는데, Spark는 gzip을 기대하고 4판을 모름 | 못 고침. 크기만 표에 남기고 저장소에서 뺌 |
| `.ply` 219MiB는 깃허브에 안 올라감 | 파일 하나 100MiB 제한 | 점은 그대로 두고 `.sog`로 변환 → 13.89MiB |
