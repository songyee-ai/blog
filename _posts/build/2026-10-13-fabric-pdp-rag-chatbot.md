## 무엇을 만들었나

> 침구·커튼 상세페이지를 만들기 전에 디자이너와 MD가 고시 원문을 근거로 확인할 수 있게 만든 터미널 RAG 챗봇. 자료를 찾아 건네자 근거와 맞는 답이 11개 중 1개에서 8개로 늘었고, '그대로 인용하라' 한 줄이 왜곡을 없앤 대신 거절을 약하게 만들었다.

23회차의 과제다. 내가 고른 분야의 자료를 모아 {% include term.html name="RAG" %} 챗봇을 만드는 것이었다. 분야는 **홈패브릭 상세페이지**로 잡았다. 침구 상세페이지에 무엇을 꼭 적어야 하는지, 커튼도 유해물질 시험성적서가 있어야 하는지, "항균 99.9%"라고 써도 되는지 같은 질문은 답이 고시에 있다. 이 챗봇은 그 고시 문장을 찾아 근거로 보여 주고, 확인할 항목을 체크리스트로 뽑아 준다.

앞의 작업물들은 화면을 만들거나 모델 하나를 시험하는 쪽이었다. 이번에는 처음으로 **내 문서를 모델에게 건네서 답하게 하고, 그 답이 정말 근거와 맞는지 숫자로 재 봤다.**

**직접 해보기** → 배포 주소는 없다. 내 컴퓨터에서 Ollama를 켜 두고 터미널에서 `node src/ask.mjs "질문"`으로 돌린다. 실행 방법은 저장소 README에 있다.

**코드 보기** → [github.com/songyee-ai/fabric-pdp-rag-chatbot](https://github.com/songyee-ai/fabric-pdp-rag-chatbot)

## 1. 만들기 전 스케치

RAG를 한 문장으로 하면 **"모델에게 답하기 전에 오픈북 시험을 보게 하는 것"**이다. 모델이 기억에 기대 답하면 그럴듯하게 지어내기 쉽다. 그래서 질문이 오면 먼저 내 자료에서 관련 문단을 찾아 시험지 옆에 펼쳐 주고, 그걸 보고 답하게 한다.

자료를 찾는 방법은 {% include term.html name="임베딩" %}이다. 문단마다 숫자 768개짜리 {% include term.html name="벡터" %}로 바꿔 두면, 뜻이 비슷한 문장끼리 숫자도 비슷해진다. 질문도 같은 방식으로 바꾸고 가장 가까운 문단 3개를 고른다. 가까운 정도는 {% include term.html name="코사인 유사도" %}로 잰다.

{% include figure.html src="/assets/images/fabric-pdp-rag-chatbot/flow.svg" alt="챗봇의 흐름. 미리 한 번, 고시 4개 원문을 청크 17개와 품목·직무 메타데이터로 나누고 벡터 17×768로 바꿔 둔다. 질문할 때마다, 질문을 EmbeddingGemma로 벡터로 바꾸고 코사인 유사도로 가까운 청크 3개를 고른다. 0.55 미만이면 경고를 붙인다. 고른 청크는 두 갈래로 간다. 체크리스트는 프로그램이 메타데이터로 만들고, 답변은 qwen3.5:2b가 시스템 메시지와 근거 3개, 그대로 인용 지시를 받아 만든다. 답변은 같은 모델이 6칸 JSON으로 채점한다" caption="그림 1. 질문 하나가 지나가는 길 — 파란 칸은 프로그램, 노란 칸은 LLM" %}

자료는 공개된 고시 4개다. 전자상거래 상품정보제공 고시, 생활용품 안전기준 중 가정용 섬유제품, 표시·광고 실증 고시, 부당한 표시·광고 유형 고시. 이것을 의미 단위로 잘라 {% include term.html name="청크" %} 17개(DC-001~DC-017)를 만들었다.

모델은 둘 다 내 컴퓨터에서 돈다. 임베딩은 EmbeddingGemma-300m을 8비트로 줄인 판본({% include term.html name="양자화" %})을 Node.js에서 직접 돌리고, 답변은 {% include term.html name="Ollama" %}에 올린 qwen3.5:2b가 쓴다. 답변은 작은 {% include term.html name="LLM" %}이 쓰지만, **근거 표시와 체크리스트는 LLM에 맡기지 않는다**는 원칙을 기획 때 정했다.

## 2. 만드는 과정 — 프롬프트 기록

이번 과제는 단계가 많아서, Claude Code와 단계마다 무엇을 할지 정하고 결과를 확인하며 진행했다.

### 시도 1 — 기획 인터뷰: 질문은 한 번에 하나씩

주제만 정해 두고 Claude Code에 기획을 같이 하자고 했다. 조건을 몇 개 걸었다.

- 질문은 **한 번에 하나씩** 할 것
- 아직 정하지 않은 것은 채우지 말고 `결정 필요`로 남길 것
- 확인하지 않은 주소·규정·수치는 지어내지 말 것
- 내가 요청하기 전에는 코드를 쓰지 말 것

인터뷰에서 내가 정한 것은 이렇다.

- **사용자는 디자이너와 MD.** 상세페이지를 만들고 등록하기 **전에** 검토하는 용도로 범위를 좁혔다
- **청크마다 메타데이터 두 칸**(`audiences` 직무, `product_types` 품목)을 따로 둔다. 원문에서 판단이 안 되면 **비워 두고, 임의로 채우지 않는다**
- **범위 밖 질문 4종**을 정했다. 러그처럼 다른 품목, 반품 배송비처럼 다른 업무, 배너 색감처럼 고시가 답할 수 없는 것, 날씨처럼 아예 무관한 것
- 채점표(루브릭)에 **"검색 근거 적합도"**를 하나 더 넣었다. 답만이 아니라 검색이 맞는 자료를 찾았는지도 따로 재기 위해서다

여기까지 정리한 기획서는 저장소에 `PRD.md`로 남겼다.

### 시도 2 — 원문을 자르고 대조하다

고시 4개를 청크로 자른 뒤, **청크와 법령 원문을 나란히 놓고 한 줄씩 대조**했다. 그러다 DC-010과 DC-011에서 **본문 속 주석 표시(`1)`, `3)`)가 빠지고 주석 문장만 끝에 붙어 있는 것**을 찾았다. 그러면 어느 칸에 달린 주석인지 알 수 없다. 그래서 "주석은 본문과 함께 넣는다"는 규칙을 더하고, 비슷한 문제가 있던 DC-009(표시와 문장이 둘 다 빠짐)·DC-013(문장이 빠짐)까지 고쳤다.

청크마다 직무·품목을 붙이는 분류표도 이 단계에서 채웠다.

### 시도 3 — 임베딩과 검색

임베딩 모델은 내 컴퓨터에 직접 받아 처음 돌려 봤다. 모델 파일(약 309MB)은 첫 실행 때 내려받는다.

그다음 질문마다 어떤 청크가 몇 점으로 뽑히는지 살펴봤다. 아래는 LLM 없이 **검색만** 돌린 결과다.

{% include figure.html src="/assets/images/fabric-pdp-rag-chatbot/screen-search.png" alt="검색만 돌린 터미널 출력. 침구 상세페이지 상품정보 항목 질문에는 DC-001 침구·커튼 품목별 정보제공 항목이 0.761로 1위, DC-005가 0.669, DC-009가 0.665. 내일 날씨 질문에는 관련 자료가 약하다는 경고와 함께 DC-003이 0.451로 1위" caption="그림 2. 검색만 돌린 결과 — 관련 있는 질문은 0.7 안팎, 날씨는 0.45로 경고가 붙는다 (실제 출력 글자를 터미널 모양으로 다시 그렸다)" %}

고정 질문 11개로 돌려 보니, "통이미지"라고 물었는데 청크에는 "문자(Text)"와 "사진"으로 적혀 있어도 맞는 청크(DC-006)를 1위로 찾았다. 같은 단어가 없어도 뜻으로 찾는다는 뜻이다. 다만 한계도 보였다. 범위 밖 질문 4개 중 점수가 0.55 아래로 떨어진 건 날씨 하나뿐이었다. 러그·반품·배너 질문은 0.55를 넘겨 경고 없이 지나갔다. 점수 하나로는 범위 밖 질문을 막을 수 없다는 뜻이다.

### 시도 4 — 답변 붙이기: 인사 한 마디에 3분

검색 결과를 qwen3.5:2b에게 넘겨 답하게 붙였다. 첫 시험에서 짧은 인사에도 답이 3분을 넘겼다. 이 모델은 **생각 과정(thinking)이 기본으로 켜져 있어서**, 대답하기 전에 혼잣말을 3,700{% include term.html name="토큰" %} 넘게 쓰고 있었다. 생각을 끄니(`think: false`) 답이 몇 초로 줄었다.

### 시도 5 — 체크리스트는 LLM에게 맡기지 않았다

처음 요청에 "검색된 근거를 바탕으로 답변과 확인할 사항을 제공합니다"를 넣었다. 확인할 사항을 어떻게 만들지 정할 때, 근거 표시와 같은 원칙(LLM에 맡기지 않는다)을 체크리스트에도 적용하기로 했다. 그래서 **체크리스트는 프로그램이** 만든다. 질문에서 품목 단어를 찾고, 뽑힌 청크의 메타데이터를 읽어 품목별·직무별로 묶기만 한다. 고정 질문 11개로 돌려 본 결과, 품목이 섞인 체크리스트는 **0개**였다. 실제로 답변 쪽에서는 2B 모델이 고시의 항목 목록을 옮기다 "제조국"을 빠뜨린 적이 있다.

### 시도 6 — 비교와 실험

같은 질문 11개를 RAG 없이와 RAG로 각각 돌리고, 답이 근거 원문과 맞는지 한 줄씩 대조한 표를 만들었다. 그 표를 보고 **무엇을 실험할지, 결과를 채택할지**를 골랐다.

{% include figure.html src="/assets/images/fabric-pdp-rag-chatbot/screen-compare.png" alt="같은 질문, 통이미지 상세페이지에 인증 정보를 이미지 안에 넣어도 되는지에 대한 두 답. RAG 없이는 가능하다고 답하고 인증 정보를 인증번호나 비밀번호로 잘못 이해했다. RAG는 DC-006을 인용해 인증·허가 정보는 문자로 표시해야 하고 사진으로 대체할 수 없다고 답했다" caption="그림 3. 같은 질문, 정반대의 답 — 왼쪽은 자료 없이, 오른쪽은 고시를 찾아서 (실제 출력 글자를 옮겨 다시 그렸고, 왼쪽의 긴 답은 줄였다)" %}

그림 3은 RAG가 왜 필요한지 가장 잘 보여 준다. 자료 없이 물으면 모델은 **"가능합니다"**라고 자신 있게 틀렸고, 인증 정보를 비밀번호로 알아들었다. 자료를 건네자 고시 문장을 그대로 가져와 **"사진으로는 대체할 수 없다"**고 답했다. 시간도 오히려 RAG 쪽이 짧았다. 자료가 있으면 4~12초에 끝나는데, 자료가 없으면 아는 걸 늘어놓느라 대부분 30~44초가 걸렸다.

그다음 실험에서 시스템 메시지({% include term.html name="메시지 역할" %} 중 system)에 한 줄을 더 넣었다. **"자료의 문장을 바꾸지 말고 그대로 인용해 답합니다."** 결과가 두 방향으로 갈렸다.

{% include figure.html src="/assets/images/fabric-pdp-rag-chatbot/experiments.svg" alt="두 번의 비교 결과 막대그래프. 자료 없이 대 RAG에서 근거와 맞는 답은 1/11에서 8/11, 범위 밖 질문 거절은 1/4에서 3/4. 인용 지시 전과 후에서 근거를 왜곡하지 않은 답은 4/7에서 7/7, 범위 밖 질문 거절은 3/4에서 2/4로 줄었다. LLM 판정은 이 변화를 6/7에서 6/7로 보고 잡지 못했다" caption="그림 4. 두 번의 비교 — 인용 지시는 하나를 얻고 하나를 잃었다" %}

왜곡은 7개 중 3개에서 0개가 됐고, 범위 밖 거절은 4개 중 3개에서 2개로 줄었다. 질문 7개와 4개를 한 번씩 돌린 결과라 작은 차이는 우연일 수 있다는 점도 함께 적어 두었다. 나는 **인용 지시를 채택**했고, 약해진 거절은 알려진 한계로 기록했다. 거절을 되살리려고 지시문을 한 번 더 고쳐 봤지만 2/4 그대로라 **되돌렸다.**

## 3. 완성 화면

{% include figure.html src="/assets/images/fabric-pdp-rag-chatbot/screen-answer.png" alt="커튼도 유해물질 시험성적서가 있어야 판매할 수 있는지 묻는 질문의 전체 출력. 검색 결과 3개, DC-010을 그대로 인용한 답변, 품목 공통과 커튼으로 나뉜 체크리스트, 근거 3개와 원문 주소, 같은 모델의 판정 grounded 통과, cited 실패, 점수 60, 그리고 검색 1.0초, 답변 12.1초, 판정 9.0초" caption="그림 5. 질문 하나의 전체 출력 — 검색, 답변, 체크리스트, 근거, 판정, 시간 순서 (실제 출력 글자를 옮겨 다시 그렸고, 긴 주소는 줄였다)" %}

한 번 물으면 여섯 덩어리가 순서대로 나온다.

- 🔎 **검색 결과** — 어떤 청크를 몇 점으로 골랐는지
- 💬 **답변** — 고른 청크의 문장을 그대로 인용한 답
- ✅ **확인할 사항** — 프로그램이 만든 체크리스트. 품목 공통과 커튼으로 나뉘고, 직무가 붙는다
- 📚 **근거** — 모델에게 넘긴 자료와 원문 주소. 답에 ID가 적힌 자료에는 ✓
- ⚖ **판정** — 같은 모델이 자기 답을 채점한 결과
- ⏱ **시간** — 단계별로 걸린 시간

판정 줄을 보면 답에 `[DC-010]`이 분명히 적혀 있는데 `cited ✗`(인용 안 함)로 채점했다. 2B 모델이 자기 답을 채점하는 {% include term.html name="LLM-as-a-Judge" %}는 이 정도로 거칠다. 그래서 화면에도 "거친 신호"라고 붙여 두었고, 실험의 최종 판단은 판정이 아니라 원문 대조 표를 보고 내렸다.

## 4. 코드에서 배운 부분

### 4-1. 체크리스트는 스티커만 보고 분류한다

도서관 사서가 책 등에 붙은 색깔 스티커만 보고 책을 칸에 꽂는 모습을 떠올리면 된다. 사서는 책 내용을 해석하지 않으니, 스티커가 맞으면 엉뚱한 칸에 꽂을 일이 없다.

```json
{ "id": "DC-005", "audiences": ["디자이너"], "product_types": ["공통"] }
```

실제로는 청크마다 이런 표시를 붙여 두고, 프로그램이 질문 속 품목 단어(`이불`, `베개`, `암막`…)와 이 표시만 보고 묶는다. LLM은 체크리스트에 손을 대지 않는다. 표시가 비어 있으면 억지로 채우지 않고 `[분류 확인 필요]` 칸에 따로 둔다. 품목 섞임이 0이었던 건 모델이 잘해서가 아니라 **모델에게 이 일을 시키지 않아서**다.

### 4-2. 온도를 0으로 둬도 입력이 바뀌면 답이 바뀐다

이 챗봇은 {% include term.html name="temperature" %}를 0으로 둔다. 그런데 같은 질문을 같은 설정으로 두 번 돌렸더니 인용 개수가 한 번은 2/3, 한 번은 3/3이었다. `temperature` 0은 **입력이 같을 때** 같은 답을 내라는 뜻이다. 그런데 프롬프트에는 **"현재 시각은 ○○이다"** 문장이 들어 있어서, 실행할 때마다 입력이 달랐다. 날짜 칸이 매번 다른 시험지를 받는 셈이다.

```javascript
const EXPERIMENT_NOW = new Date("2026-10-13T18:00:00+09:00");
```

그래서 실험을 돌릴 때만 시각을 이렇게 고정했다. 같은 입력을 두 번 돌려 같은 답이 나오는 것도 확인했다. 그래야 실험 A와 B의 차이가 내가 바꾼 한 줄 때문인지 확인할 수 있다. 평소에 물을 때는 진짜 현재 시각을 넣는다. 그리고 한 번의 차이는 개선이라고 부르지 않기로 했다.

### 4-3. 한 줄짜리 지시가 한 일과 치른 값

```javascript
const QUOTE = "자료의 문장을 바꾸지 말고 그대로 인용해 답합니다.";
```

전화 연락망으로 말을 전하면 몇 사람만 거쳐도 뜻이 바뀐다. 쪽지를 그대로 읽어 주면 바뀌지 않는다. 2B 모델은 고시 문장을 요약하거나 자기 말로 바꾸다가 **"~하지 않는다"를 "~한다"로 뒤집곤 했다.** 그대로 옮기게 하자 뒤집을 틈이 없어졌다.

값도 치렀다. 첫째, "인용해서 답하라"를 너무 잘 따라서 답이 없는 질문에도 뭔가를 인용했다. 프롬프트에 있던 현재 시각 문장까지 인용한 적이 있다. 둘째, 답이 질문에 덜 직접적이 됐다. "써도 되나요?"에 맞는 원문을 인용하긴 하지만 "된다/안 된다"로 답하지는 않았다. 그리고 이 변화는 LLM 판정으로는 보이지 않았다(그림 4의 6/7 → 6/7). **프롬프트 한 줄을 바꾸면 무엇이 좋아지고 무엇이 나빠졌는지를 따로따로 재야 한다**는 걸 여기서 배웠다.
