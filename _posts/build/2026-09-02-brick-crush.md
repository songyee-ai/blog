## 2. 만드는 과정 — 프롬프트 기록

### 페어프로그래밍은 이렇게 굴러갔다

{% include figure.html src="/assets/images/brick-crush/pair.svg" alt="네비게이터와 드라이버가 제안과 결과를 주고받는 구조도" caption="그림 2. 역할을 정해 두고 시간마다 교대한다" %}

마이크와 화면을 공유한 채, 정해진 시간마다 **드라이버**와 **네비게이터**를 바꿔 가며 진행하는 방식이었다. 이 벽돌깨기는 **네비게이터인 팀원이 게임과 아이템 구성을 제안하고, 드라이버인 내가 만든** 구간이다.

그래서 아래 기록에는 한계가 하나 있다. **말로 오간 제안과 지적은 남아 있지 않다.** 키보드 앞에서 일어난 일만 기록으로 남는데, 페어프로그래밍에서 절반은 말로 지나간다.

### 역할을 바꿨을 때 — 내가 네비게이터였던 판

같은 실습의 다른 구간에서는 역할이 반대였다. 팀원이 드라이버, 내가 네비게이터.

내가 제안한 건 **카드 짝맞추기**였다. 뒤집어서 같은 그림 두 장을 찾는 그 게임. 여기에 조건을 하나 붙였다 — **귀여운 동물 그림이 카드에 그려졌으면 좋겠다.**

그런데 만들기 시작하면서 바로 걸렸다. 일러스트를 그리거나 구해 오는 시간까지 계산하면 실습 시간 안에 게임이 돌아가지 않는다. 그래서 **동물 이모지로 대체하자고 조정했다.** 그림 파일이 필요 없으니 카드 뒤집는 로직에만 시간을 쓸 수 있었다.

{% include figure.html src="/assets/images/brick-crush/pair-cardmatch.png" alt="동물 이모지가 그려진 4×5 카드 짝맞추기 게임 화면. 맞춘 카드는 초록색으로 남아 있다" caption="그림 3. 팀원이 드라이버로 만든 결과 — 일러스트 대신 동물 이모지로 갔다" width="52%" %}

네비게이터를 해 보니 신경 쓰는 곳이 달랐다. 드라이버일 때는 "어떻게 만들지"를 붙잡고 있었는데, 네비게이터일 때는 **무엇을 포기할지**를 먼저 정해야 했다. 귀여운 동물 일러스트를 끝까지 고집했으면 카드가 한 장도 안 뒤집힌 채로 시간이 끝났을 것이다. 만들고 싶은 것과 시간 안에 되는 것 사이에서 한 칸 물러서는 판단 — 그게 네비게이터의 몫이었다.

### 시도 1 — 설계안 전문 (11:37)

> 로컬 game_crush 와 깃허브 레지스토리 game_crush를 연결하고 거기에 벽돌깨기 게임을 만들거야. 아래의 내용으로 진행해줘.
>
> **모바일 벽돌깨기 게임 제작 요청**
>
> 단일 HTML 파일로 동작하는 벽돌깨기 게임을 만들어주세요. 아래 사양을 그대로 따라주시고, **명시되지 않은 부분은 판단에 맡깁니다.**
>
> **기술 조건**
> - 단일 `.html` 파일 하나로 완결. 외부 라이브러리, 빌드 도구, 에셋 파일 없음
> - 플레이 영역은 `<canvas>` + Vanilla JS. HUD와 오버레이는 DOM + CSS
> - 이미지·사운드 파일 사용 금지. 모든 그래픽은 캔버스 드로잉으로 해결
> - 세로 화면(모바일) 우선. 데스크톱에서는 중앙에 세로 비율을 유지한 채 배치
> - 최고 점수만 `localStorage`에 저장
>
> **게임 컨셉** — 클래식 벽돌깨기에 아이템 드롭과 내구도 벽돌을 더한 스테이지 진행형.
>
> **1. 조작 (가장 중요)**
> 모바일에서 편한 조작이 이 게임의 성패를 가릅니다. 다음을 반드시 지켜주세요.
> - 화면 어디를 잡아도 패들이 반응. 패들을 정확히 짚을 필요 없음
> - 절대 위치가 아닌 상대 이동. 손가락이 20px 움직이면 패들도 그만큼 이동. 화면 왼쪽 끝을 터치했다고 패들이 순간이동하면 안 됨
> - 감도 배율 1.5배. 엄지 하나로 화면 끝에서 끝까지 갈 수 있어야 함
> - 조작 인식 영역은 캔버스뿐 아니라 하단 여백까지 포함. 손가락이 공을 가리는 걸 최대한 피함
> - 캔버스와 조작 영역에 `touch-action: none`, `user-select: none` 필수. 없으면 드래그할 때마다 페이지가 스크롤됨
> - 뷰포트 메타 태그로 확대 방지
> - 개발·테스트 편의를 위해 마우스 드래그와 좌우 방향키도 동일하게 지원
>
> **2. 화면 구성** — 세로로 위에서부터 HUD → 플레이 영역 → 조작 여백.
>
> HUD (한 줄): 좌측에 남은 목숨을 하트 아이콘 3개로, 중앙에 `STAGE 1`, 우측에 현재 점수 / 최고 점수
>
> 플레이 영역
> - 화면 폭 전체, 세로 비율 3:4
> - 좌·우·상단은 벽, 하단만 열려 있음
> - 벽돌은 위쪽 60%에만 배치. 아래 40%는 공이 노는 공간. 이 여백이 없으면 반응할 시간이 없어 짜증만 남음
>
> 요소별 표현
> - 벽돌: 둥근 모서리 사각형. 색으로 내구도 구분 — 1은 연한 하늘, 2는 파랑, 3은 보라, 강철은 회색에 사선 무늬, 폭탄은 붉은 계열에 점 표시. 맞을 때마다 색이 바뀌므로 숫자 표기 불필요
> - 패들: 둥근 모서리 막대. 아이템으로 길이가 변할 때 폭에 트랜지션을 줘서 늘어나는 게 눈에 보이게
> - 공: 단색 원 + 짧은 잔상(이전 3~4프레임 위치를 투명도 낮춰 그림). 잔상 하나로 속도감이 크게 살아남
> - 파티클: 벽돌이 깨질 때 그 벽돌 색으로 6~8개를 튀김. 사운드 없이 타격감을 내는 유일한 수단
> - 아이템 캡슐: 종류별 색 + 한 글자 라벨
>
> 오버레이: 시작 전(`ready`)에는 공이 패들에 붙어 있고 `탭해서 발사` 안내. 첫 조작 전에만 하단에 옅은 `드래그해서 이동` 안내. 스테이지 클리어 / 게임 오버 시 반투명 레이어 + 버튼
>
> **3. 상태 구조**
>
> ```js
> {
>   status: 'ready',        // ready | playing | paused | cleared | over
>   stage: 1,
>   score: 0,
>   best: 0,
>   lives: 3,
>   paddle:  { x, width, baseWidth },
>   balls:   [ { x, y, vx, vy, speed, radius, piercing } ],
>   bricks:  [ { id, col, row, hp, maxHp, type } ],   // type: normal | steel | bomb
>   items:   [ { id, x, y, kind } ],
>   effects: { wide: 0, slow: 0, pierce: 0, multi: 0 }, // 남은 시간(ms)
>   particles: []
> }
> ```
>
> 두 가지를 처음부터 이렇게 잡아주세요.
> - 공은 반드시 배열. 나중에 멀티볼을 넣으려고 단일 객체를 배열로 바꾸면 충돌 처리부터 목숨 차감까지 전부 고쳐야 합니다. 목숨은 "공 배열이 비었을 때" 차감하면 멀티볼과 자연스럽게 맞물립니다
> - 효과는 불리언이 아니라 남은 시간(ms). 같은 아이템을 중복으로 먹었을 때 시간이 연장되어야 합니다
>
> **4. 물리와 반사 처리** — 여기가 이 게임의 핵심 설계 포인트입니다.
>
> *패들 반사는 물리가 아니라 위치로 결정* — 입사각=반사각으로 구현하면 공이 수평에 가깝게 갇혀 최악의 플레이가 됩니다. 패들의 어느 지점을 맞았는지로 각도를 정하세요.
>
> ```js
> const hit = (ball.x - paddle.x) / (paddle.width / 2); // -1 ~ 1
> const angle = hit * (Math.PI / 3);                    // 최대 60도
> ball.vx = ball.speed * Math.sin(angle);
> ball.vy = -ball.speed * Math.cos(angle);
> ```
>
> 플레이어가 각도를 의도적으로 조준할 수 있게 되고, 이게 벽돌깨기의 실력 요소 전부입니다. 속도는 `speed` 스칼라로 따로 관리해야 반사할 때마다 속도가 미묘하게 변하는 문제가 없습니다.
>
> *벽돌 충돌은 맞은 면을 판정* — 무조건 `vy = -vy`로 하면 옆구리를 스칠 때 공이 벽돌 속으로 파고듭니다. 겹침이 작은 축을 뒤집으세요.
>
> ```js
> if (overlapX < overlapY) ball.vx = -ball.vx;
> else                     ball.vy = -ball.vy;
> ```
>
> *프레임당 벽돌 하나만 처리* — 관통 상태가 아니라면, 한 프레임에 두 벽돌에 닿아도 가까운 하나만 깨고 반사도 한 번만. 안 그러면 `vy`를 두 번 뒤집어 공이 원래 방향으로 되돌아갑니다.
>
> *반드시 막아야 할 함정 3가지*
> 1. 터널링 — 속도가 빨라지면 한 프레임에 벽돌을 뛰어넘습니다. 공 이동을 한 번에 하지 말고 `속도 / 반지름` 만큼 잘게 나눠 여러 번 이동+판정 하세요. 속도 상한도 함께 두세요
> 2. 수평 갇힘 — `Math.abs(vy)`가 `speed * 0.2` 아래로 내려가면 강제로 올려주세요. 안 하면 공이 벽 사이를 영원히 왕복하는 걸 지켜봐야 합니다
> 3. 프레임 의존 — `requestAnimationFrame`의 delta time으로 이동량을 계산하세요. 120Hz 기기에서 두 배로 빨라지는 사고를 막습니다
>
> **5. 게임 규칙**
> - `ready` 상태에서 공이 패들에 붙어 있고, 화면을 탭하면 발사
> - 강철을 제외한 모든 벽돌이 사라지면 스테이지 클리어. 다음 스테이지는 공 속도 +8%
> - 공이 바닥 아래로 나가면 배열에서 제거. 배열이 비면 목숨 -1 후 `ready`로 복귀. 목숨이 0이면 게임 오버
> - 벽돌: `normal`(hp 1~3) / `steel`(파괴 불가, 점수 없음, 클리어 조건 제외) / `bomb`(파괴 시 상하좌우 1칸 연쇄, 깊이 제한)
> - 점수: 벽돌 파괴 시 `10 × 스테이지 배율`
> - 아이템: 벽돌 파괴 시 12% 확률로 캡슐 낙하, 패들로 받아야 발동. `wide` / `slow` / `pierce` / `multi` / `shrink`(함정). 지속형은 8초
>
> 레벨 데이터는 문자열 배열로 정의해 레벨 추가가 한 줄로 끝나게 해주세요. 최소 5스테이지.
>
> ```js
> const STAGES = [
>   [ "1111111111",
>     "1122221111",
>     "0011S11100" ],   // 0=빈칸, 1~3=내구도, S=강철, B=폭탄
> ];
> ```
>
> **완료 조건**
> - 모바일 세로 화면에서 엄지 하나로 무리 없이 플레이 가능
> - 스테이지 5개를 끝까지 진행할 수 있고, 클리어와 게임 오버가 모두 정상 동작
> - 위 "함정 3가지"가 실제로 재현되지 않는지 확인

**결과:** 폴더 연결 → `index.html` 한 개 생성. 여기서도 셸로 긴 HTML을 밀어 넣다가 파일이 깨져서, 파일 쓰기 도구로 다시 작성했다. **2048 때와 똑같은 지점에서 똑같이 걸렸다.**

**고친 점:** 이번에도 내가 다시 요청한 건 없다. 대신 검증 과정에서 **진짜 버그 하나가 나왔다.**

### 그 사이 — 검증에서 걸린 것 (11:44 ~ 11:51)

내가 설계안에 적은 규칙은 이랬다.

> 무조건 `vy = -vy`로 하면 옆구리를 스칠 때 공이 벽돌 속으로 파고듭니다. **겹침이 작은 축을 뒤집으세요.**

맞는 규칙이었다. 그런데 **공이 벽돌 사이 틈으로 똑바로 위를 향해 들어가는 경우**가 있었다. 이때 좌우 겹침이 더 작으니 규칙대로 `vx`를 뒤집는데, 수직으로 올라가는 공은 `vx`가 0이다. **0을 뒤집어도 0이라 반사가 아예 일어나지 않고**, 공은 벽돌 두 개를 그대로 통과했다.

고친 방법은 한 줄 추가다. 겹침의 크기만 보지 말고 **그 축으로 실제 다가가고 있는지**를 함께 본다.

같은 검증에서 나온 나머지 수정 셋.

- 프레임당 벽돌 하나만 처리하도록 플래그를 둬서 보강
- `restart()`에서 패들 위치를 가운데로 되돌리지 않던 것 수정 — 새 게임을 시작해도 패들이 죽은 자리에 남아 있었다
- `드래그해서 이동` 안내 문구를 조작 영역 위쪽으로 이동

그리고 함정 3가지는 **실제로 재현을 시도해서** 확인했다.

## 4. 코드에서 배운 부분

### 4-1. 반사각을 물리가 아니라 위치로 정하면 생기는 일

{% include figure.html src="/assets/images/brick-crush/paddle-angle.svg" alt="패들의 맞은 지점 -1에서 1까지가 -60도에서 60도 반사각으로 이어지는 그림" caption="그림 10. 패들의 어디를 맞았는지가 곧 각도다" %}

```javascript
function bounceOffPaddle(ball){
  const p = state.paddle;
  const hit   = clamp((ball.x - p.x) / (p.width / 2), -1, 1);   // -1 ~ 1
  const angle = hit * (Math.PI / 3);                            // 최대 60도
  ball.vx =  ball.speed * Math.sin(angle);
  ball.vy = -ball.speed * Math.cos(angle);
  ball.y  = PADDLE_Y - ball.radius - 0.5;
}
```

현실의 반사를 흉내 내지 않았더니 오히려 게임이 됐다. 패들 끝으로 받으면 크게 꺾이고 가운데로 받으면 곧게 올라가니까, **어디로 받을지 고르는 것이 실력**이 된다. 그리고 방향만 각도로 정하고 빠르기는 `speed` 하나로 따로 들고 있어서, 몇 번을 튕겨도 속도가 흔들리지 않는다.

### 4-2. 조건이 맞아도 실행할 게 없을 수 있다

수정 후의 충돌 처리 코드다.

```javascript
// 겹침이 작은 축을 고르되, 그 축으로 실제 접근 중일 때만.
// (벽돌 사이 틈으로 수직 진입하면 overlapX가 더 작아도 vx는 뒤집을 게 없다)
const approachX = (ball.x < bcx && ball.vx > 0) || (ball.x > bcx && ball.vx < 0);
const approachY = (ball.y < bcy && ball.vy > 0) || (ball.y > bcy && ball.vy < 0);

if ((overlapX < overlapY && approachX) || !approachY){
  ball.vx = -ball.vx;
  ...
```

`overlapX < overlapY`는 **틀린 조건이 아니었다.** 조건은 맞았는데 그 조건이 고른 동작(`vx` 반전)이 그 상황에서는 아무것도 하지 않았을 뿐이다. 조건문을 볼 때 "이 조건이 참인가"만 보면 안 되고 **"참일 때 하는 일이 실제로 의미가 있는가"**까지 봐야 한다는 걸 여기서 배웠다.

### 4-3. 함정 3가지를 막은 방법

{% include figure.html src="/assets/images/brick-crush/traps.svg" alt="터널링·수평 갇힘·프레임 의존 세 함정과 각각의 대응 방법" caption="그림 11. 만들기 전에 이름을 붙여 뒀기 때문에 만든 뒤에 확인할 수 있었다" %}

셋 다 "돌려보면 멀쩡해 보이는" 종류다. 느린 기기에서, 특정 속도에서, 특정 각도에서만 나타난다. 그래서 **만든 다음에 찾는 게 아니라 만들기 전에 이름을 붙여 두는 쪽**이 맞았다. 4-2의 버그도 결국 같은 방식으로 잡혔다 — 재현 조건을 코드로 만들어 수백 번 반복하니 드러났다.

## 5. 막혔던 점과 해결

| 막힌 지점 | 원인 | 해결 방법 |
| --- | --- | --- |
| 벽돌 사이 틈으로 들어간 공이 벽돌 2개를 통과 | 겹침이 작은 축(`vx`)을 뒤집었는데 수직 진입이라 `vx`가 0. 0을 뒤집어도 0 | 그 축으로 접근 중인지 확인하는 조건 추가 (그림 4) |
| 긴 HTML을 셸로 넣다가 파일이 깨짐 | 2048 때와 같은 문제 — 긴 텍스트를 셸 명령으로 밀어 넣으면 셸이 먼저 해석한다 | 파일 쓰기 도구로 통째로 작성 |
| 새 게임을 시작해도 패들이 죽은 자리에 남아 있음 | `restart()`가 점수·목숨·스테이지만 되돌리고 패들 위치를 빼먹음 | 패들을 화면 가운데로 되돌리는 한 줄 추가 |
| 최고 점수 저장을 로컬에서 확인 못 함 | 미리보기가 `data:` 주소로 열려 브라우저 저장소에 접근할 수 없었다 | 배포 후 실제 `https://` 주소에서 저장·재읽기 확인 |
