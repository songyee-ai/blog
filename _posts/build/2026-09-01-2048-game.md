## 1. 만들기 전 스케치

코드를 한 줄도 쓰기 전에 **설계안을 먼저 한 장 썼다.** 화면, 상태, 규칙, 모바일에서 챙길 것 네 덩어리다.

{% include figure.html src="/assets/images/2048-game/sketch.svg" alt="상단 바·안내문·4×4 보드로 구성된 세로 한 화면 구상도와 설계안 항목들" caption="그림 1. 설계안에 적어 둔 화면 — 첫 줄이 '세로 한 화면에 다 들어가야 한다'였다" %}

여기서 제일 중요한 판단은 화면이 아니라 **상태를 어떻게 들 것인가**였다.

> 보드를 숫자 16칸 배열로만 들고 있으면 이동 애니메이션을 못 만듭니다. "어느 타일이 어디서 어디로 갔는지"를 알 수 없기 때문입니다. 그래서 타일에 고유 id를 부여합니다.

이 한 문단이 이 게임의 유일한 설계 포인트였다. 실제로 만들고 나서 보니 코드의 절반이 이 결정에서 갈라져 나왔다.

## 2. 만드는 과정 — 프롬프트 기록

먼저 정직하게 적어 두면, **내가 넣은 프롬프트는 두 번뿐이다.** 시도 1에서 설계안을 통째로 넣었고, 마지막에 배포 여부를 골랐다. 그 사이 12분은 AI가 혼자 만들고 혼자 검증한 시간이다.

{% include figure.html src="/assets/images/2048-game/timeline.svg" alt="17시 14분 설계안 투입부터 17시 34분 배포까지의 22분 타임라인" caption="그림 2. 22분 동안 실제로 일어난 일 — 파란 칸이 내가 한 것" %}

### 시도 1 — 설계안 전문 (17:14)

> game_2048 폴더를 만들고, 깃허브의 game_2048 레포지토리와 연결해줘. 우리는 게임 2048을 만들거야. 결과물은 온라인에서 바로 할 수 있는 html로 만들어줘. **아래 내용에서 수정하거나 첨가하고 싶은 아이디어가 있으면 함께 제안해줘.**
>
> **2048 설계안**
>
> **보이는 것** — 세로 한 화면에 다 들어가야 합니다. 위에서부터:
> - 상단 바: 좌측에 `2048` 타이틀, 우측에 현재 점수와 최고 점수를 작은 박스 두 개로
> - 그 아래 한 줄 안내문과 `새 게임` 버튼
> - 4×4 보드. 화면 폭의 90%를 쓰고 `aspect-ratio: 1`로 정사각형 고정. 회색 배경판 위에 빈 칸 16개를 먼저 깔고, 타일은 그 위에 절대 위치로 얹음
> - 타일은 값에 따라 배경색이 달라짐. 2·4는 밝은 베이지에 어두운 글씨, 8 이상은 채도 높은 주황 계열에 흰 글씨. 자릿수가 늘어나면 폰트 크기를 줄임
> - 게임 오버 시 보드 위에 반투명 레이어와 `다시 하기`. 2048 달성 시엔 `계속하기` 버튼도 함께
>
> 애니메이션은 세 종류만 있으면 충분합니다. 새 타일이 나타날 때 팝(scale 0→1), 이동할 때 위치 트랜지션, 병합될 때 살짝 커졌다 돌아오는 바운스.
>
> **상태** — 여기가 이 게임의 유일한 설계 포인트입니다. 보드를 숫자 16칸 배열로만 들고 있으면 이동 애니메이션을 못 만듭니다. "어느 타일이 어디서 어디로 갔는지"를 알 수 없기 때문입니다. 그래서 타일에 고유 id를 부여합니다.
>
> ```js
> {
>   tiles: [ { id: 7, value: 4, row: 2, col: 0, isNew: false, merged: false } ],
>   score: 1240,
>   best: 8192,          // 영속 저장
>   status: 'playing',   // 'playing' | 'won' | 'over'
>   keepPlaying: false   // 2048 이후 계속하기 여부
> }
> ```
>
> 계산은 4×4 숫자 격자로 하고, 그 결과를 `tiles` 배열에 반영하는 식으로 두 표현을 나누는 게 편합니다. 병합된 타일은 기존 id를 유지하고 사라지는 쪽 id를 제거하면, 두 타일이 겹쳐지며 합쳐지는 모습이 자연스럽게 나옵니다.
>
> **규칙**
> 1. 시작할 때 빈 칸 중 임의의 두 곳에 타일 생성. 값은 90% 확률로 2, 10% 확률로 4
> 2. 스와이프가 들어오면 그 방향으로 한 줄씩 처리: 빈 칸을 없애 한쪽으로 몰고 → 인접한 같은 값을 병합하고 → 다시 몬다
> 3. 한 번의 이동에서 각 타일은 최대 한 번만 병합됩니다. `4 4 4 4`는 `8 8`이 되어야 하고 `16`이 되면 버그입니다
> 4. 방향은 4개지만 한 줄을 왼쪽으로 미는 함수 하나만 만들고, 격자를 회전시켜 재사용합니다. 상하좌우 로직을 각각 쓰면 버그가 4배로 늘어납니다
> 5. 병합 시 합쳐진 값만큼 점수에 더함
> 6. 격자가 실제로 바뀌었을 때만 새 타일을 생성합니다. 벽에 붙은 방향으로 스와이프해도 타일이 늘어나면 억울한 게임이 됩니다
> 7. 게임 오버 판정: 빈 칸이 없고, 네 방향 모두 시뮬레이션해도 격자가 변하지 않을 때
> 8. 2048이 등장하면 승리 표시. 단 계속 진행할 수 있게 함
>
> **모바일에서 챙길 것**
> - `touchstart`와 `touchend`의 좌표 차이로 방향 판정. 임계값은 30px 정도, x와 y 절대값을 비교해 큰 축을 채택
> - 보드에 `touch-action: none`을 주지 않으면 스와이프할 때마다 페이지가 스크롤되거나 당겨집니다. 이거 하나로 체감 품질이 갈립니다
> - 더블탭 확대 방지를 위해 `user-select: none`과 뷰포트 메타 태그
> - 데스크톱 테스트용으로 방향키도 같이 받아두면 개발이 훨씬 빠릅니다

**결과:** 폴더 생성 → `git init` → 원격 저장소 연결까지 먼저 하고, `index.html` 한 개를 만들었다.
첫 시도는 셸에서 긴 HTML을 한 번에 밀어 넣다가 **파일이 깨졌다.** 다시 파일 쓰기 도구로 통째로 작성해서 해결.

**고친 점:** 이 단계에서 내가 다시 요청한 건 없다. 대신 AI가 만든 결과를 스스로 브라우저에 띄워 검증했고, 그 과정에서 나온 수정이 두 가지였다.

### 그 사이 — AI가 혼자 돌린 검증 (17:20 ~ 17:32)

| 확인한 것 | 방법 | 결과 |
| --- | --- | --- |
| 회전·병합 알고리즘 | 순수 함수로 떼어내 단위 테스트 17개 (`4444→8800`, `224→44`, `222→42`, 4방향 매핑) | 17/17 통과 |
| 판이 망가지지 않는가 | 랜덤 90수 두고 칸 중복·좌표 이탈·점수 감소·타일 17개 초과 검사 | 오류 0 |
| 되돌리기 | 보드와 점수가 직전 상태와 일치하는지 | 8/8 일치 |
| 승리 → 계속하기 | 목표값을 64로 낮춘 임시 사본으로 승리 화면 재현 | 정상 |
| 게임 오버 | 빈 칸 0 + 네 방향 모두 변화 없음 | 정상 |
| 모바일 터치 | 스와이프 4방향, 임계값 미달 무시, 페이지 스크롤 차단 | 전부 정상 |

중간에 **"왼쪽·위만 눌렀는데 아무 일도 안 일어난다"**를 버그로 의심했는데, 확인해 보니 그 판에서 두 방향이 **실제로 아무것도 바꾸지 못하는 상태**였다. 규칙 6(격자가 바뀌었을 때만 새 타일)이 제대로 동작한 것이었다. 네 방향 랜덤으로 다시 돌려서 게임 오버까지 확인.

그리고 눈으로 보고 고친 것 하나. **게임 오버 화면의 글씨가 뒤의 타일과 겹쳐서 읽히지 않았다.** 보드 전체를 덮는 반투명 레이어 위에 글자를 얹은 구조였기 때문이다. 가운데 카드 패널로 바꾸고 문구를 정리했다.

### 왕복이 없었던 이유

프롬프트를 여러 번 주고받지 않은 게 운이 좋아서는 아닌 것 같다. 설계안에 이런 문장들을 미리 적어 둔 게 컸다.

- "`4 4 4 4`는 `8 8`이 되어야 하고 `16`이 되면 버그입니다"
- "벽에 붙은 방향으로 스와이프해도 타일이 늘어나면 억울한 게임이 됩니다"
- "`touch-action: none`을 주지 않으면 스와이프할 때마다 페이지가 스크롤됩니다"

전부 **"이렇게 되면 틀린 것"**을 적은 문장이다. 만들 것만 적으면 결과를 볼 때 "음, 되네"밖에 할 말이 없는데, 틀린 모습을 미리 적어 두면 그게 그대로 검사 항목이 된다. 고칠 거리가 나에게 오기 전에 걸러진 셈이다.

## 4. 코드에서 배운 부분

### 4-1. 방향 네 개를 로직 하나로

설계안 규칙 4에 적은 내용인데, 실제 코드를 보고 나서야 왜 그런지 알았다.

{% include figure.html src="/assets/images/2048-game/rotation.svg" alt="네 방향이 회전 횟수 k로 바뀌어 '왼쪽으로 밀기' 로직 하나로 모이는 구조도" caption="그림 7. 방향은 네 개, 로직은 하나" %}

핵심은 이 여섯 줄이다.

```javascript
var DIRS = ['left', 'down', 'right', 'up'];   // 배열 인덱스 = 격자 시계방향 회전 횟수

// 격자를 시계방향으로 k번 돌렸을 때의 좌표 (r,c)가 원본 격자에서 어디였는지 되돌린다
function back(r, c, k) {
  for (var i = 0; i < k; i++) { var nr = N - 1 - c; c = r; r = nr; }
  return [r, c];
}
```

"위로 밀기"를 따로 구현하지 않는다. 격자를 세 번 돌려서 **읽는 순서만 바꾸면** 그건 이미 "왼쪽으로 밀기"다. 밀기 로직은 한 벌만 존재하고, 고칠 일이 생겨도 한 군데만 고치면 된다.

### 4-2. 합쳐진 타일은 바로 지우지 않는다

설계안에는 "사라지는 쪽 id를 제거"라고 적었는데, 그대로 하면 **두 타일이 겹쳐지는 장면이 아예 안 보인다.** 이미 사라진 뒤니까.

{% include figure.html src="/assets/images/2048-game/merge.svg" alt="병합 직전, 이동 중, 정리 후 세 단계로 나눈 타일의 수명 다이어그램" caption="그림 8. 사라지는 타일도 130ms 동안은 살아 있어야 한다" %}

```javascript
plan.merges.forEach(function (m) {
  var p = plan.pos.get(m.survivor.id);
  m.victim.row = p[0]; m.victim.col = p[1];   // 사라지는 타일을 살아남는 쪽 칸으로 보내고
  m.victim.dying = true;                       // 표시만 해 둔다 (아직 안 지운다)
});

// 새 타일은 이동이 거의 끝난 시점에 등장시킨다 (동시에 뜨면 어디서 왔는지 읽기 어렵다)
var born = spawn(alive, Math.round(MOVE * 0.8));
```

애니메이션이 끝나는 시점(`130ms + 20`)에 `dying` 타일을 실제로 지운다. **"언제 지우는가"가 화면의 자연스러움을 만든다**는 게 이 코드에서 배운 부분이다.

### 4-3. 설계안과 다르게 구현된 곳 세 군데

내가 쓴 설계안이 전부 그대로 간 건 아니다. 바뀐 데가 셋 있고, 셋 다 이유가 분명했다.

| 설계안 | 실제 구현 | 왜 |
| --- | --- | --- |
| 사라지는 쪽 id를 제거 | `dying`으로 남겼다가 애니메이션 후 제거 | 즉시 지우면 합쳐지는 장면이 안 보인다 |
| 이동할 때 위치 트랜지션 | Web Animations API | 클래스를 토글하는 방식은 **연속으로 병합될 때** 같은 클래스가 유지돼 다시 재생되지 않는다 |
| 보드는 화면 폭의 90% | `min(92vw, 440px, 66dvh)` | 가로 폭만 기준으로 삼으면 화면이 낮을 때(가로 모드) 보드가 화면을 넘는다 |
